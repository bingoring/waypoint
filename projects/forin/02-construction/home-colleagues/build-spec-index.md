# Build Spec — 홈 탭 · 동료 시스템

SoT: 디자인 핸드오프 **v20**(홈 신설) → **v21**(동료 시스템 + 홈의 PeerTicker를 실제 동료로 교체).

## §0. 개요 & 범위

### 왜

커리어 탭은 커리큘럼·건물·상황이 전부 **목록**으로 펼쳐져 있어, 앱을 켜자마자 마주하면
"골라야 한다"는 압박이 된다. 홈은 그 반대 원칙이다 — **오늘 할 딱 한 가지**만 크게, 성취를
먼저, 나머지는 얕은 문.

v21은 여기에 **동료**를 얹는다. 익명 티커("같은 목표를 준비하는 사람들")는 관계가 남지
않으므로, 초대 코드로 맺는 관계로 바꾸고 응원을 주고받게 한다. 관계 타입(`peer`/`mentor`/
`mentee`)을 **처음부터 데이터에 둬서**, 추후 현지 간호사 멘토–멘티로 확장할 때 화면 구조를
바꾸지 않아도 되게 한다.

### 범위 (In)

- 홈 탭 신설 — 모듈 10종, 2상태(진행/완료). **탭 5개로 확장, 홈이 최좌측·기본 진입**
- 동료 시스템 — 목록 / 코드 추가 / 상세 / 응원 시트, 프로필 탭의 동료 카드(관리 소유권)
- 서버 전체 — 마이그레이션, `colleague` 도메인, 홈 집계 엔드포인트, 콘텐츠 풀

### 범위 밖 (Out)

- 멘토–멘티 **매칭·검증·정산** (관계 타입과 화면만 준비. "현지 간호사 멘토 매칭은 준비 중이에요")
- 푸시 알림 (응원 도착 알림은 인박스 뱃지로만)
- 실시간 소켓 프레즌스 (§business-logic-model §1 `UpdatePresence` 참조)

### 더미 금지

이 스펙의 전제: **홈의 어떤 모듈도 하드코딩 문자열로 채우지 않는다.** 값이 없으면 모듈을
숨긴다. 핸드오프의 문자열은 전부 프로토타입 예시이며 그대로 옮기지 않는다.

## §3. 결정 (2026-08-10 확정 — 구현 착수 가능)

| ID | 질문 | 결정 |
|---|---|---|
| Q1 | `ShiftBadge`의 날씨(☀27°) | **제거.** 더미 금지 원칙과 일관. 근무·배치만으로 세계관 연출은 충분하고, 위치 권한·외부 의존이 생기지 않는다 |
| Q2 | 멘토 쪽지·한마디 초기 콘텐츠 | **이번 스코프에서 시드 작성.** 부서별 멘토 쪽지 ~24, 현장 표현 ~30 → 한 달 반복 없음 |
| Q3 | 홈·동료의 이모지 | **라인 아이콘으로 통일.** 기존 뱃지·칭호·스티커·미션 전환 방침과 일관. `PixelIcon`에 필요한 이름 추가(§frontend-components) |
| Q4 | ⚔ 대결 | **이번 범위 제외.** 버튼을 렌더하지 않는다(동작 없는 버튼을 남기지 않음). 규칙 설계가 선행돼야 함 |

**선결정(근거와 함께 확정):**
- 프레즌스 공개 **기본값 = 공개**. 동료는 상호 수락으로만 맺어지므로 기본 공개가 자연스럽고,
  `colleague_prefs`로 언제든 끌 수 있다(R-10/11).
- 코드 입력은 **즉시 연결이 아니라 요청**. 코드 유출이 곧 현황 유출이 되면 안 된다.

## §5. 검증 계획

| 대상 | 방법 |
|---|---|
| 도메인 규칙 | Go 단위 테스트 — 코드 생성·정규화, `MirrorRelation`, 60 rune 경계(한글), 자기추가·중복·역방향 자동수락 |

| 홈 집계 | 모듈별 데이터 없음 → 해당 필드 **부재** 확인 |

| 모바일 | `tsc` + `jest` + 시뮬레이터 렌더(홈 2상태 · 동료 4화면) |
