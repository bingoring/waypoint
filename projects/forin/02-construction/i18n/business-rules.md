# 비즈니스 규칙 — 다국어

## 로케일 해석

| # | 규칙 | 근거 |
|---|---|---|
| R1 | **UI 언어**와 **학습 대상 언어**는 별개 축이다. 한국인이 미국으로 가면 UI=ko, 학습=en이다. 하나로 합치면 독일어 UI로 영어를 배우는 조합이 표현 불가능해진다 | 사용자 지시(설정=UI, 온보딩=학습) |
| R2 | UI 언어 해석 순서: **프로필 설정 → 온보딩의 모국어 → 기기 로케일 → `ko`** | 설정이 최우선이어야 "설정으로 바꾼다"가 성립한다 |
| R3 | 학습 대상 언어는 **목적지 나라**에서 파생한다(`us→en`, `de→de`). 목적지가 곧 대상 언어를 정하므로 두 값을 따로 묻지 않는다 | 기존 `locale.tsx`의 `DEST.targetLang` 유지 |
| R4 | 서버는 요청마다 UI 로케일을 받는다(`Accept-Language`). 프로필에 저장된 값이 **정본**이고 헤더는 로그인 전 화면을 위한 보조다 | 온보딩·로그인 화면도 번역돼야 한다 |

## 폴백

| # | 규칙 | 근거 |
|---|---|---|
| R5 | 키가 선택 로케일에 없으면 **`ko`로 폴백**하고, `ko`에도 없으면 **키 문자열 자체**를 보인다. 빈 문자열이나 크래시는 금지 | 번역은 점진적으로 채워진다 — 미완성 상태가 앱을 깨뜨려선 안 된다 |
| R6 | 폴백이 일어나면 **개발 빌드에서만** 경고를 남긴다. 프로덕션에서 콘솔을 더럽히지 않는다 | — |
| R7 | 서버 콘텐츠 문자열도 같은 사슬을 탄다. 커리큘럼 이름이 그 로케일에 없으면 한국어 원문을 보낸다 | 부분 번역 상태에서 목록이 비면 앱이 고장난 것처럼 보인다 |

## 완성도 표시 (야매 금지)

| # | 규칙 | 근거 |
|---|---|---|
| R8 | 로케일은 **완성도**를 갖는다: `full`(UI+콘텐츠) · `ui`(UI만) · `partial`. 설정 화면과 온보딩은 이 값을 **그대로 보여준다** | 사용자 지시 "야매로 하지 말고". 부분 번역을 완전한 것처럼 제시하지 않는다 |
| R9 | 완성도는 **계산된다** — 카탈로그의 키 수를 `ko` 대비로 세어 산출한다. 손으로 적은 라벨은 낡는다 | 자동 산출이면 번역을 채우는 만큼 표시가 따라온다 |
| R10 | 의료 용어가 든 문자열은 기계번역으로 채우지 않는다. 번역이 없으면 R5의 폴백을 탄다 | 오역이 안전 문제가 된다("구획증후군 의심 사정") |
| R11 | 목적지는 **저작된 학습 문장이 그 언어로 존재할 때만** 완전 지원으로 표시한다. AI 대화는 프롬프트로 어느 언어든 되지만 `tagline`/`keyPhrases`는 저작물이다 | 대화만 독일어이고 예시 문장이 영어인 상태를 "독일 지원"이라 부를 수 없다 |

## 구현 규율

| # | 규칙 | 근거 |
|---|---|---|
| R12 | 화면에 새 한국어 리터럴을 넣지 않는다. 문자열은 카탈로그에만 있고, 테스트가 `src/app`·`src/components`의 한글 리터럴 수를 **상한으로 고정**한다 | 추출한 다음 다시 새는 것을 막는 유일한 방법이다. `762bb6a`의 이모지 규율과 같은 형태 |
