# 실행 모델 — 다국어

## §1. 단계

각 단계는 **독립적으로 검증 가능하고 배포 가능**하다. 4,788개 번역을 한 커밋에 밀어넣으면 리뷰가
불가능하고, 중간에 끊기면 앱이 반쪽 상태로 남는다.

| 단계 | 내용 | 검증 |
|---|---|---|
| **P1** | 클라이언트 i18n 레이어 + 프로필 언어 설정 + 로케일 해석/폴백 | 설정에서 바꾸면 즉시 반영. 카탈로그가 `ko` 하나뿐이어도 동작 |
| **P2** | UI 크롬 513개 + `map`/`engine` 120개를 키로 추출 (`ko` 카탈로그로 이사) | 한글 리터럴 상한 테스트(R12). 화면 문자열은 한 글자도 바뀌지 않아야 한다 |
| **P3** ✅ | 서버 로케일 파이프라인: `profiles.ui_lang` + `Accept-Language` + 서버 카탈로그. 커리큘럼 이름 89 + 층 24 + 상황 태그 3을 영어로. **스텝 이름 약 400개는 폴백(P6)** | `ResolveLocalized`가 ko/en에서 다른 이름을 내는지 세는 테스트. 89개 전부 번역 확인 |
| **P4** | 인테리어 픽스처 1,095개 추출 | 위와 동일 |
| **P5** | 목적지별 저작 학습 문장(`tagline`/`keyPhrases`) 로케일 차원 + 온보딩 목록을 실제 완성도와 일치 | 독일 선택 시 예시 문장이 독일어이거나, 아니면 "준비 중"으로 표시된다 |
| **P6** | `en`/`ja`/`de` 카탈로그 번역 채우기 | 완성도 산출값이 올라간다(R9) |

**P1이 먼저인 이유:** 추출(P2)은 레이어가 있어야 갈 곳이 있다. 그리고 P1만 끝나도 "설정에서 언어를
바꾼다"는 골격이 완성돼, 나머지는 카탈로그를 채우는 일로 환원된다.

## §2. 클라이언트 레이어 설계

```
src/i18n/
  locales.ts   지원 로케일 + 완성도 산출
  catalog/ko.ts en.ts ja.ts de.ts
  store.ts     선택값(expo-secure-store) + 구독
  index.ts     t(key, vars?) · useLocale() · setLocale()
```

- **정적 import 4개.** 동적 `require`를 쓰지 않는다 — Metro는 정적 해석이라 계산된 경로는 번들에
  들어가지 않는다(`sfx.ts`에서 같은 이유로 `require`를 정적으로 썼다).
- **`t()`는 훅이 아니다.** 컴포넌트 밖(유틸·상수)에서도 불려야 한다. 대신 `useLocale()`이 리렌더를
  구독하고, 화면은 그 훅을 한 번 부른 뒤 `t()`를 쓴다. 훅 전용으로 만들면 `STEP_META` 같은 모듈
  상수를 번역할 수 없다.
- **보간:** `t('x.y', { n: 3 })` → `"{n}일 연속"`. 복수형은 **넣지 않는다** — 한국어에 복수형이 없고,
  영어에서 필요한 자리는 키를 둘로 나누는 편이 예측 가능하다(YAGNI).
- **영속:** `expo-secure-store` (레포 선례: `onboardingDraft.ts`, `sfx.ts`).

## §3. 키 이름 규칙

```
<화면 또는 컴포넌트>.<의미>        campus.resume, dialogue.exitTitle
common.<의미>                     common.cancel, common.done
step.kind.<종류>                  step.kind.boss
```

의미로 짓는다. `campus.text1` 같은 위치 기반 키는 문자열이 옮겨지면 거짓이 된다.

## §4. 서버 파이프라인 (P3)

- 요청 로케일: `Accept-Language`의 첫 태그를 지원 목록과 대조 → 없으면 프로필 `ui_lang` → 없으면 `ko`.
- 커리큘럼 이름/스텝 이름은 **이미 있는 `Key`/`ScenarioID`를 키로 재사용**한다. 새 키 체계를 만들지
  않으므로 이름을 다듬어도 키가 안 바뀐다.
- **한국어는 카탈로그에 넣지 않는다.** 저작된 한국어가 `authored_*.go`에 그대로 남고, 조회마다 그
  문자열을 폴백으로 넘긴다(`i18n.Tr(locale, c.Key, c.Name)`). 결과: 번역 없는 로케일은 **오늘과
  똑같이** 렌더되고, 언어 추가가 콘텐츠 파일을 한 줄도 건드리지 않으며, 저작된 이름을 읽는 불변식
  테스트(커리큘럼 v2의 `catalog_content_test.go`)가 계속 유효하다.
- **구현 중 변경:** 미들웨어는 프로필을 읽지 않고 `Accept-Language`만 본다. 언어를 알기 위해 DB
  왕복을 추가하면 앱 첫 화면까지 느려지고, 클라이언트는 이미 자기 설정을 안다. `profiles.ui_lang`은
  **재설치 시 복구용**이고 요청마다 조회하는 값이 아니다.
- **상황 태그를 코드/라벨로 쪼갰다.** `tag`가 한국어 하나로 상태와 표시를 겸해서, 클라이언트가
  `'완료'`와 비교할 수밖에 없었다 — 그 문자열은 비교를 깨지 않고는 번역이 불가능했다. 이제
  `tagCode`(cleared/urgent/new)로 비교하고 `tag`는 요청 언어 라벨이다. 이걸로 클라이언트의 마지막
  한국어 비교 3개가 사라졌다.

## §5. 검증 (야매 방지)

1. **R12 상한 테스트** — `src/app`·`src/components`의 한글 리터럴 수를 세어 상한을 넘으면 실패.
   숫자는 각 단계에서 내려간다. 이것이 "다시 새는 것"을 막는 유일한 기계적 장치다.
2. **키 대조 테스트** — 각 로케일 카탈로그의 키가 `ko`의 부분집합인지(오타 키를 잡는다). `ko`에만 있는
   키는 미번역으로 세어 완성도가 된다(R9).
3. **보간 인자 테스트** — 같은 키의 번역이 `ko`와 **같은 변수 집합**을 쓰는지. `{n}`을 빠뜨린 번역은
   숫자가 사라진 문장을 만든다.
