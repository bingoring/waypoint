# 비즈니스 규칙 — P2 전수조사

> P1의 R1~R22를 상속한다(특히 R1 한 상황=한 주제, R2 ≥20, R3 고아 0, R7 명시 태그). 아래는 P2 고유 규칙.

## 태깅 규칙

| # | 규칙 | 근거 |
|---|---|---|
| R-P2-1 | **생성 시나리오의 theme은 소스 Topic.Theme에서 emit된다.** 시나리오 파일을 손으로 태깅하지 않는다 — 생성분은 코드(depts*.go)에서 파생 | 결정성·규모 (index §0.5) |
| R-P2-2 | **손저작 시나리오(scn-*.yaml)만 파일에 `theme:`을 직접 쓴다.** 반자동 매핑 후 사람 검수 | logic §4 |
| R-P2-3 | **모든 Topic은 유효한 Theme을 갖는다.** `gencontent` 테스트가 "Topic.Theme != '' && 레지스트리에 존재"를 강제 | logic §3 |

## 묶음(주제 경계) 규칙

| # | 규칙 | 근거 |
|---|---|---|
| R-P2-4 | **주제는 Topic 2~3개를 묶어 시나리오 ≥20을 이룬다.** 한 Topic만으로 20을 넘으면 단독 주제도 허용. 20 미만이면 인접 주제와 병합하거나 Topic/페르소나를 추가해 보강 | U2·index 규모 |
| R-P2-5 | **묶음은 임상 스킬·상황 성격으로 한다.** "트리아지"·"통증 사정"·"인계"처럼 학습 축으로. 부서 무관 범용 스킬(SBAR·낙상·감염·환자 교육·가족 소통)은 `track: core` | U3 |
| R-P2-6 | **협업 주제는 내 부서 시점의 타 부서 접점만.** `track: collab`, `dept`=내 부서, 상황 `collabWith`=상대. 어떤 접점을 세울지는 큐레이션 선택 | U3·v41 |

## 정리·보강 규칙

| # | 규칙 | 근거 |
|---|---|---|
| R-P2-7 | **제거는 규칙으로 후보를 뽑고 부서 검수에서 승인한다.** 자동 삭제 금지. "비현실"은 도메인 판단(사용자 승인) | index §0.5 |
| R-P2-8 | **정본 재발급 확정(사용자 결정 2026-09-09).** 정리·보강 후 전체를 정본 재생성하며 시나리오 id를 새로 매긴다. **진도 리셋을 수용**한다(TestFlight 내부 단계). append-우선 제약을 두지 않으므로 Topic은 자유롭게 재배치·제거·추가한다. 재생성 시 audit로 id 매핑 diff를 출력해 영향을 확인한다 | 사용자 결정 · logic §6 |
| R-P2-9 | **중복은 하나만 남긴다.** 제목·persona·difficulty가 동일한 시나리오는 대표 1개만. 생성기 혼합기수 로직이 이미 대부분 제거했으나 잔여를 audit로 점검 | index A3·v2 D7 |

## 검수·게이트 규칙

| # | 규칙 | 근거 |
|---|---|---|
| R-P2-10 | **부서 단위 검수 후 커밋.** vertical slice(ER 먼저)로 파이프라인을 검증하고 팬아웃 | logic §1 |
| R-P2-11 | **완료 정의 = 게이트 그린.** 고아 0(R3) + 주제당 ≥20(R2) + Topic-Theme 정합 + 중복/thin 0(또는 승인 잔여만) | logic §7 |
| R-P2-12 | **레지스트리는 nameKey를 갖는다.** 다국어 후속을 위해 각 주제에 `nameKey`. 실제 번역은 P2 범위 밖 | index 범위 밖 |
| R-P2-13 | **부분 태깅은 안전하다.** 미완 부서는 P1 조립에서 빈 트랙. 라이브 전환은 전체 완료 후에만 | logic §1·§8 |
