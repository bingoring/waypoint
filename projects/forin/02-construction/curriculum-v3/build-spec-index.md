# Build Spec — 커리큘럼 v3 · 주제 기반 심화 커리큘럼 + 여정 지도

> **구현 스펙(Build Spec)** = 코딩 전에 SoT를 라인 단위로 유도해 "다시 유도하지 않고 바로 구현 가능한"
> 수준으로 구체화한 것. (FRAMEWORK "구현 스펙")

## §0. 개요 & 범위

- **목표(한 줄):** 얕은 커리큘럼(부서당 3~6개 · 스텝 2~4개, 전체 상황의 약 10%만 편입)을 **주제 단위
  심화 커리큘럼**(한 주제 = 상황 20~30개 이상, 난이도 계단)으로 바꾸고, 지금 고아 상태인 약 2,700개
  상황을 전부 주제로 편입해, 학습 앱으로서의 깊이와 커버리지를 확보한다.
- **SoT(진실 공급원):** 사용자 구술(2026-09-09) + v41 디자인 핸드오프(`inputs/design-handoff_v41/`
  `07_NOTEBOOK_REDESIGN.md`, `08_JOURNEY_RESOURCES.md`) + 현재 코드. curriculum-v2를 대체한다.
- **깊이 티어 & 사유:** `comprehensive` — 서버 콘텐츠 모델 + 생성/조립 + 계약 + 클라이언트 주 탭이
  동시에 바뀌고, 대규모 콘텐츠 전수조사(태깅·보강·정리)가 포함되며, 기존 사용자의 진도 표시가 달라진다.

### curriculum-v2와의 관계 — 왜 v2가 하드코딩으로 후퇴했고, v3는 D6를 반복하지 않는가

curriculum-v2(2026-08-18)는 "층 = 부서별 3단 테마"를 도입하며 **기계 배정**을 시도했으나, D6("29개 부서 중
14개에서 3단이 깨진다 — `Diff`/`Acuity`/`Role`을 프록시로 **추론**하면 SIM/LOUNGE/SPD는 환자가 없어 밴드가
비고, ER은 긴급 주제가 7개")로 인해 **전량 손저작(89개)으로 후퇴**했다. 규칙은 폴백으로만 남았다(현재
`fallback = []Curriculum{}`, 빈 값 = 모든 부서가 손저작으로 커버됨).

v3는 다시 **조립(assembly)** 방식으로 가지만 D6를 반복하지 않는다. 차이는 다음과 같다.

- v2의 실패 = **추론**. 주제 밴드를 `Diff`/`Acuity`/`Role`이라는 **프록시 필드에서 유추**했고, 프록시가
  부서 성격과 안 맞으면 깨졌다.
- v3의 조립 = **명시 태그 그룹핑**. 각 상황이 `theme`을 **명시적으로 선언**하고(전수조사 P2에서 부여·검수),
  주제는 그 태그로 결정적으로 조립된다. 유추가 없으므로 D6의 실패 모드가 원천적으로 없다.
- 큐레이션의 위치가 바뀐다: "커리큘럼 목록을 Go로 손저작"(89개, 규모 한계) → "상황마다 주제 태그를
  부여·검수 + 주제 레지스트리(약 100개) 큐레이션"(전수조사에 이미 필요한 작업과 동일).

즉 v3는 v2가 옳게 판단한 "추론 배정 금지"를 유지하면서, 큐레이션 대상을 **커리큘럼 나열**에서 **상황 태그 +
주제 레지스트리**로 옮겨 규모 문제를 푼다.

## §0.5 프로그램 분해 — P1 / P2 / P3

이 재설계는 하나의 스펙으로 담기엔 크므로 3개 하위 프로젝트로 나눈다. 각자 독립적으로 동작하는 산출물을 낸다.

| 단계 | 범위 | 이 스펙의 위치 |
|---|---|---|
| **P1** | 주제 분류체계 스키마 + 커리큘럼 데이터 모델 재설계 + 조립·진행 로직 | **이 Build Spec(전체)** |
| **P2** | 전수조사 파이프라인 — 모든 상황에 주제 태그 부여, 갭 주제 보강 생성, 불필요·중복 제거, 과광범위 세분화 | 별도 Build Spec(다음). P1 스키마를 채운다 |
| **P3** | 여정 지도 UI — JourneyMap · StationSheet · LicenseTrack (자유 탐방 제외) | 별도 Build Spec(다음). v41 `08_JOURNEY_RESOURCES.md`가 SoT |

**P1을 먼저 확정해야** P2 전수조사가 "무엇으로 분류할지"의 타깃(태그 스키마 + 주제 레지스트리 형식)을 갖는다.
이 문서는 **P1만** 구현 가능 수준으로 유도한다. P2·P3는 §6 인터페이스로만 규정한다.

### P1 범위 밖 (P2·P3로 미룸)

| 항목 | 왜 지금이 아닌가 |
|---|---|
| 실제 100개 주제 목록의 확정 | P2의 첫 산출물. P1은 레지스트리의 **형식·불변식**만 정의한다 |

## §3. 비기능 요구 (NFR)

- **왕복 수:** 커리어/여정 탭은 `GET /me/curriculum` **1회**로 완성된다(현행 유지). 단 페이로드가 커진다 —
  주제 약 100개 × 상황 20~30개의 **메타**(상황 title·난이도·상태)를 전부 실으면 과대해진다. 따라서
  **주제 목록 + 각 주제의 요약(총/완료 수, 난이도 계단별 카운트)만** 1회 응답에 싣고, **주제 내 상황 목록은
  정거장 시트를 열 때 별도 조회**한다(§6 계약). 목록·요약은 열린 여부와 무관하게 전부 보낸다.
- **결정성:** 같은 입력(themes.yaml + 태그된 시나리오)에 같은 카탈로그가 나와야 한다. 정렬 키에 맵 순회를
  쓰지 않는다(레지스트리의 명시적 순서 필드 사용).
- **기존 사용자 회귀:** 진도는 `scenario_attempts`에서 파생되므로 **마이그레이션 불필요**. 주제 경계가
  바뀌므로 "완료 수" 표시는 달라진다(데이터 손실 아님, 표시 변화). curriculum-v2 R17과 동일한 취급.
- **계약 파괴:** 응답 셰이프가 바뀌므로 **서버 promote + 모바일 OTA 동시 배포**(01-deployment.md 기록).
