지라(Jira)와 컨플루언스(Confluence)는 엔터프라이즈 환경과 고도화된 스타트업에서 '작업의 단위(Ticket)'와 '공식적인 기술 명세(Technical Spec)'를 관리하는 핵심 도구입니다.

노션과 슬랙이 '자유로운 기획과 소통'을 담당한다면, 지라와 컨플루언스는 '명확한 태스크 할당과 검증된 기록'을 담당합니다. 이 네 가지 도구를 모두 통합하면, 개발자가 겪는 파편화된 맥락을 완벽하게 수집하여 코드베이스로 전환할 수 있습니다.

# [제품 요구사항 명세서 (PRD) v0.2] 섀도우 엔지니어 (Shadow Engineer)

> **최종 목표:** Notion/Confluence(기획·명세) + Jira(태스크·제약) + Slack(실시간 합의)의 4각 맥락을 융합하여 IDE 아키텍처를 자동 수립하는 AI 에이전트.

---

## 1. 확장된 통합 아키텍처 (The Quadrant Context)

섀도우 엔지니어는 네 가지 소스의 데이터를 서로 다른 가중치로 병합하여 '최종 실행 가능한 컨텍스트(Actionable Context)'를 도출합니다.

| 도구 | 역할 (Role) | 컨텍스트 성격 | 데이터 가중치 |
| --- | --- | --- | --- |
| **Notion / Confluence** | **Skeleton** | 서비스 전체 구조, 도메인 모델, 비즈니스 목표 | Low (기본값) |
| **Jira** | **Constraint** | 특정 작업 범위(Scope), 마일스톤, 기술적 수치 제약 | Medium |
| **Slack** | **Pivot** | 최신 의사결정 사항, 긴급 수정, 실시간 예외 처리 합의 | High (최신순) |

## 2. 신규 추가 기능 요구사항 (Atlassian Integration)

### [Epic 5] 컨플루언스(Confluence) 기술 명세 엔진

* **FR-5.1 (공식 명세 추출):** 프로젝트 스페이스 내의 공식 기술 설계서(TDD)를 분석합니다. 노션보다 보수적이고 정형화된 데이터를 기반으로 API 스키마 및 보안 규정을 파싱합니다.
* **FR-5.2 (변경 이력 매핑):** 컨플루언스의 문서 버전 관리를 추적하여, 과거의 결정 사항과 현재의 아키텍처 정렬 상태를 대조합니다.

### [Epic 6] 지라(Jira) 태스크 및 제약 사항 파서

* **FR-6.1 (티켓 맥락 파악):** 현재 개발자가 작업 중인 지라 티켓(Issue Key)의 설명을 분석합니다. `[요구사항]`, `[Acceptance Criteria]` 항목에서 기술적인 제약 사항을 추출합니다.
* **FR-6.2 (상태 연동):** 티켓 상태가 `In Progress`로 변경되는 순간, 섀도우 엔지니어가 자동으로 로컬 환경 스캔 및 브랜치 생성을 준비합니다.

## 3. 융합 데이터 흐름 (Advanced Pipeline)

네 가지 툴의 데이터는 아래와 같은 계층 구조로 병합되어 LLM에 전달됩니다.

1. **Layer 1 (Base):** Notion/Confluence에서 **'무엇을(What)'** 만드는지 뼈대를 가져옵니다.
2. **Layer 2 (Scope):** Jira 티켓에서 **'지금(Now)'** 어떤 기능을 구현해야 하는지 구체적인 범위를 좁힙니다.
3. **Layer 3 (Adjustment):** Slack에서 **'어떻게(How)'** 바꿨는지 최신 피드백을 반영해 최종 보정합니다.

## 4. 상세 시스템 기획안 (Technical Specification)

### 4.1 데이터 병합 전략 (Context Merging Strategy)

단순한 텍스트 합치기가 아닌, **상충하는 요구사항 해결(Conflict Resolution)** 로직이 포함됩니다.

> **예시:**
> * **Confluence:** "모든 API 응답은 XML로 처리한다." (2024년 작성)
> * **Jira:** "이번 스프린트 과제: REST API JSON 포맷 전환."
> * **Slack:** "방금 대표님과 회의 끝났는데, 특정 엔드포인트만 일단 JSON으로 가죠."
> * **Shadow Engineer의 판단:** 지라와 슬랙의 맥락을 우선하여, 특정 엔드포인트에 대한 JSON 처리 로직과 DTO를 생성함.
> 
> 

### 4.2 로컬 에이전트의 역할 (Tauri Client)

로컬 에이전트는 클라우드에서 넘어온 설계도(Architecture Plan)를 바탕으로 '실제 파일 시스템 수술'을 집도합니다.

* **AST 스캔:** 기존 코드의 패턴(NestJS의 경우 `@Module`, `@Injectable` 등)을 분석합니다.
* **파일 주입:** 새로운 도메인이 추가될 경우, `src/domains/{domain_name}` 하위에 규격화된 파일셋을 생성합니다.
* **의존성 자동 업데이트:** 새 모듈을 생성하면 상위 모듈의 `imports` 배열에 자동으로 추가합니다.

## 5. 상세 유저 시나리오 (Full-Suite Scenario)

1. **시작:** 유저는 Jira 티켓 `APP-123: 학식 알림 서비스 고도화`를 `In Progress`로 바꿉니다.
2. **맥락 수집:**
* **Confluence**에서 기존 알림 시스템 아키텍처 문서를 읽어옵니다.
* **Notion**에서 새롭게 기획된 UI/UX 변경안을 가져옵니다.
* **Slack**에서 "이번엔 Firebase 대신 자체 알림 서버를 테스트해보자"는 대화 맥락을 포착합니다.


3. **설계 수립:** 에이전트가 "자체 알림 서버용 Redis Queue + NestJS 서비스 레이어"를 설계합니다.
4. **로컬 실행:** 개발자가 IDE를 켜면 Tauri 앱이 팝업됩니다.
* `[Jira APP-123 발견]`
* `[알림 서버 신규 모듈 및 Redis 설정 브랜치 준비 완료]`
* `[Apply 클릭 시 5개 파일 생성 및 2개 파일 수정]`


5. **완료:** 버튼 클릭 한 번으로 모든 인프라 설정과 보일러플레이트 코드가 준비된 상태에서 개발을 시작합니다.
