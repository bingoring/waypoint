### 0. 결정의 전제 — 인원 여유 분석

회전 근무 간호사 10명(수간호사 제외), K-tass 보유자 6명, 기준 OFF를 다 준다고 가정하고 계산했다.

| 달 | 인당 근무일 | 총 근무 vs 최소 필요(6/일) | N 필요 vs 상한(7×인원) | K-tass 필요 vs 보유자 근무 |
|---|---|---|---|---|
| 2026-10 | 20 | 200 vs 186 (여유 **14**) | 62 vs 70 (여유 **8**) | 93 vs 120 (여유 27) |
| 2026-11 | 21 | 210 vs 180 (여유 30) | 60 vs 70 (여유 10) | 90 vs 126 (여유 36) |
| 2026-10, 신규 1명 3인 배정 기간 | 20 | 180 vs 186 (**−6**) | 62 vs 63 (여유 **1**) | 93 vs 120 |

여기서 세 가지를 결론으로 얻는다.
1. **제약 밀도가 높다.** 여유가 14칸인 달에 연차·교육·휴가 몇 건만 들어와도 여유가 한 자릿수로 줄어든다.
2. **"기준 OFF를 다 주는 해"가 존재하지 않는 달이 실제로 생긴다.** 이때 유일한 완충 장치는 누적 OFF다(덜 쉬게 하고
   음수로 이월, 1-1 Q4). 따라서 **기준 OFF는 하드 제약이 아니라 공정성 목표**로 모델링해야 하고, 솔버는 누구에게 오프를
   덜 줄지를 공정하게 정해야 한다(원문 §15 "공평하게 돌아가는 것이 1순위").
3. **나이트 상한 7은 여유가 1~8칸뿐인 하드 제약이다.** 해가 아예 없는 경우 시스템은 "왜 없는지"를 관리자에게 알려야 한다.

→ 생성기는 ① 하드 제약을 **보장**하고, ② 해가 없으면 **불가능을 판정**하며, ③ 공정성 같은 **min-max 목적**을 다뤄야 한다.
이 세 요구가 솔버 선택(§3)을 결정한다.

### 3. 솔버 결정 ⚠️ (가장 번복 비용이 큰 결정)

| 기준 | A. **OR-Tools CP-SAT (Python 서비스)** | B. TS 지역 탐색(시뮬레이티드 어닐링) | C. MIP (HiGHS WASM, Node 안) |
|---|---|---|---|
| 하드 제약 보장 | ✅ 해를 내면 반드시 만족 | ❌ 벌점을 크게 줄 뿐, 보장 없음 | ✅ |
| 불가능 판정 (§0 결론 3) | ✅ `INFEASIBLE` 증명 + 가정(assumption)으로 원인 제약 추출 | ❌ "못 찾음"과 "없음"을 구분 못 함 | △ 판정은 되지만 원인 추출이 어렵다 |
| 금지 패턴·연속 제약 표현 | ✅ 불리언 제약으로 직접 표현 (간호사 근무표는 CP-SAT의 대표 예제) | ✅ 검사기를 그대로 목적 함수로 사용 | △ 선형화 필요 |

| 언어·배포 | ❌ Python 런타임 추가 (컨테이너 1개) | ✅ TS 단일 | ✅ TS 단일 |
| 규칙 이중 구현 | ❌ TS 검사기 + Python 모델 | ✅ 검사기 하나 | ❌ TS 검사기 + MIP 모델 |
| 성숙도 | ✅ 9.15, 활발히 유지 | 자체 구현 | △ `highs` npm 1.15, 커뮤니티 바인딩 |

**권고: A. CP-SAT.** §0의 세 요구(보장·불가능 판정·min-max 공정성)를 모두 충족하는 유일한 선택지다. B는 여유가
충분한 달에는 잘 동작하지만, 여유가 1칸인 달에는 해가 없는지 못 찾은 건지 구분할 수 없어서 관리자가 리롤만 반복하게 된다.

**A의 약점(규칙 이중 구현)은 구조로 막는다.**
1. **TS 검사기가 규칙의 SoT다.** 솔버가 낸 모든 안은 web이 `@duty/domain` 검사기로 **재검사**한 뒤에야 저장한다.
   재검사에서 하드 위반이 나오면 그 안을 버리고 버그로 기록한다(사용자에게는 절대 노출되지 않음).
2. **교차 검증 테스트:** `fixtures/`의 시나리오(종이 10월, 신규 포함 달, 연휴 달 등)를 솔버로 풀고, 결과를 TS 검사기에
   넣어 하드 위반 0을 CI에서 단정한다. 규칙 추가 시 이 테스트가 두 구현의 불일치를 잡는다.
3. 솔버는 **DB에 접근하지 않는 무상태 함수**다(입력 JSON → 출력 JSON). 계약은 `packages/contract`의 zod 스키마가 SoT이고,
   Python 쪽 모델은 생성된 JSON Schema에서 만든다.

**CP-SAT 모델 개요** (Build Spec에서 상세화)
- 변수: `x[n, d, s]` ∈ {0,1}, s ∈ {D, E, N, S, OFF}. 고정 셀(승인 휴가·연차·교육 신청, 수간호사)은 상수로 둔다.
- 하드: 1-2 §7 인원·K-tass·신규 페어, 금지 패턴(전월 말 3일 포함), 16시간 휴식, 월 N ≤ 7, 연속 N ≤ 3, 연속 오프 ≤ 10.
- 소프트(가중 합 최소화): 신청 불충족, N 후 OFF 2개 미충족, N > 6, 주말 통 OFF 미배정(전달 미배정자는 가중치 상향),
  저연차만 구성, 반복 페어, D→E→N 순환 위반, 그리고 **공정성 항 = 누적 OFF 편차의 최댓값**(min-max).
- 슬리핑오프: 부여 가능 수 = floor((잔여 N + 그달 N)/6) — N 수가 변수이므로 모델 안에서 정수 제약으로 계산한다.
- 시간 제한 기본 20초, `num_workers=1`(결정성). 불가능하면 제약 그룹별 assumption 리터럴로 원인 그룹을 돌려준다
  (예: "11/7 N 인원 부족 — 가용 K-tass 보유자 없음").

### 4. 규칙 검사기 공유 방식

- `@duty/domain`은 프레임워크 의존이 없는 순수 TS다. 입력은 `(셀 격자, 사용자 속성, RuleVersion, Holiday, 전월 말 3일, 신청)`,
  출력은 `{ hardViolations[], softWarnings[] }`이다(1-2 §9).
- **브라우저(S9 셀 편집 팝오버)**: 즉시 피드백용으로 같은 코드를 번들에 넣는다.
- **서버(저장·확정)**: 같은 코드로 최종 검증한다. 클라이언트 결과는 믿지 않는다.
- 정산(`settle`)·특휴 산식·셀 출처 결정도 같은 패키지에 둔다. 1-2 §0 종이 검증 데이터와 특휴 구간 경계값이 첫 테스트다.

### 5. 인증·권한

- 로그인: 사번 + 비밀번호. 실패 5회 시 15분 잠금. "이 기기에서 로그인 유지" = 30일 쿠키, 해제 시 브라우저 세션 쿠키.
- 계정 발급: 관리자가 간호사를 추가하면 임시 비밀번호를 한 번만 화면에 보여 준다. 첫 로그인에서 비밀번호 변경을 강제한다.
  분실 시 관리자가 재발급한다(1-1 Q8).
- 권한은 **서버의 한 계층**에서 적용한다: 모든 조회는 `toNurseDTO` / `toAdminDTO` 매퍼를 거치고, 코멘트·휴가 사유는
  관리자 DTO에만 들어간다(1-2 §8). 매퍼별 스냅샷 테스트로 누출을 막는다.
- CSRF: Server Actions의 Origin 검사 + SameSite 쿠키. 비밀번호·세션 토큰은 로그에 남기지 않는다.

### 6. 데이터 소스·파일

- **공휴일:** 2026~2027년 공휴일(대체공휴일 포함)을 **정적 시드**로 넣고 관리자가 편집한다(병원 지정일·개원기념일 추가).
  공공데이터포털 특일 API 연동은 API 키 발급과 외부 통신이 필요해 MVP에서 제외하고, 필요해지면 "가져오기" 버튼으로 추가한다.
- **증빙 파일(S5, 2차 범위):** `FileStore` 포트만 정의하고 구현은 S5 스테이지에서 고른다(로컬 볼륨 또는 S3 호환).
- **시간대:** 모든 날짜는 `Asia/Seoul` 기준 `DATE`로 저장한다. 휴식 시간 계산만 근무 시각표(N은 익일 07:30 종료)로 한다.

### 8. 배포 선택지와 비용 (Q7 — 사람 결정 필요)

아키텍처는 **Docker Compose 한 벌**로 고정하므로, 아래 어느 쪽을 골라도 코드는 바뀌지 않는다. 결정은 3-1에서 해도 되지만,
TLS·백업 준비 방식이 달라서 미리 알면 좋다.

| 선택지 | 월 비용(추정) | 장점 | 단점 |
|---|---|---|---|
| ① 클라우드 VPS 1대 (2 vCPU·2~4GB, 서울 리전) + Caddy 자동 TLS | 약 1~3만 원 | 집·병원 어디서나 접속, 운영 단순 | 병원 개인정보가 외부 서버에 저장됨 → 병원 정책 확인 필요 |
| ② 병원 내부 서버 | 0원 (하드웨어 별도) | 데이터가 병원 밖으로 나가지 않음 | 병원 IT 승인 필요, 집에서 근무 신청 불가(VPN 없으면) |
| ③ 관리형 분산 (Vercel + Neon/Supabase + Cloud Run) | 0원~ (무료 등급) | 서버 관리 불필요 | 공급자 3곳, Vercel Hobby는 상업적 사용 금지, 솔버 콜드 스타트 |

**권고: ①.** 간호사가 집에서 근무를 신청하는 흐름(S4)이 핵심이라 외부 접속이 필요하다. 다만 병원 정책상 외부 저장이 안 되면 ②로 간다.

### 9. 번복 시 영향 범위

| 결정 | 번복하면 바뀌는 것 |
|---|---|
| CP-SAT 솔버 | `services/solver/` 전체, `packages/contract`, compose의 solver 서비스, CI의 Python 잡. **`@duty/domain`과 화면은 영향 없음**(솔버는 계약 뒤의 교체 가능한 부품) |
| Next.js | `apps/web/` 전체. `@duty/domain`·솔버는 영향 없음 |
| Drizzle·Postgres | `apps/web`의 DB 계층·마이그레이션 전체 |
| 자체 세션 인증 | `apps/web`의 인증 미들웨어·세션 테이블 |
| Tailwind | 모든 화면 컴포넌트의 스타일 |

→ 도메인 로직을 `@duty/domain`으로, 솔버를 계약 뒤로 분리했기 때문에 가장 비싼 두 결정(솔버·프레임워크)이 서로의 번복 비용을 키우지 않는다.

### 10. Construction 스테이지 분해 (MVP = 1-1 Q1 범위)

| 스테이지 | 내용 | Build Spec |
|---|---|---|
| 2-1 Foundation | 모노레포·compose·CI, Drizzle 스키마(1-2 전 엔티티)·마이그레이션, 시드(병동·명단 11명·공휴일·RuleVersion v1), 인증·세션·S1 로그인, 공통 셸(사이드바·토큰) | standard |
| 2-2 Domain Core | `@duty/domain`: 규칙 검사기·인원 계산·정산·특휴·셀 출처. TDD, 종이 10월 fixture | comprehensive |
| 2-3 근무표 조회 | S3 격자(1c)·요약 카드·월 이동·인쇄, 역할별 DTO | standard |
| 2-4 관리자 설정 | S10 간호사 관리(추가·임시 비밀번호·잔여치 입력), S11 규칙 설정(버전·이력), 공휴일 관리 | standard |
| 2-5 근무 신청 | S4 격자 신청·팝오버·코멘트 권한·마감 처리 | standard |
| 2-6 솔버·듀티 생성 | `services/solver` CP-SAT, 계약, 교차 검증, S8 생성·리롤·확정·불가능 원인 표시 | comprehensive |
| 2-7 근무 조정·월 마감 | S9 셀 편집·맞바꾸기·즉시 검사·재배포, 협의 기간, 월 마감·정산·마감 취소 | comprehensive |
| 2-8 통합·E2E | 한 달 전체 흐름 Playwright(신청 → 생성 → 조정 → 마감 → 다음 달 이월) | minimal |

- 2차 범위(S2 초기 설정, S5 휴가 신청·승인, S6 동료 현황, S7 규칙 안내)는 MVP 리뷰 후 2-9 이후로 추가한다.
  **S2가 없는 동안 초기 잔여치(연차·잔여 N·이월 오프)는 관리자가 S10에서 입력한다.**
- 순서 근거: 2-2(도메인)가 2-3 이후 모든 화면과 2-6 솔버 교차 검증의 기반이다. 2-4가 2-5보다 먼저인 이유는 신청 마감일·
  간호사 명단이 규칙 설정과 간호사 관리에서 나오기 때문이다.
