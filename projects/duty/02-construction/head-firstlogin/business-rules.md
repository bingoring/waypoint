# Business Rules — 2-11 수간호사 S·칸 출처 표시·최초 로그인

## 1. 수간호사 근무 (S 기본)

| ID | 규칙 | 근거 |
|---|---|---|
| R-HEAD-1 | 수간호사(`rotation = fixed_weekday`) 칸 기본값: 빨간 날 OFF(regular), **그 외 S**. 승인 휴가·특수 신청·본인 신청이 기본값을 이긴다(`headCells` 우선순위 유지) | 사용자 2026-10-09, 원문 응급실 §7 |
| R-HEAD-2 | 수간호사는 근무 신청(S4)에 행이 생기고 **OFF·D만** 고를 수 있다(E·N·복수 선택 없음). 단일 D 신청 → D 고정(`source = requested`), 평일 OFF 신청 → OFF 고정(지금과 같음) | 사용자 "본인이 신청했거나" |
| R-HEAD-3 | 솔버 보충: 신청·고정이 아닌 수간호사의 평일 S 칸은 솔버 입력에 `flex: true`로 넘긴다. 솔버는 그 칸을 S 또는 D로 정하고, D이면 그날 D 인원·K-tass에 센다. D마다 벌점 `headD` = **20000**(`offShortMax` 10000보다 크다) → 필수 조건(인원·K-tass)을 다른 방법으로 채울 수 없을 때만 쓴다 | 사용자 "정말 근무표가 안 나오는 경우만" |
| R-HEAD-4 | 기존 `S-HEAD-FILL`(수간호사 D를 빼고도 인원이 차는지) 벌점은 없앤다. 수간호사 D는 이제 기본이 아니므로 R-HEAD-3 벌점이 같은 역할을 한다. 저연차만 근무(S-JUNIOR-ONLY)의 "수간호사가 있으면 면제"는 그날 수간호사가 D일 때만 | R-HEAD-3 |
| R-HEAD-5 | 솔버가 D로 바꾼 수간호사 칸은 `source = auto`, 툴팁 "인원 부족 보충"(생성 결과 메타 `headFill` 날짜 목록으로 판정). 외곽선 없음 | 신청·조정이 아니므로 |
| R-HEAD-6 | 검사기: 수간호사는 지금처럼 휴식·금지 패턴·연속 근무 검사 대상이 아니다(`checkPerson`은 교대 근무자만). 인원 계산의 수간호사 몫(`fallback`)은 그날 D·E·N인 칸만 센다(S는 세지 않음) | 원문 §4 "교대근무자" |
| R-HEAD-7 | 관리자 근무 조정(S9)의 수간호사 행은 지금처럼 편집할 수 있다. 칩은 D·S·OFF만 보인다 | 사용자 "조정된 경우" |
| R-HEAD-8 | 이미 확정·마감된 달(가져온 이력 포함)은 바꾸지 않는다. 새로 생성하는 달부터 적용 | 기록 보존 |

## 2. 교환에 수간호사 (S9 간호사, 2-8 확장)

| ID | 규칙 | 근거 |
|---|---|---|
| R-SWAPH-1 | 간호사 교환 화면(3a)에 수간호사 행을 보이고 선택할 수 있다(R-SWAP-2 "교대 근무자끼리만" 완화). 요청은 여전히 간호사만 만든다 | 사용자 2026-10-09 |
| R-SWAPH-2 | 수간호사 칸은 **S ↔ D만** 바꿀 수 있다. 수간호사의 OFF·휴가 칸은 교환할 수 없다 | 수간호사는 E·N을 하지 않는다 |
| R-SWAPH-3 | 그날 개수 유지(R-SWAP-5) 판정에서 수간호사의 S는 OFF와 같게 센다. 예: 간호사 D → OFF + 수간호사 S → D(인정), 간호사 OFF → D + 수간호사 D → S(인정) | 교대 인원 수가 유지된다 |
| R-SWAPH-4 | 수간호사(관리자)는 근무 조정(관리자) 화면 상단 "받은 교환 요청"에서 수락·거절한다. 전원 수락 → 재검사 뒤 반영(R-SWAP-8 그대로), 칸 `source = swap` | 2-8 흐름 재사용 |

## 3. 칸 외곽선 (R-VIEW-6 변경)

| ID | 규칙 | 근거 |
|---|---|---|
| R-MARK-1 | 우선순위 관리자 수정 > 교환 > 신청. 관리자 수정(`admin`) = 파란 inset 2px 실선, 교환(`swap`) = **빨간 1.5px 점선**, 신청 반영(`requested`) = 빨간 inset 1.5px 실선 | 사용자 "파랑은 관리자 개입만" |
| R-MARK-2 | 휴가 칸(AL·LEAVE)과 교육·특휴 등 특수 신청 OFF도 신청으로 생긴 칸이므로 빨간 실선을 그린다(기존 "휴가 칸 외곽선 없음" 폐지). 휴가 승인·취소로 바뀐 칸(편집 사유 `leave_*`)은 관리자 수정이 아니라 신청으로 본다 | 사용자 "어쨌든 구분" |
| R-MARK-3 | 근무표 범례: "신청(빨간 실선) · 교환(빨간 점선) · 관리자 수정(파란 실선)". 규칙 안내(S7)의 마지막 항목 문구도 같게 | 핸드오프 S3 범례 확장 |
| R-MARK-4 | 같은 표시를 근무표(S3)·관리자 근무 조정(S9)·간호사 교환 화면(3a)·인쇄에 쓴다. 생성안 미리보기는 지금처럼 신청 반영만 | 일관성 |

## 4. 칸 툴팁

| ID | 규칙 | 근거 |
|---|---|---|
| R-TIP-1 | 칸에 마우스를 올리거나(150ms) 키보드 포커스·터치 길게 누르기로 툴팁 카드를 띄운다. 첫 줄은 지금 `title`과 같은 "10/13 (화) · off · 슬리핑오프" | 사용자 요청 4 |
| R-TIP-2 | 출처 줄: 신청 반영 → "신청 반영 · 신청: OFF/D", 교환 → "교환 반영 · {상대 이름} · {수락일}", 관리자 수정 → "관리자 수정 · {수정자} · {M/D HH:mm} · 이전 {코드}", 휴가 → "{종류} 신청 · {기간}", 솔버 보충 → "인원 부족 보충" | 사용자 "조정인지 신청인지 등 특이사항" |
| R-TIP-3 | 본인 칸과 관리자에게만 추가로: 신청 코멘트, 관리자 수정 메모(예외 적용 사유), 경조·공가 사유. 다른 간호사에게는 종류까지만(R-1 ①) | DECISIONS 2026-10-08 |
| R-TIP-4 | 툴팁 데이터는 근무표 조회 때 함께 읽는다(칸별 최신 편집 기록 1건, 교환 요청, 신청). 칸마다 따로 요청하지 않는다 | 성능 |

## 5. 개인정보 동의

| ID | 규칙 | 근거 |
|---|---|---|
| R-CONSENT-1 | 로그인 성공 뒤, **현재 동의서 버전**(`PRIVACY_NOTICE_VERSION`)에 동의한 기록이 없으면 `/consent`로 보낸다. 동의 전에는 다른 모든 화면·서버 액션을 막는다(로그아웃·동의 처리만 허용) | 사용자 요청 6 |
| R-CONSENT-2 | 동의는 체크박스 2개: ① 개인정보 수집·이용(필수 항목) ② 민감정보(노조 가입 여부·병가 사유) 처리. 둘 다 체크해야 "동의하고 계속". 각 항목 옆에 전문 펼치기 | 개인정보 보호법 제22조·제23조(민감정보 별도 동의) |
| R-CONSENT-3 | "동의하지 않음" → 로그아웃하고 로그인 화면에 "동의하지 않으면 근무표를 사용할 수 없습니다. 관리자에게 문의하세요." | 사용자 "동의한 유저만 메인으로" |
| R-CONSENT-4 | 기록: `privacy_consents`(사용자, 버전, 필수 동의 시각, 민감정보 동의 시각, 접속 IP). 지우지 않고 쌓는다. 버전이 바뀌면 다음 로그인 때 다시 동의 | 동의 입증 책임 |
| R-CONSENT-5 | 동의서 문안은 초안이다(§7). 고지 항목: 목적, 수집 항목, 보유·이용 기간, 거부 권리와 불이익, 처리 위탁(Google Cloud 서울 리전 서버·백업), 문의처. 운영 전에 병원 개인정보 담당 검토 | 사용자 답변, 제15조 ② |
| R-CONSENT-6 | 로그인 화면과 설정 화면에 "개인정보 처리 안내" 링크(`/privacy`, 로그인 없이 열람) | 고지 상시 열람 |

## 6. 최초 로그인 초기 설정 (S2 부활)

| ID | 규칙 | 근거 |
|---|---|---|
| R-ONB-1 | 흐름: 로그인 → 동의(R-CONSENT-1) → 비밀번호 변경(`mustChangePassword`) → 초기 설정(`users.onboardedYear`가 null) → 근무표. 초기 설정 전에는 다른 화면을 막는다(가드는 동의와 같은 방식) | 핸드오프 S1 동작, 사용자 요청 5 |
| R-ONB-2 | 항목(교대 근무자): 입사일, K-tass 여부, 연차 구분(고·중·저), 근무 방식(교대 / 야간 전담 + 기간), 노조 가입, 올해 연차 수, 잔여 N, 이월 오프(음수 허용), 신규 여부 → 신규면 프리셉터(교대 근무자 중 선택)·구분(완전 신규 / 경력자)·트레이닝 시작일·종료일·3인 근무 종료일 | 사용자 요청 5, 원문 §10·11·응급실 §6 |
| R-ONB-3 | 수간호사는 입사일·K-tass·노조·올해 연차 수만(교대 관련 항목 없음) | 수간호사는 교대 근무자가 아니다 |
| R-ONB-4 | 값은 지금 DB 값으로 **미리 채운다**(잔여치는 원장 투영 `requests/balance.ts` 기준). 본인은 확인만 하거나 고친 뒤 "저장하고 근무표 보기". "나중에"는 없다 | 사용자 답변 "미리 채우고 본인이 확인·수정" |
| R-ONB-5 | 검증: 날짜 형식, 트레이닝 시작 ≤ 3인 종료 ≤ 종료, 프리셉터 ≠ 본인, 연차 0~30, 잔여 N 0~99, 이월 오프 −60~60(0.5 단위). 빈 값 저장 불가 | 핸드오프 S2 검증 |
| R-ONB-6 | 저장: 인적 항목은 `users`를 바꾸고, 잔여치는 차이만큼 원장에 `self_input` 항목(메모 "본인 초기 설정")을 쌓고, 신규 트레이닝은 `trainings`에 만들거나 고친다(작성자 본인). 바꾼 항목이 하나라도 있으면 `onboarding_submissions`(이전·이후 값, 제출 시각)를 남긴다. `onboardedYear` = 올해 | 원장 append-only 유지 |
| R-ONB-7 | 관리자 간호사 관리(S10)에 미확인 제출이 있는 사람마다 "본인 입력 확인 필요" 배지와 바뀐 항목(이전 → 이후)을 보인다. 관리자는 "확인"(그대로 둠) 또는 "되돌리기"(이전 값으로 복원 = 반대 원장 항목, 메모 필수)를 한다. 그 뒤에도 기존 편집으로 언제든 고친다 | 사용자 "관리자가 수정" |
| R-ONB-8 | 본인 입력이 이미 확정된 달의 생성·정산 결과를 바꾸지는 않는다. 잔여치는 다음 생성부터 반영된다 | 확정 기록 보존 |
| R-ONB-9 | 해마다: 올해 첫 로그인에 `onboardedYear < 올해`이면 **올해 연차 수만** 묻는 짧은 화면(같은 저장 규칙). 다른 항목은 다시 묻지 않는다 | 핸드오프 S2 "연차는 매년 1/1 재요청", 원문 §11 |
| R-ONB-10 | 관리자가 새로 추가한 간호사·명단·이력 가져오기로 들어온 사용자는 `onboardedYear` null, 동의 없음으로 시작한다. 개발 시드·E2E 시드 사용자는 동의·초기 설정을 마친 상태로 만든다(첫 로그인 E2E 전용 사용자 1명 제외) | 운영·테스트 |

## 7. 동의서 초안 (병원 검토용)

> 이 문안은 개발자가 쓴 초안이다. 법률 자문이 아니다. 근무 편성은 근로계약 이행에 필요한 처리(제15조 ① 4호)로 동의 없이 가능할 수 있으므로, 병원이 동의 방식 자체를 유지할지도 검토한다.

**개인정보 수집·이용 동의 (필수)**
- 목적: 응급실 근무표 작성·조정, 오프·나이트·휴가 잔여 관리, 근무 교환·신청 처리, 본인 확인(로그인)
- 항목: 사번, 이름, 입사일, 연차 구분, K-tass 자격, 근무 방식(교대·야간 전담 기간), 근무 기록, 근무·휴가 신청과 사유, 오프·나이트·연차 잔여, 트레이닝(프리셉터·기간), 접속 기록(로그인 시각·IP)
- 보유·이용 기간: 재직 기간 동안, 퇴직 후 3년(근로기준법 제42조 근로자 명부·계약 서류 보존 기간) 뒤 파기. 백업 사본은 최대 90일 뒤 삭제
- 처리 위탁: Google Cloud(서울 리전) — 서버 운영과 암호화 백업 보관
- 거부 권리: 동의를 거부할 수 있다. 다만 이 서비스는 근무표 작성에 위 정보가 필요하므로, 거부하면 서비스를 사용할 수 없고 종이 근무표로 처리한다

**민감정보 처리 동의 (별도)**
- 항목: 노동조합 가입 여부(노조교육 OFF 배정), 병가 사유(건강 정보)
- 목적·기간·거부 권리: 위와 같음. 병가 사유는 본인과 관리자만 열람
