# Build Spec — 2-9 통합·E2E

## §0. 개요 & 범위
- **목표(한 줄):** 11월 한 달 운영 흐름을 "오늘"을 옮기며 끝까지 따라가는 연속 E2E 1개 + 화면 × 역할 커버리지 점검과 보강.
- **SoT:** 1-3 §10 「신청 → 생성 → 조정 → 마감 → 다음 달 이월」 + 2-5 휴가·2-8 교환(Q2). 각 단계의 기대값은 해당 스테이지 Build Spec을 따른다(재정의하지 않는다).
- **규모/제약:** E2E는 `workers: 1`, 오늘 기본값 2026-10-13(`DUTY_FAKE_TODAY`). 개발 시드: 10월 확정(종이 근무표), 11월 신청 중(마감 10/15), 9월 끝난 달. 기본 규칙: 신청 마감 15일, 협의 기간 16~20일.
- **깊이 티어 & 사유:** `minimal` — 새 도메인·화면이 없고 테스트와 시계 주입만 더한다(1-3 §10).

### §1.2 커버리지 표

화면(S1·S3·S4·S5 팝오버·S8·S9 관리자·S9 간호사·S10·S11·내 설정) × 역할(간호사·관리자) × 주요 경로를 표로 만들고, 각 칸에 덮는 스펙·테스트를 적는다.
빈 칸 중 핵심 경로만 메운다. 지금 알려진 후보: 교환 요청 거절·철회, 겹치는 교환 경고, 관리자 편집으로 걸린 교환 무효(통합 테스트만 있음).
2차 범위 화면(S2·S6·S7, 현재 자리 표시)은 표에 "2차"로만 적는다.

## §7. 편차 로그 (Deviations) — 구현 후

| SoT | 실제 구현 | 사유 |
|---|---|---|
| §1 `requestToday()`가 `appToday()`를 감싼다 | 쿠키 값은 `appToday(env, now, override)`의 세 번째 인자로 넘기고, 운영 차단은 한곳(`appToday`)에 둔다 | 운영 무시 규칙을 단위 테스트 하나로 고정 |
| §1 `cycle`은 `chromium` 뒤에 돈다 | `cycle-reset`(DB를 시드 상태로) → `cycle` | 2-6 E2E가 11월보다 먼저 12월을 확정해 둔 상태에서는 11월 말이 실제로 풀 수 없을 때가 있었다(앱은 원인을 맞게 보여 줌). 흐름 E2E가 다른 스펙이 남긴 상태에 기대지 않게 |
| §1.1 9단계 | 11/16 「12월 생성·확정」 추가, 12/1에 10월을 먼저 마감 | 12월 이월은 12월 근무표가 있어야 보인다. 마감은 앞 달부터(2-7 규칙) |
| §1.1 "DB 직접 쓰기 없음" | 그대로. 단 교환·관리자 편집 대상은 생성 결과에 따라 달라서, 규칙을 통과하는 칸을 도메인 검사기로 **읽어서** 고른다(`e2e/search.ts`) | 생성안은 시드가 무작위 |
| §1.1 관리자 편집 대상 | 교환 당사자는 뺀다 | 같은 칸을 교환 뒤 되돌리면(X→Y→X) 안내에 바뀐 것이 없어 띠가 뜨지 않는다(앱 동작은 맞음, 테스트가 3회 중 1회 실패) |
| §1.2 겹치는 교환 경고·관리자 편집으로 교환 무효 | E2E는 두지 않고 통합 테스트(`swaps/service.int.test.ts`)로 둔다 | 화면은 거절·철회와 같은 상태 표시 경로. 서버 규칙은 통합에서 시나리오별로 확인 |
| (보강) 교환 거절·철회 E2E | 오늘을 쿠키로 9/17(10월 협의 기간)에 두고 확인 | 기존 교환 E2E처럼 DB의 협의 기간을 바꾸지 않아도 된다 |
