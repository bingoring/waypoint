# Tokens Are Running Out: Claude Code 한도 소진 진단 앱 설계

- 작성일: 2026-11-17
- 상태: 브레인스토밍 산출물. Inception 스테이지(1-1~1-3)의 입력 문서이며, 승인은 각 스테이지의 검토 게이트에서 받습니다. 이후 결정은 스테이지 문서의 `승인 결과`와 [DECISIONS.md](../DECISIONS.md)가 이 문서보다 우선합니다.
- 공개 저장소이므로, 개발자 기기의 세션 제목 같은 실제 업무 정보는 가상의 예시로 바꿨습니다. 수치는 집계값만 남겼습니다.
- 앱 이름: **Tokens Are Running Out**. 한 줄 소개는 "Where did my tokens go?"(영어)와 "내 토큰 어디 갔어?"(한국어)입니다. 이름만 보면 남은 양을 보여주는 게이지처럼 읽힐 수 있으므로, 소개 문구와 README 첫 줄에서 "왜 닳았는지 알려 준다"는 점을 분명히 합니다.

## 1. 의도와 배경

### 목표
많은 사람이 불평하지만 이를 해결하는 도구는 적은 문제를 골라, 오픈소스 macOS 메뉴 막대 앱으로 해결합니다.

### 문제
Claude Code 구독자(Pro/Max)는 한도가 왜 빨리 닳았는지 알 수 없습니다.

- **불만의 규모:** 공식 이슈 트래커에서 반응이 가장 많은 이슈 500개 중, 한도 소진에 대한 불만 이슈가 16개입니다. 👍는 합계 2,746개, 댓글은 3,490개이고, 16개 중 12개가 아직 열려 있습니다. 대표 이슈는 #16157(👍697, 댓글 1,499)과 #38335(👍477)입니다.
- **불만의 내용:** "같은 작업을 했는데 한도가 1~2시간 만에 끝났다"는 것입니다. 사용자는 원인이 자기 사용 습관인지 Anthropic 쪽 변경인지 구분하지 못합니다. 일부 사용자는 캐시 유지 시간 변화(#46829)나 버전별 토큰 증가(#46917)를 손으로 직접 분석해서 이슈로 올리고 있습니다.

### 기존 도구와의 빈틈
- **"얼마나"를 보여주는 도구는 포화 상태입니다.** claude-hud(★29.2k), CodexBar(★23.2k), ccusage(★19.5k) 등이 있습니다.
- **"왜"를 진단하는 도구는 승자가 없습니다.** 같은 문제를 노린 도구가 최근 몇 달 사이에 10개 가까이 생겼지만, 가장 큰 것이 ★27입니다(2026-11-17 GitHub 검색 기준).
- **큰 도구들도 원인을 다루지 않습니다.** ccusage, claude-hud, CodexBar, Claude-Code-Usage-Monitor의 README를 확인했습니다. ccusage는 캐시 쓰기와 읽기 토큰을 따로 세어 줄 뿐이고, 재구축의 원인이나 캐시 만료를 다루는 도구는 없었습니다. 다만 README 기준의 확인입니다.
- **이 빈틈은 가설입니다.** 작은 도구가 여럿 생겼는데 모두 자리를 잡지 못했다는 사실은, 아직 승자가 없다는 뜻일 수도 있고, 이런 방식의 진단에 대한 수요가 약하다는 뜻일 수도 있습니다. 첫 공개 뒤의 반응으로 검증합니다(13장).

### 로컬 검증
개발자의 Mac에 있는 7일치 기록(2026-11-10T00:00Z부터 2026-11-17T00:00Z까지, API 호출 4,133건)을 프로토타입 스크립트 메인 저장소의 `prototype/drain.py`로 분석했습니다.

- **재구축의 비중:** 캐시를 처음부터 다시 만든 호출이 80건이었고, 이 호출들이 전체 캐시 쓰기 토큰의 65.8%를 차지했습니다.
- **원인 분류:** 메인 세션의 재구축 62건은 6.3의 규칙으로 모두 설명되었습니다.
  - 1시간 넘게 쉰 뒤 캐시가 만료된 경우: 50건
  - 압축 직후: 9건
  - 모델 변경: 3건
  - 원인 불명: 0건
  - 나머지 18건은 서브에이전트 기록에서 나왔습니다.
- **만료 재구축의 비용:** 만료로 생긴 재구축 50건(약 1,806만 토큰)의 캐시 쓰기 비용이 API 정가 환산 비용의 17.0%를 차지했습니다. 쉰 시간으로 나누면 다음과 같습니다.
  - 짧은 휴식(1~3시간) 뒤: 16건, 비용의 5.8%. 만료 전에 이어 갔다면 피할 수 있었던 양은 5.5%입니다.
  - 긴 휴식(3시간 초과) 뒤: 34건, 비용의 11.2%. 대부분 밤새 쉰 경우라서, 더 일찍 돌아오는 방법으로는 피할 수 없습니다.
- **사례:** 62분 쉰 뒤 72만 토큰을 다시 쓴 경우와, 하루 쉰 뒤 82만 토큰을 다시 쓴 경우가 있었습니다.

### 성공의 모습 (제안)
- 사용자가 "점심 먹고 돌아와서 큰 세션을 이어 간 게 원인이었구나" 같은 사실을 1분 안에 알아냅니다.
- 그다음 사용자가 행동을 바꿀 수 있습니다.
  - 짧은 휴식: 만료 경고를 보고, 이어 갈 세션은 만료 전에 이어 갑니다.
  - 긴 휴식: 쉬기 전의 컨텍스트 크기를 보고, 오래 비울 세션은 정리하거나 새 세션으로 시작할지 판단합니다. 정리하면 실제로 얼마나 줄어드는지는 v1에서 측정하지 않습니다.
- 외부 지표는 GitHub 별 수와 GitHub Releases 다운로드 수로 봅니다. 자체 Homebrew tap의 설치 수는 공개 통계로 확인하기 어렵기 때문입니다.

## 2. 목표, 비목표, 반목표

### v1 목표
- **G1 원인 분해:** 기간(최근 5시간, 오늘, 최근 7일)마다 사용량을 원인별로 나눕니다. 수치는 API 정가 환산으로 보여줍니다.
- **G2 만료 경고:** 쉬고 있는 세션마다 캐시가 만료되기까지 남은 시간과, 만료되면 다시 써야 할 토큰 양을 보여줍니다. 원하는 사용자에게는 만료 직전에 macOS 알림을 보냅니다.
- **G3 비싼 순간 목록:** 재구축이 일어난 순간을 시각, 세션 제목, 원인, 비용과 함께 나열합니다.
- **G4 세션 범위:** Claude 데스크톱 앱(Code 탭)의 세션과 터미널 CLI의 세션을 모두 다룹니다. 두 세션 모두 같은 위치에 기록을 남깁니다.

### 비목표 (v1에서 하지 않음)
- 공식 한도 %를 보여주는 기능.
- 버그 증거 내보내기. 원인 불명인 재구축을 버전별·날짜별로 정리해 이슈에 첨부하게 해 주는 기능은 v2 후보입니다.
- Codex, Cursor 같은 다른 도구 지원.
- Windows와 Linux 지원.
- 공개 CLI. 개발용 CLI는 만들지만 사용자용으로 문서화하지 않습니다.
- 세션을 클릭해서 해당 세션으로 이동하는 기능. 딥 링크 형식을 확인하지 못했습니다.
- 세션 진행 상황 모니터와 복귀 요약. 데스크톱 앱에서 이미 볼 수 있어서 제외했습니다.

### 반목표 (이렇게 되면 기술적으로 동작하더라도 실패)
- 로그인 토큰, 키체인, 쿠키를 읽는 것.
- 사용자의 한도를 소비하는 동작. 예를 들어 캐시를 살려 두려고 자동으로 메시지를 보내는 기능이 여기에 해당합니다.
- 네트워크로 데이터를 보내는 것. 텔레메트리도 포함합니다.
- `~/.claude` 아래의 파일을 수정하는 것. 앱은 읽기만 합니다.
- 근거 없이 "낭비"라고 단정하는 것. 추정치는 추정이라고 표시하고, 각 재구축을 어떤 규칙으로 분류했는지 화면에서 확인할 수 있어야 합니다.

## 3. 제약

- **플랫폼:**
  - macOS 14 이상을 대상으로 하고, Swift 6과 SwiftUI의 `MenuBarExtra`를 씁니다.
  - 개발 환경에는 Xcode 26.4와 Swift 6.3이 설치되어 있습니다.
- **샌드박스를 쓸 수 없습니다.** `~/.claude`를 읽어야 하기 때문입니다. 따라서 Mac App Store가 아니라 GitHub Releases와 Homebrew cask로 배포합니다.
- **기록 형식은 문서화되지 않은 내부 형식입니다.** Claude Code가 업데이트되면 바뀔 수 있습니다. 그래서 모르는 필드와 모르는 항목 유형은 무시하고, 읽지 못한 줄은 건너뛰되 그 비율을 기록합니다.
- **데이터 규모:**
  - 개발자의 Mac 기준으로 `~/.claude/projects`가 1.7GB이고, 세션 기록 하나가 228MB에 이르기도 합니다.
  - 그래서 처음 한 번만 색인을 만들고, 그 뒤로는 파일에 새로 추가된 부분만 읽습니다.
- **공식 한도 %는 로컬에 저장되지 않습니다.** 그래서 토큰과 API 정가 환산 비용으로 진단합니다.
- **오픈소스로 공개합니다.** 라이선스는 MIT를 제안합니다.

## 4. 접근 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. Swift 네이티브 (선택)** | SwiftUI 메뉴 막대 앱. 분석 코어는 별도 Swift 패키지로 분리 | 작고 빠름. 실행에 추가 설치물이 필요 없음. Homebrew 배포와 잘 맞음. 코어를 재사용해 나중에 CLI로 확장 가능 | macOS 전용 |
| B. Rust 코어 + Swift UI | 분석은 Rust CLI, 화면은 Swift | Linux나 터미널 사용자층까지 노릴 수 있음 | 언어가 두 개라서 빌드와 배포가 복잡하고, 첫 출시가 늦어짐 |
| C. Tauri나 Electron | 웹 기술로 만든 데스크톱 앱 | 여러 OS 지원, 차트를 만들기 쉬움 | 무거움(Electron 기반 메뉴 막대 앱은 100MB를 넘기도 함). 가볍고 믿을 수 있다는 차별점과 맞지 않음 |

- **제외한 방식:** Claude Code 화면 안에 UI를 그리는 플러그인(Mods)도 검토했지만 제외했습니다. 세션 안에서는 그 세션만 보이므로, 여러 세션에 걸친 분석이나 쉬고 있는 세션에 대한 경고에 맞지 않습니다.
- **선택:** 사용자가 A를 골랐습니다. 이 앱의 차별점은 가볍고 믿을 수 있는 진단 도구라는 데 있고, 빨리 내놓아서 자리를 잡는 것이 중요하기 때문입니다.

## 5. 데이터 출처

아래 내용은 2026-11-17에 개발자의 Mac(Claude Code 2.1.293~2.1.325)에서 직접 확인했습니다.

| 항목 | 위치와 형식 | 비고 |
|---|---|---|
| 세션 기록 | `~/.claude/projects/<cwd를 인코딩한 이름>/<sessionId>.jsonl` | 한 줄이 JSON 객체 하나 |
| 서브에이전트 기록 | `~/.claude/projects/<...>/<sessionId>/subagents/agent-<id>.jsonl`, 같은 이름의 `.meta.json` | meta에 `agentType`, `description`이 있음 |
| 사용량 | `type == "assistant"`인 줄의 `message.usage` | `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `cache_creation.ephemeral_1h_input_tokens`, `cache_creation.ephemeral_5m_input_tokens` |
| 모델, 시각, 버전 | `message.model`, `timestamp`, `version`, `sessionId` | model이 `<synthetic>`인 줄은 무시 |
| 중복 | 같은 `message.id`가 여러 줄에 기록됨(콘텐츠 블록마다 한 줄) | 표본 2,731줄에 고유 id는 1,227개였음. 중복 922건 모두 usage 값이 같았으므로, `message.id`로 중복을 제거 |
| 메아리 항목 | `api-request-blob` 같은 다른 type의 줄에도 이전 tool_use 내용이 다시 들어 있음 | `type == "assistant"` 외의 줄은 사용량 계산에서 제외 |
| 압축 | `type == "system"`이고 `subtype == "compact_boundary"`인 줄, 또는 `isCompactSummary`가 있는 줄 | |
| 세션 제목 | 기록의 `custom-title` 항목(`customTitle`). 데스크톱 세션은 `~/Library/Application Support/Claude/claude-code-sessions/**/local_*.json`의 `title`도 있음(`cliSessionId`로 연결) | 제목이 없으면 폴더 이름을 씀 |
| 실행 중인 세션과 상태 | `~/.claude/sessions/<pid>.json`(비공식): `pid`, `sessionId`, `name`, `status`(busy/idle), `entrypoint`. 공식 CLI `claude agents --json`도 같은 정보를 줌. 두 곳 모두 데스크톱 앱 세션을 포함함(확인함) | 앱은 이 파일을 읽고, `kill(pid, 0)`으로 프로세스가 살아 있는지 확인함. CLI는 실행 중에 호출하지 않음(6.5 참고) |

- **캐시 유지 시간(TTL) 정보:** 한 호출 안에 1시간 캐시와 5분 캐시가 함께 쓰인 경우는 없었습니다(검증 기간의 호출 4,133건 중 0건). 메인 세션은 모두 1시간 캐시를 썼고, 서브에이전트는 모두 5분 캐시를 썼습니다.
- **TTL 갱신 규칙:** Anthropic API의 캐시는 사용될 때마다 유지 시간이 다시 시작됩니다. 따라서 만료 시각은 "그 세션의 마지막 API 호출 시각 + 그 호출에 적용된 TTL"로 계산합니다.
- **공식 hooks로는 대체할 수 없습니다.** hooks의 입력에는 토큰 사용량이 없으므로, 사용량은 기록 파일에서만 얻을 수 있습니다.

## 6. 핵심 계산

### 6.1 API 정가 환산
- **기준:** 모델별 기본 입력 단가를 기준으로 삼고, 아래 배수를 적용합니다.
  - 출력: 모델별 가격표를 따릅니다.
  - 캐시 읽기: ×0.1
  - 5분 캐시 쓰기: ×1.25
  - 1시간 캐시 쓰기: ×2
- **가격표:** 앱에 JSON 파일로 포함합니다. 빌더는 구현 시점의 공식 가격 페이지로 단가와 배수를 확인해야 합니다.
- **표시 문구:** 화면에는 항상 "API 정가 환산"이라고 표시합니다. 구독 요금제에서 실제로 청구되는 금액이 아니기 때문입니다.

### 6.2 재구축 판정
한 API 호출이 아래 두 조건을 모두 만족하면 "재구축"으로 판정합니다.
- `cache_creation_input_tokens`가 임계값(기본 50,000) 이상이다.
- `cache_creation_input_tokens`가 `cache_read_input_tokens`보다 크다. 즉, 프롬프트의 대부분을 캐시에서 읽지 못했다는 뜻입니다.

### 6.3 재구축 원인 분류
위에서부터 차례로 검사하고, 처음 맞는 원인으로 분류합니다.

| 원인 | 판정 규칙 | 줄일 수 있는가 |
|---|---|---|
| 세션 시작 | 해당 세션(또는 서브에이전트)의 첫 호출 | 아니요 (정상) |
| 압축 직후 | 압축 경계 이후 첫 호출 | 아니요 (불가피) |
| 모델 변경 | 직전 호출과 `message.model`이 다름 | 사용자가 선택한 결과로 별도 표시 |
| 짧은 휴식 후 만료 | 같은 세션의 직전 호출로부터 경과한 시간이 직전 호출의 TTL보다 길고, 3시간 이하 | **예**. 만료 전에 이어 갔다면 피할 수 있었음 |
| 긴 휴식 후 만료 | 경과한 시간이 3시간보다 김 | 시간 조절로는 피하기 어려움. "줄일 수 있었던 양"에 넣지 않음 |
| 업데이트 직후 | 직전 호출과 `version`이 다름 | 별도 표시 |
| 원인 불명 | 위 어느 것에도 해당하지 않음 | 서버 쪽 원인일 수 있음. v2 증거 정리의 재료 |

- **직전 호출의 TTL 판단:** 한 호출에는 TTL이 하나만 쓰입니다(5장 참고). 그래서 직전 호출의 `cache_creation` 세부 필드 중 0이 아닌 쪽으로 판단합니다. 두 값이 모두 0이면 같은 기록 파일에서 가장 최근에 확인된 TTL을 씁니다. 그것도 없으면 메인 세션은 1시간, 서브에이전트는 5분으로 봅니다.
- **"세션 시작"의 정의:** 같은 기록 파일 안에 앞선 assistant 호출이 없는 첫 호출만 세션 시작으로 봅니다.
  - 데스크톱 앱은 쉬고 있던 세션을 다시 열 때 같은 파일에 이어서 기록합니다(확인함). 그래서 점심 뒤에 큰 세션을 이어 가는 경우는 세션 시작이 아니라 "짧은 휴식 후 만료"나 "긴 휴식 후 만료"로 분류됩니다.
  - 터미널의 `--resume`이 새 파일을 만드는지는 확인하지 못했습니다. 새 파일에 이전 대화가 복사된다면, 복사된 호출의 시각으로 경과 시간을 계산하면 됩니다. 이 동작은 빌더가 구현 초기에 확인합니다.
- **`<synthetic>` 메시지:** model이 `<synthetic>`인 메시지는 실제 API 호출이 아니므로, 직전 호출을 찾을 때도 건너뜁니다.
- **짧은 휴식과 긴 휴식의 경계:** 기본값은 3시간이고 설정에서 바꿀 수 있습니다.
- **임계값과 규칙의 세부 조정:** 실제 기록으로 보정하는 일은 빌더에게 맡깁니다.

### 6.4 원인별 분해
- **분해 항목:** 기간마다 정가 환산 비용을 다음 항목으로 나눕니다.
  - 일반 작업
  - 짧은 휴식 후 캐시 재구축
  - 긴 휴식 후 캐시 재구축
  - 세션 시작과 압축
  - 서브에이전트
  - 모델 변경과 업데이트
  - 원인 불명
- **재구축 호출의 비용 배분:** 재구축 호출의 캐시 쓰기 비용만 그 원인 항목에 넣습니다. 같은 호출의 출력, 캐시 읽기, 캐시되지 않은 입력 비용은 "일반 작업"에 넣습니다.
- **서브에이전트:** 서브에이전트 기록에서 나온 사용량은 원인과 관계없이 모두 "서브에이전트" 항목에 넣습니다.
- **"줄일 수 있었던 양"의 정의:** 짧은 휴식 후 캐시 재구축의 캐시 쓰기 비용에서, 같은 토큰을 캐시 읽기로 처리했다면 들었을 비용을 뺀 값입니다. 긴 휴식 후 재구축은 넣지 않습니다.
- **메뉴 막대의 숫자:** 오늘의 전체 비용 중 "쉬었다 돌아온 캐시 재구축"(짧은 휴식과 긴 휴식을 합친 것)의 캐시 쓰기 비용이 차지한 비율입니다. 피할 수 있었다는 판단이 아니라 사실이므로, 반목표 5번과 충돌하지 않습니다. 검증 기간의 값은 17.0%(짧은 휴식 5.8%, 긴 휴식 11.2%)였고, 줄일 수 있었던 양은 5.5%였습니다.

### 6.5 만료 경고
- **실행 상태를 읽는 방법:**
  - `~/.claude/sessions/<pid>.json`을 FSEvents로 감시하고, `kill(pid, 0)`으로 프로세스가 살아 있는지 확인합니다.
  - `claude agents --json`은 앱 실행 중에 호출하지 않습니다. 데스크톱 앱만 쓰는 사용자는 PATH에 `claude`가 없을 수 있습니다. 또 프로세스를 주기적으로 띄우면 유휴 CPU 목표에 어긋나고, 그 CLI가 시작할 때 네트워크를 쓰는지도 알 수 없습니다.
  - 이 파일을 찾지 못하거나 형식이 바뀌면, 마지막 호출이 아직 TTL 안에 있는 세션을 "상태 확인 불가"로 표시하고 경고는 계속합니다.
- **경고 대상:** 메인 세션 가운데 실행 중이고 상태가 idle이며, 아래 두 조건을 모두 만족하는 세션입니다. 서브에이전트는 5분 캐시를 쓰고 금방 끝나므로 경고하지 않습니다.
  - 마지막 호출의 컨텍스트 크기(`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`)가 기본 100,000토큰 이상이다.
  - 아직 만료되지 않았다.
- **표시 내용:** 남은 시간과, 만료되면 재구축에 드는 예상 비용(컨텍스트 크기 × 해당 TTL의 쓰기 단가)을 보여줍니다.
- **알림 (사용자가 켰을 때만):**
  - 만료 10분 전에 보냅니다. 10분은 기본값이고 바꿀 수 있습니다.
  - 같은 세션에 같은 만료 시점으로는 한 번만 보냅니다.
  - 마지막 호출의 TTL이 5분인 세션에는 알림을 보내지 않고 화면에만 표시합니다. 알림 시점(10분 전)이 TTL보다 길기 때문입니다.
- **세션당 카운트다운:** 한 호출에는 TTL이 하나만 쓰이므로, 세션마다 카운트다운도 하나만 둡니다.
- **경고 문구의 원칙:** 사용자가 판단할 수 있도록 사실만 전합니다. 예를 들면 "이어서 하려면 8분 안에 메시지를 보내세요. 만료되면 다음에 열 때 72만 토큰으로 캐시를 다시 만듭니다." 정도로 씁니다. 오래 비울 세션이라면 이 숫자(컨텍스트 크기)가 정리할지 판단하는 근거가 됩니다.

### 6.6 기간
- 최근 5시간, 오늘(로컬 자정 기준), 최근 7일을 제공합니다.
- 공식 한도의 리셋 시각은 로컬에 없으므로, 기간을 한도 창에 맞추지 않습니다.

## 7. 구조

### 구성 요소
- **`RunningOutCore` (Swift 패키지):**
  - JSONL 증분 리더: 파일별 바이트 오프셋과 inode를 저장하고, 파일이 잘리거나 교체되면 그 파일을 처음부터 다시 색인합니다.
  - 파서, 중복 제거, 재구축 판정, 원인 분류, 기간별 집계, SQLite 저장소를 담당합니다.
- **`running-out` (개발용 CLI):**
  - `index`, `report --since 7d`, `events` 같은 명령을 둡니다.
  - 테스트와 보정에 씁니다. v1에서는 사용자용으로 문서화하지 않습니다.
- **`TokensAreRunningOut.app` (메뉴 막대 앱):**
  - `MenuBarExtra`, 설정 창, 알림으로 구성합니다.
  - 파일 변경은 `~/.claude/projects`를 대상으로 FSEvents로 감시합니다(하위 폴더 포함).
- **색인 저장 위치:** `~/Library/Application Support/TokensAreRunningOut/index.sqlite`에 둡니다. 원본에서 다시 만들 수 있는 파생 데이터이므로, 지워도 다시 색인하면 됩니다.

### 성능 목표 (제안, 빌더가 측정 후 조정)
- 첫 색인: 1.7GB 기준 2분 이내. 처음 30일치를 먼저 처리해서 화면을 띄우고, 나머지는 백그라운드에서 처리합니다.
- 증분 갱신: 파일이 바뀐 뒤 1초 이내에 반영합니다.
- 유휴 상태: CPU를 거의 쓰지 않고, 메모리는 100MB 이하로 유지합니다.

- **설정 창:**
  - "캐시 만료 전에 알림 받기"와 알림 시점
  - 재구축 임계값과 경고 임계값
  - "로그인할 때 열기"

### 8.3 화면 요구 사항

**접근성 (better-accessibility)**
- **메뉴 막대 항목의 VoiceOver 이름:** 숫자만 읽히지 않도록 이름을 붙입니다. 예를 들면 "Tokens Are Running Out, 오늘 쉬었다 돌아온 캐시 재구축 17%"입니다. 만료가 임박한 세션이 있으면 "캐시 만료 8분 전인 세션이 있습니다"로 읽힙니다. 장식용 아이콘은 접근성 트리에서 숨깁니다.
- **키보드 조작:** 모든 조작을 키보드로 할 수 있어야 합니다.
  - 기간 선택은 기본 제공되는 segmented `Picker`를 씁니다.
  - "분류 근거 보기"와 "설정 열기"는 기본 `Button`으로 만듭니다.
  - Esc를 누르면 팝오버가 닫힙니다.
  - 직접 만든 제스처만으로 동작하는 조작은 두지 않습니다.
- **색에만 의존하지 않기:** 원인 분해 막대는 항목 이름과 %를 텍스트로 함께 표시합니다. Swift Charts를 쓰면 막대마다 접근성 레이블과 값을 지정합니다.
- **자동 갱신:** 남은 시간은 1분 단위로 갱신하고, 갱신될 때마다 VoiceOver가 읽어 주지 않게 합니다. 시간을 알려 주는 역할은 알림이 맡습니다.
- **모션 줄이기:** 시스템의 "동작 줄이기" 설정을 따르고, 이 설정이 켜져 있으면 움직임 대신 투명도 변화만 씁니다.

**레이아웃 (better-layout)**
- **간격으로 묶기:** 구분선 대신 간격으로 그룹을 나눕니다. 그룹 사이 간격은 그룹 안 간격의 2배 이상으로 합니다(예: 8pt와 16pt). 구분선은 하단 메뉴 위에만 둡니다.
- **잘린 제목:** 긴 세션 제목은 한 줄로 자르되, 전체 제목은 도움말 툴팁(`.help`)과 "분류 근거 보기" 화면에서 볼 수 있게 합니다.
- **크기:** 팝오버 너비는 약 360pt로 고정하고, 높이는 내용에 맞춥니다. 목록이 길어지면 스크롤하게 하고, 다음 항목이 조금 보이게 해서 더 있다는 것을 알 수 있게 합니다.
- **긴 문자열 대비:** 레이블에 고정 폭을 주지 않습니다. 영어처럼 문자열이 길어지는 언어에서도 줄바꿈이나 잘림으로 버틸 수 있게 합니다.

**문구 (better-writing)**
- **용어 통일:** "캐시 재구축(cache rebuild)"과 "줄일 수 있었던"으로 통일합니다. "낭비", "다시 씀" 같은 표현은 화면에 쓰지 않습니다.
- **경고 문구:** 경고는 사실과 다음 행동을 함께 말합니다. 예: "이어서 하려면 8분 안에 메시지를 보내세요."
- **오류 문구:** 오류는 원인과 복구 방법을 함께 말합니다(8.2 참고).
- **설정 토글:** 켜졌을 때의 동작으로 이름을 붙입니다. 예: "캐시 만료 전에 알림 받기"
- **버튼:** 동사로 시작합니다. 예: "설정 열기", "종료"
- **현지화:** 숫자, 시간, 복수형은 String Catalog(`.xcstrings`)와 `FormatStyle`로 처리하고, 문장을 조각으로 이어 붙이지 않습니다. 기본 언어는 영어로 하고, 한국어를 함께 제공합니다.

**타이포그래피 (better-typography)**
- **고정 폭 숫자:** 바뀌는 숫자(남은 시간, %, 토큰 수, 메뉴 막대의 숫자)에는 `.monospacedDigit()`을 적용합니다. 숫자가 바뀔 때 메뉴 막대 항목의 폭이 흔들리지 않게 하려는 것입니다.
- **글자 크기:** 시스템 텍스트 스타일만 씁니다. 본문은 `.body`, 보조 텍스트는 `.callout`이나 `.subheadline` 이상으로 하고, 10pt 캡션은 쓰지 않습니다.
- **굵기:** 굵기는 regular와 semibold 두 단계만 씁니다.

**색 (better-colors)**
- **시스템 색:** 시스템 의미 색(`primary`, `secondary`, `accentColor`)과 시스템 머티리얼만 쓰고, 색 값을 직접 지정하지 않습니다.
- **강조:** 강조색은 "줄일 수 있었음" 항목 하나에만 씁니다.
- **빨간색 금지:** 빨간색은 위험이나 삭제를 뜻하는데, 이 앱에는 그런 동작이 없으므로 쓰지 않습니다.
- **만료 경고:** 시스템 주황색을 쓰고, 아이콘과 텍스트를 함께 둡니다.

**UI 다듬기 (better-ui)**
- **애니메이션:** 팝오버는 자주 여닫는 화면이므로, 열 때 등장 애니메이션을 넣지 않습니다. 막대가 차오르는 애니메이션도 넣지 않습니다.
- **아이콘:** 아이콘은 SF Symbols 하나로 통일합니다. 메뉴 막대 아이콘은 템플릿 이미지로 만들어, 메뉴 막대의 밝기에 따라 색이 자동으로 바뀌게 합니다.
- **상태 변화의 흔적:** 만료 임박 같은 상태 변화는 아이콘과 텍스트로 남깁니다. 움직임만으로 알리지 않습니다.

### 8.4 디자인 검토 기록 (2026-11-17, 구현 전 시안 대상)

- **검토 범위:** 이 문서 8장의 텍스트 시안을 better-interface의 순서(접근성, 레이아웃, 문구, 타이포그래피, 색, UI)대로 검토했습니다. 구현된 화면이 없으므로 실제 렌더링, 대비 측정, VoiceOver 읽기, 키보드 이동은 **검증하지 못했습니다**. 이 항목들은 구현 뒤에 확인합니다.

## 9. 배포

- **저장소와 라이선스:** GitHub 공개 저장소 `tokens-are-running-out`에 MIT 라이선스로 올립니다.
- **릴리스:** 개발자에게 Apple Developer Program 계정이 있습니다. 릴리스 빌드는 Developer ID로 서명하고 `notarytool`로 공증한 뒤 GitHub Releases에 올립니다. 서명과 공증은 CI(GitHub Actions)에서 하고, 인증서와 공증용 자격 증명은 저장소 비밀 값으로 보관합니다.
- **Homebrew:** 출시 시점에는 프로젝트 자체 tap(`homebrew-tap` 저장소, cask 이름 `tokens-are-running-out`)으로 제공합니다. 공식 homebrew/cask 저장소에는 등록 조건(인지도, 서명과 공증)을 만족한 뒤에 신청합니다. 등록 조건은 신청 시점에 다시 확인합니다.
- **업데이트:** v1에는 자동 업데이트를 넣지 않습니다(네트워크 금지 원칙). 업데이트는 Homebrew로 받습니다.
- **텔레메트리:** 넣지 않습니다.

## 10. 테스트와 검증

- **단위 테스트:** 실제 기록의 구조를 본뜬 합성 JSONL 픽스처로 파서, 중복 제거, 재구축 판정, 원인 분류를 테스트합니다. 실제 사용자 기록은 저장소에 넣지 않습니다.

    - API 호출 4,133건, 캐시 쓰기 32,306,214토큰
    - 재구축 80건(21,262,573토큰, 캐시 쓰기의 65.8%). 이 중 서브에이전트 18건, 메인 세션 62건

## 13. 주요 위험과 첫 확인 사항

- **검증 범위가 좁습니다.** 모든 수치는 개발자의 Mac 한 대에서, 데스크톱 앱 세션만으로 얻었습니다. 이 세션들은 메인 세션이 모두 1시간 캐시를 썼습니다.
- **터미널 사용자는 다를 수 있습니다.** 인용한 불만의 상당수는 터미널 CLI 사용자에게서 나왔습니다. 일부 이슈는 메인 세션의 캐시가 5분으로 떨어졌다고 보고합니다(#46829, 그리고 텔레메트리를 끄면 1시간 캐시도 꺼진다는 #45381).
- **5분 캐시 사용자에게는 설계가 다르게 작동합니다.** 메인 세션이 5분 캐시를 쓰는 사용자에게는 다음 문제가 생깁니다.
  - 커피 한 잔 마실 때마다 "짧은 휴식 후 만료"가 생깁니다.
  - 알림은 보내지 않습니다(6.5).
  - "만료 전에 이어 간다"는 조언도 현실적이지 않습니다.
- **첫 구현 단계: 터미널 세션의 TTL 확인.** 개발자의 Mac에서 터미널로 대화형 세션을 열어 다음을 확인합니다.
  - 메인 세션이 쓰는 TTL
  - `--resume`이 같은 파일에 이어서 기록하는지
  
  5분 캐시라면, 메인 세션이 5분 캐시를 쓰고 있다는 사실 자체를 진단 결과로 보여줄지 결정합니다. 원인은 단정하지 않고 사실만 보여줍니다.
- **수요의 형태가 가설입니다(1장).** 첫 공개 뒤에는 GeekNews나 Show HN 같은 곳에 소개하고, 별 수와 다운로드 수, 이슈 내용으로 이 진단 방식이 원하는 것이었는지 확인합니다.
- **기록 형식이 바뀔 수 있습니다(3장).** 형식 변화 감지와 기준값 대조로 대비합니다.
