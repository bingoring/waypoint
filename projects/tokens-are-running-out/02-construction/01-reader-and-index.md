# [Stage 2-1] 기록 리더와 색인

## 목적

Claude Code 기록 파일을 읽기 전용으로 증분 색인하는 Swift 패키지 `RunningOutCore`와 개발용 CLI `running-out`을 만든다. 산출물은 2-2(재구축 판정·원인 분류·집계)가 그대로 쓸 수 있는 SQLite 색인이다.

## 입력 (Inputs)

- 승인된 스테이지: [`../01-inception/02-domain-model.md`](../01-inception/02-domain-model.md), [`../01-inception/03-architecture-decision.md`](../01-inception/03-architecture-decision.md)
- 설계 입력: [`../inputs/design.md`](../inputs/design.md) 3장(제약), 5장(데이터 출처), 7장(구조), 10장(테스트)
- 기준값 스크립트: 메인 저장소의 `prototype/drain.py`

### 범위

### 2-1에서 새로 확인한 사실과 1-2 계약 확장
- **같은 호출이 여러 파일에 있다.** 이 Mac의 기록에서 고유 메시지 43,707개 중 4,628개가 두 개 이상의 기록 파일에 나타났다(2026-11-17 확인). 세션을 이어 가거나 갈라낼 때 이전 대화가 새 파일로 복사되기 때문으로 보인다. 복사본 대부분(3,667건)은 줄의 `sessionId`가 원래 파일의 ID와 같았지만, 310건은 복사할 때 `sessionId`도 새 파일의 ID로 바뀌어 있었다.
- **파일 단위 중복 제거는 시간이 지나면 결과가 바뀐다.** 기준값 기간(2026-11-10 ~ 11-17)의 호출 중 280건이 오늘 이어 간 세션의 새 파일에 복사되었다. 그래서 파일 단위로 세면 4,413건이 되고, 전체 단위로 세면 원래 기준값인 4,133건 그대로다.
- **1-2 계약 확장(불변식 1):** "같은 `message.id`는 **모든 기록 파일을 통틀어** 하나의 ApiCall이다. 비용과 개수는 소유 파일 하나에서만 센다. 복사된 호출도 그 파일 안의 순서(직전 호출, 압축 경계)를 정하는 맥락으로는 쓴다." 소유 파일을 정하는 규칙은 Build Spec business-rules R4에 있다. [DECISIONS](../DECISIONS.md) 2026-11-17 항목에 기록했다.
- **기준값은 바뀌지 않는다.** 프로토타입을 전체 단위 중복 제거로 고친 뒤 다시 돌려도 설계 입력 10장의 값과 같았다.

### 터미널 세션의 캐시 TTL 확인은 2-2 착수 전으로 옮김
- 2-1 첫 작업으로 계획했지만, 이 Mac의 터미널 CLI 로그인이 만료되어 확인하지 못했다. 로그인은 사용자가 직접 해야 한다.
- 2-1의 색인은 호출마다 TTL을 그대로 저장하므로 결과와 무관하게 동작한다. 결과가 영향을 주는 곳은 2-2의 분류 규칙이다. 그래서 **2-2 착수 전 확인 항목**으로 옮긴다.

### 결정 (작성자 판단, DECISIONS에 기록)
- **외부 의존성 없음:** SQLite는 macOS에 포함된 `SQLite3`를 얇게 감싸서 쓰고, CLI 인자는 직접 파싱한다. 오픈소스 신뢰와 공급망 위험을 줄이기 위해서다.
- **린터:** Swift 6.3 툴체인에 포함된 `swift format lint --strict`를 쓴다. 따로 설치할 것이 없다.
- **언어 모드:** Swift 6 언어 모드(엄격한 동시성 검사)로 빌드하고, 경고를 0건으로 유지한다.
