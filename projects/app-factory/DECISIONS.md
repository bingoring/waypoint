## 2026-10-13 · Waypoint 워크플로 적용
- **결정:** App Factory 작업 전체를 Waypoint 라이프사이클로 진행한다. 문서는 `projects/app-factory/`에 둔다.
  메인 코드 저장소는 1-3 승인 후 만들고, waypoint를 서브모듈로 연결한다.
- **근거:** 사용자가 "가장 중요하게 여겨야 할 것"으로 지정했다.
- **대안(탈락):** superpowers 브레인스토밍 → 스펙 → 계획 흐름 — 사용자가 Waypoint를 지정함.
- **결정자:** 사용자

## 2026-10-13 · 앱 카테고리 A~E 모두 범위에 포함
- **결정:** 게임(A), 재미·랜덤(B), 생활 계산기(C), 센서 도구(D), 습관 트래커(E)를 모두 대상으로 한다.
- **근거:** 사용자가 다섯 카테고리 모두 좋다고 승인했다. 목적은 "필요한 앱"보다 빠른 수익화다.
- **대안(탈락):** 게임만 / 유틸리티만 — 어느 분야에 반응이 오는지 검증하기 전에 좁힐 근거가 없다.
- **결정자:** 사용자

## 2026-10-13 · 기술 스택 잠정 선택: Flutter + Melos
- **결정:** Flutter + Melos 모노레포를 잠정 채택한다. 최종 확정은 1-3 ⚠️ 비가역 게이트에서 한다.
- **근거:** 사용자 기준은 "확장성과 커뮤니티 활성도"이고, 게임(A) 성능이 좋은 쪽을 선호했다. 공식 AdMob 플러그인(`google_mobile_ads`)이 있다.
- **대안(탈락, 잠정):** React Native + Expo — 사용자가 forin에서 쓰고 있어 익숙하고 EAS 배포가 편하지만, 게임 렌더링 성능에서 불리하다.
  네이티브(Kotlin + Swift) — 작업량이 두 배라 빠른 제작 목표와 맞지 않는다.
- **결정자:** 사용자

## 2026-10-13 · 1-1 Context Synthesis 승인 (PRD v1.0, 포트폴리오 규칙 P1~P6)
- **결정:** PRD 초안을 v1.0으로 확정하고, 반복 콘텐츠 정책 대응 규칙 P1~P6(기능 중복 금지, 소기능은 모드로 묶기, 보이는 셸 비공유,

- **근거:** 앱 하나의 정책 위반이 같은 계정의 포트폴리오 전체를 잃게 만들 수 있다(1-1 §2 E2·E3).

- **결정자:** 사용자

## 2026-10-13 · Google Play 조직 계정 사용 (Q1)
- **결정:** 사업자등록 후 Play **조직 계정**을 새로 만든다. 오너가 Windows PC로 홈택스에서 직접 등록한다(macOS에서 보안 프로그램 미지원).
  등록 → D-U-N-S → 계정 개설은 3-1 Store Release 착수 전 선행 조건이며, 1-2부터 Phase 2까지는 병행 진행한다.
- **근거:** 2023-11 이후 개인 계정은 앱마다 테스터 12명 × 14일 비공개 테스트가 필요해 "앱당 1~3일" 목표와 맞지 않는다.
- **대안(탈락):** 기존 개인 계정 사용 — 앱마다 14일 지연이 생긴다.
- **결정자:** 사용자

## 2026-10-13 · 시장·플랫폼·광고 네트워크 (Q2·Q3·Q5)
- **결정:** 한국어 + 영어 동시 출시(한국 전용 기능은 한국어만), **Android 먼저** 출시하고 30일 지표가 좋은 앱만 iOS로 확장한다. 광고는 **AdMob 단독**으로 시작한다.
- **근거:** 영어를 함께 내면 D(센서 도구)·A(게임)의 글로벌 수요를 받을 수 있다. iOS는 4.3 리젝 위험과 비용이 있어 검증 후 확장한다. 미디에이션은 DAU가 작을 때 이득이 적고 설정 비용이 크다.
- **대안(탈락):** 한국 전용 / 글로벌 우선, 양 플랫폼 동시 출시, 처음부터 미디에이션(AppLovin MAX 등).
- **결정자:** 사용자

## 2026-10-13 · Wave 1 구성과 순서 (Q6)
- **결정:** 로또 번호 생성기 → 연봉 실수령액 계산기 → 소음 측정기 → 물 마시기 알림 → 블록·숫자 퍼즐 1종.
- **근거:** 쉬운 앱으로 코어와 배포 파이프라인을 먼저 검증하고, 게임 키트는 마지막에 만든다. 카테고리마다 하나씩 골라 반응을 비교한다.
- **대안(탈락):** 퍼즐 게임을 앞당김 — 게임 키트를 먼저 만들어야 해서 첫 출시가 늦어진다.
- **결정자:** 사용자

## 2026-10-13 · 개발자 브랜드와 저장소 (Q7·Q8)
- **결정:** 모든 앱을 하나의 개발자명(스튜디오 브랜드)으로 내고 앱마다 고유 이름을 붙인다. 스튜디오명은 3-1 전까지 정한다.
  메인 코드 저장소는 비공개 `bingoring/app-factory`이고, waypoint는 서브모듈로 연결한다.
- **근거:** 계정 하나에 브랜드 하나가 관리하기 쉽다. 광고 단위 ID와 서명 설정을 보호하려면 비공개여야 한다.
- **대안(탈락):** 앱별 개발자명 — 계정이 하나라서 이점이 없다. 공개 저장소 — 설정 노출 위험.
- **결정자:** 사용자

## 2026-10-13 · 1-2 Domain Model 승인 — 코어는 화면을 소유하지 않는다
- **결정:** 공통 코어는 광고·동의·분석·원격 설정·인앱결제·리뷰·저장소 로직과 행 단위 부품(배너 슬롯, 광고 제거 행 등)만 제공하고,
  홈·내비게이션·설정 페이지 같은 화면 단위 위젯은 제공하지 않는다. 앱 생성기는 빈 홈 화면 + 코어 연결 + `app.yaml`을 만든다.
- **근거:** 1-1 P3(보이는 셸 비공유)을 계약 수준에서 강제해 반복 콘텐츠 정책 위험을 구조적으로 줄인다.
- **대안(탈락):** 코어가 공통 셸(홈 템플릿·설정 페이지)을 제공하고 앱은 테마만 바꿈 — 제작은 빠르지만 "테마만 다른 같은 앱"이 된다.
- **결정자:** 사용자 (AI 제안 승인)

## 2026-10-13 · 원격 설정은 다음 실행에 활성화, 영수증 서버 검증 없음
- **결정:** 원격 설정은 백그라운드에서 받아 두고 다음 실행에 활성화한다. 광고 제거 구매는 서버 영수증 검증 없이 클라이언트에서 확인·acknowledge한다.
  광고 수익 이벤트(`ad_impression`)는 AdMob–Firebase 연결의 자동 수집에 맡기고 코어는 노출 판정(`ad_show_attempt`)만 기록한다.
- **근거:** 사용 중 광고 빈도·화면 데이터가 바뀌는 것을 막는다. 서버 비용 0원 제약(PRD §3), IAP 매출 비중이 작아 위변조 위험을 수용한다. 수익 중복 집계를 피한다.
- **대안(탈락):** 실행 즉시 fetch-and-activate(시작 지연·화면 변동), 서버리스 영수증 검증(운영 부담 대비 이득 작음), 코어의 paid event 직접 기록(중복).
- **결정자:** 사용자 (AI 제안 승인)

## 2026-10-13 · 광고 제거 가격·전면 광고 강도·보상형 실패 처리 (D1~D3)
- **결정:** 광고 제거 **₩2,500 / US$1.99**(전 앱 동일). 전면 광고는 보수적 기본값(최소 간격 90초, 세션당 5회, 첫 세션 없음)으로 시작해 원격 설정으로 조정한다.
  보상형 광고를 불러오지 못하면 보상을 준다.
- **근거:** 저가로 구매 전환율을 우선한다(오너 선택). 초기에는 리텐션과 평점을 지키는 편이 히트 가능성에 유리하다. 광고 실패로 사용자가 막히면 평점이 떨어진다.
- **대안(탈락):** ₩3,900 / $2.99(AI 기본안), ₩5,900 / $4.99, 공격적 전면 광고(60초·8회·첫 세션부터), 보상 미지급.
- **결정자:** 사용자

## 2026-10-13 · 품질·보안·메모리 기준을 CI 게이트로 강제
- **결정:** 스토어 심사·보안 검토가 엄격해진 것을 전제로, 코드 구조(3층·의존 방향), 엄격한 정적 분석, 권한 허용 목록, 난독화·비밀 검사,
  메모리·앱 크기·콜드 스타트·비정상 종료율 예산을 정의하고 CI에서 강제한다. 구체 수치는 1-3 §7이고, R-1 독립 리뷰의 기준선이 된다.
- **근거:** 오너 요구("코드를 더 체계적이고 메모리 효율적으로"). 앱 수가 늘수록 수동 확인은 누락되므로 자동 게이트가 필요하다.
- **대안(탈락):** 리뷰 시 수동 확인만 — 앱 수에 비례해 비용이 늘고 누락된다.
- **결정자:** 사용자 (요구), AI (구체 기준 제안 — 1-3 승인 대기)

## 2026-10-13 · 1-3 Architecture Decision 승인 ⚠️ (비가역)
- **결정:** Flutter 3.47.7(Dart 3.13.5, FVM 고정) + Dart pub workspace·Melos 8.9. 앱마다 독립 Flutter 프로젝트(`apps/<slug>/`)를 두고,
  코어는 기능별 패키지(`factory_core`·`runtime`·`ads`·`firebase`·`iap`·`ui`·선택 패키지)로 나눈다. 상태 관리는 Riverpod 3(코드 생성 없음).
  Wave 1 퍼즐은 순수 Flutter로 만들고 Flame은 실시간 게임에서만 쓴다. 앱별 Firebase 프로젝트, GitHub Actions(Linux) + fastlane supply,
  Play App Signing + 앱별 업로드 키. 1-3 §7 품질 기준을 CI 게이트로 강제하고 R-1 리뷰 기준선으로 쓴다.
- **근거:** 게임 성능과 공식 AdMob 지원(1-1), flavor는 한 앱의 변형용이라 서로 다른 앱에 쓰면 권한·SDK가 섞여 심사·보안·크기에 불리하다.
  Firebase 공식 안내상 한 프로젝트는 같은 앱의 변형만 담아야 한다. Android 먼저(Q3)라 Linux 러너로 충분하다.
- **대안(탈락):** React Native + Expo, 네이티브, Unity / 한 프로젝트 + flavor / 단일 core 패키지 / Bloc / 처음부터 Flame /
  공용 Firebase 프로젝트 / Codemagic, r0adkll 액션 / 업로드 키 공유.
- **결정자:** 사용자 (AI 제안 승인)

## 2026-10-13 · Waypoint 프레임워크 개선 (승인 결과 기록·외부 사실 표기·리뷰 기준선)
- **결정:** FRAMEWORK에 세 규칙을 추가했다. ① 사람의 게이트 답은 `AI Proposal`을 고치지 않고 `승인 결과` 표에 기록, 계약 확장은 확장하는 스테이지에 기록
  ② 외부 사실은 조회일·출처·확인 수준 표기 ③ 리뷰 게이트는 아키텍처 단계에서 정의한 품질 기준으로 판정.
- **근거:** app-factory 진행 중 실제로 필요했던 규칙이다. 오너가 진행 중 Waypoint 개선을 허용했다.
- **대안(탈락):** 프로젝트 문서에서만 임시로 처리 — 다른 프로젝트에 같은 공백이 반복된다.
- **결정자:** 사용자 (허용), AI (규칙 작성)
