## 2026-10-13 · 기술 스택 잠정 선택: Flutter + Melos
- **결정:** Flutter + Melos 모노레포를 잠정 채택한다. 최종 확정은 1-3 ⚠️ 비가역 게이트에서 한다.

## 2026-10-13 · 1-2 Domain Model 승인 — 코어는 화면을 소유하지 않는다
- **결정:** 공통 코어는 광고·동의·분석·원격 설정·인앱결제·리뷰·저장소 로직과 행 단위 부품(배너 슬롯, 광고 제거 행 등)만 제공하고,
  홈·내비게이션·설정 페이지 같은 화면 단위 위젯은 제공하지 않는다. 앱 생성기는 빈 홈 화면 + 코어 연결 + `app.yaml`을 만든다.
- **근거:** 1-1 P3(보이는 셸 비공유)을 계약 수준에서 강제해 반복 콘텐츠 정책 위험을 구조적으로 줄인다.
- **대안(탈락):** 코어가 공통 셸(홈 템플릿·설정 페이지)을 제공하고 앱은 테마만 바꿈 — 제작은 빠르지만 "테마만 다른 같은 앱"이 된다.
- **결정자:** 사용자 (AI 제안 승인)

## 2026-10-13 · 원격 설정은 다음 실행에 활성화, 영수증 서버 검증 없음
- **결정:** 원격 설정은 백그라운드에서 받아 두고 다음 실행에 활성화한다. 광고 제거 구매는 서버 영수증 검증 없이 클라이언트에서 확인·acknowledge한다.
  광고 수익 이벤트(`ad_impression`)는 AdMob–Firebase 연결의 자동 수집에 맡기고 코어는 노출 판정(`ad_show_attempt`)만 기록한다.
- **근거:** 사용 중 광고 빈도·화면 데이터가 바뀌는 것을 막는다. 서버 비용 0원 제약(PRD §3), IAP 매출 비중이 작아 위변조 위험을 수용한다. 수익 중복 집계를 피한다.
- **대안(탈락):** 실행 즉시 fetch-and-activate(시작 지연·화면 변동), 서버리스 영수증 검증(운영 부담 대비 이득 작음), 코어의 paid event 직접 기록(중복).
- **결정자:** 사용자 (AI 제안 승인)

## 2026-10-13 · 1-3 Architecture Decision 승인 ⚠️ (비가역)
- **결정:** Flutter 3.47.7(Dart 3.13.5, FVM 고정) + Dart pub workspace·Melos 8.9. 앱마다 독립 Flutter 프로젝트(`apps/<slug>/`)를 두고,
  코어는 기능별 패키지(`factory_core`·`runtime`·`ads`·`firebase`·`iap`·`ui`·선택 패키지)로 나눈다. 상태 관리는 Riverpod 3(코드 생성 없음).
  Wave 1 퍼즐은 순수 Flutter로 만들고 Flame은 실시간 게임에서만 쓴다. 앱별 Firebase 프로젝트, GitHub Actions(Linux) + fastlane supply,
  Play App Signing + 앱별 업로드 키. 1-3 §7 품질 기준을 CI 게이트로 강제하고 R-1 리뷰 기준선으로 쓴다.
- **근거:** 게임 성능과 공식 AdMob 지원(1-1), flavor는 한 앱의 변형용이라 서로 다른 앱에 쓰면 권한·SDK가 섞여 심사·보안·크기에 불리하다.
  Firebase 공식 안내상 한 프로젝트는 같은 앱의 변형만 담아야 한다. Android 먼저(Q3)라 Linux 러너로 충분하다.
- **대안(탈락):** React Native + Expo, 네이티브, Unity / 한 프로젝트 + flavor / 단일 core 패키지 / Bloc / 처음부터 Flame /
  공용 Firebase 프로젝트 / Codemagic, r0adkll 액션 / 업로드 키 공유.
- **결정자:** 사용자 (AI 제안 승인)

## 2026-10-13 · Waypoint 프레임워크 개선 (승인 결과 기록·외부 사실 표기·리뷰 기준선)

  ② 외부 사실은 조회일·출처·확인 수준 표기 ③ 리뷰 게이트는 아키텍처 단계에서 정의한 품질 기준으로 판정.
- **근거:** app-factory 진행 중 실제로 필요했던 규칙이다. 오너가 진행 중 Waypoint 개선을 허용했다.

- **결정자:** 사용자 (허용), AI (규칙 작성)

## 2026-10-13 · 2-1 Build Spec READY — 구현 세부값 확정
- **결정:** 정책 엔진과 서비스(광고·광고 제거·리뷰·세션)는 순수 Dart `factory_core`에 두고, SDK는 게이트웨이 인터페이스 뒤 어댑터로 분리한다.
  동의 수집과 광고 초기화는 **첫 프레임 뒤**로 미룬다(1-2 §3 순서 조정, 동의 전 광고 요청 금지는 유지). 세션 기준 30분, 원격 값은 범위를 벗어나면
  기본값 사용, 동의 갱신 타임아웃 5초, 보상형 로드 대기 5초, 리뷰 요청은 전면형 광고 10초 이내 금지. 광고 제거 하향은 Android
  `queryPastPurchases()` 조회 성공 + 상품 없음일 때만. 성능 기준 기기는 API 36 에뮬레이터로 우선 측정한다.
- **근거:** 기기 없이 핵심 로직을 단위 테스트(커버리지 90%)하기 위해서다. 동의를 첫 프레임 앞에 두면 1-3 §7.4 콜드 스타트 1.5초를 지킬 수 없다.
  `restorePurchases()`는 완료 신호가 없어 "구매 없음"을 판정할 수 없다(`in_app_purchase_android` 0.5.3 소스 확인).
- **대안(탈락):** 서비스 구현을 어댑터에 둠(테스트에 기기 필요), 동의를 `runApp` 전에 대기, 원격 값을 범위로 자르기, 실기기 확보 후 측정.
- **결정자:** 사용자 (READY 승인), AI (세부값 제안)

## 2026-10-13 · 2-1 승인 — 메모리 예산 조정(G1)과 AdService 계약 확장
- **결정:** 1-3 §7.4 메모리 예산을 앱 전체 PSS 유틸리티 ≤ 200MB · 게임 ≤ 300MB로 바꾸고, 코어가 통제하는 항목을 따로 예산화한다
  (광고 객체 ≤ 20MB, 코어·UI 추가분 ≤ 40MB). `AdService`에 `prepareRewarded()`·`onAppBackground()`를 추가하고, 시작 시에는 전면 광고만 미리 불러온다.
