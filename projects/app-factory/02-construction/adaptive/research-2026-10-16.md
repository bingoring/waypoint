# 모바일 캐주얼·하이퍼캐주얼 퍼즐의 적응형 난이도(DDA)·절차적 레벨 생성 조사

- 기준일: 2026-10-16
- 목적: Flutter 기반 다수 하이퍼캐주얼 게임 공통 「적응형 난이도 모듈」 설계 근거
- 표기: **[확인]** 1차 출처(논문 본문·특허·공식 문서·당사자 발언 보도 원문)를 직접 확인 / **[2차]** 블로그·요약·검색 스니펫 / **[추정]** 조사자 판단 / **미확인** 찾지 못함
- 용어 주의: 회사마다 "difficulty"의 방향이 다르다. **이 문서는 가능한 한 "승률(win rate, 시도당 성공 비율)"로 정규화**하고 원래 표현을 병기한다.
  - King "pass rate" = 시도 100회당 성공 수 → 승률
  - Playrix "difficulty" = 패배/전체 시도 → **패배율** (difficulty 80% = 승률 20%)
  - Rovio(Dream Blast) "pass rate" = 플레이어별 (1/통과까지 시도 수)의 평균
  - Tactile(Lily's Garden) "difficulty" = 클리어 1회당 평균 시도 수 (≈ 1/승률)
  - EA(Xue 2017) "difficulty" = 1/win rate = 평균 시도 수 [2차]

**요점**
- 공개 자료가 있는 대형 퍼즐사(King·Rovio·Tactile·Playrix)는 모두 **"레벨을 오프라인으로 측정·예측·수정"** 하는 방식이고, **개인별 런타임 DDA를 공개적으로 인정한 곳은 EA(논문·특허)뿐**이다. [확인]
- King의 목표 승률 절대값은 **미확인**(논문에서 민감 정보로 제거).
- 공통 입력: 시도 수, 성공/실패, 포기까지 시간, 이탈(7일 기준). 공통 산출: 레벨별 승률·이탈률 예측, 레벨 순서·교체.

### Google Play 데이터 보안 양식 [확인]
- 「수집(Collect)」 = **앱에서 사용자 기기 밖으로 데이터를 전송하는 것**.
- 기기에서만 로컬 처리되고 밖으로 보내지 않는 데이터는 **공개(신고) 불필요**. SDK가 기기 안에서만 접근하는 것도 신고 불필요.
- 일시적 처리(ephemeral) = 메모리에만 두고 실시간 요청 처리에 필요한 기간만 보관. 단 **광고 프로필·기타 사용자 프로필 생성은 일시적 처리로 볼 수 없음**.
- 페이지 변경 기록 최신 2023-12-05 (조회 2026-10-16).
- [추정] 플레이 로그·시간대·네트워크 종류로 기기 안에서 난이도를 고르고 **아무것도 전송하지 않으면** 「수집」 아님. 그러나 **Firebase Analytics 등 분석 SDK가 이 필드를 서버로 보내는 순간** "App activity(앱 상호작용 등)" 수집으로 신고 대상. 기기 내 "플레이어 모델"이 '사용자 프로필'에 해당하는지는 전송이 없으면 문제되지 않는 것으로 읽힘(전송 시 일시적 처리 예외 불가).

### Android 권한 [확인] (developer.android.com Manifest.permission, 2026-10-16 조회)
- `ACCESS_NETWORK_STATE`: "Allows applications to access information about networks." **Protection level: normal** (API 1) — 런타임 동의 불필요, 매니페스트 선언만.
- `ACCESS_WIFI_STATE`: normal. `INTERNET`: normal.

## ⑦ 우리 모듈에 대한 시사점 [추정]

1. **풀이기는 봇을 대체하지만 보정은 대체 못 한다.** King·Rovio·Tactile가 비싼 봇으로 얻는 "레벨 고유 난이도"를 우리는 완전 탐색으로 정확히 얻는다(이기는 조합 비율, 니어미스 조합 수, 필요 탭 수). 그러나 사람 승률과의 관계는 King처럼 **logit(사람 승률) = β0 + β1·f(풀이기 지표) + Σβj·기믹 특징** 같은 보정이 필요. 출시 초기엔 손으로 정한 사전값 → 판 결과가 쌓이면 갱신(로컬, 그리고 동의 시 집계).
2. **구조 제안: 「스킬 체인 게이트 + Glicko-2 매칭 + 톱니 오프셋」** (Sarkar & Cooper 2020 형태).
   - 게이트: 기믹 해금은 **진행도(클리어 판 수·해당 기믹 사용 횟수)**로만. 레이팅이 높아도 미획득 기믹이 2개 이상 필요한 판은 후보 제외 → "첫 판 빨리 깼다고 어려운 기믹 바로 열기" 방지. King의 complexity staircase와 같은 생각.
   - 매칭: 플레이어 레이팅(평균·불확실성 RD)과 판 레이팅(풀이기 지표에서 초기화) 비교, 목표 패배확률에 가장 가까운 판 선택. 목표는 신규 ≈10% 패배(Sarkar, HCG 맥락 수치이므로 초기값일 뿐 자체 데이터로 조정)에서 시작해 실력 따라 완만히 상승.
   - 레이팅 변화폭 제한: King은 실력 파악에 "몇 주~몇 달"이 걸린다고 함 → 한 판 결과로 크게 움직이지 않게 RD 하한·변화량 상한. 초반 몇 판은 실력 추정에 쓰지 말고 튜토리얼 고정.
   - 톱니: 목표 승률에 주기적 오프셋(예: 5~7판마다 쉬어가기, 가끔 어려운 판, 어려운 판 다음 반드시 쉬운 판). 어려운 판 연속 금지(Playrix).
3. **연속 실패 완화**: Calgary처럼 "시도 수가 많으면 상승 금지"는 하드 제약, 그 위에 N회 연속 실패 시 **같은 기믹 세트 안에서** 이기는 조합 비율이 높은 판으로. 완화를 유료 제안과 같은 화면에 묶지 말 것(다크 패턴 해석 위험).
4. **시간 하나만 쓰지 말 것**: Calgary 결과에서 시간 단독 모델이 체감 난이도·진행감 최하. 시도 수·실패·니어미스·리셋을 함께. "가만히 있던 시간"은 King의 time-to-abandon처럼 **재미/막힘 신호**로 쓰되, 앱 백그라운드·화면 꺼짐과 구분.
5. **맥락 신호(시간대·Wi-Fi/LTE)는 난이도가 아니라 '페이스'에** 쓰기를 기본값으로: 출퇴근 추정 시간대·셀룰러면 짧은 판(탭 수 적은 판)·이어하기 쉬운 구성, 집 Wi-Fi·저녁이면 긴 판 허용. 난이도에 반영하려면 자체 A/B 후. 근거가 거의 없는 영역(상용 공개 사례 미확인).
   - 늦은 밤 세션 늘리기 설계는 피함(문제적 이용 연구).
6. **니어미스 지표의 용도 분리**: 니어미스 조합 수는 "아깝다" 감정을 만들 수 있어 Royal Match 사례처럼 결제 압박에 쓰일 수 있음. 모듈 API에서 난이도/몰입 목적으로만 노출하고 결제 트리거와 연결하지 않는 원칙을 문서화.
7. **기기 안에서만 처리**: 모든 플레이어 모델을 로컬(shared_preferences/sqlite)에 두면 Google Play 「수집」 아님. 분석 업로드는 별도 옵트인 모듈로 분리하고, 켜면 데이터 보안 양식 갱신. ACCESS_NETWORK_STATE는 normal이라 동의 팝업 불필요. SSID·위치는 읽지 않음.
8. **투명성**: "조작" 반발을 줄이려면 레벨 번호 대신 "오늘의 퍼즐"처럼 개인화가 자연스러운 표현, 설정에 "도전 모드(적응 끔)" 제공, 리더보드는 적응 판 제외 또는 고정 시드 판만.
9. **출시 전 시뮬레이션**: Rovio Algorithm 1을 거의 그대로 Dart로 옮겨, skill·persistence·boredom이 다른 가상 플레이어 수천 명이 우리 모듈을 상대로 판을 받게 하고 ① 레이팅 수렴 속도 ② 실제 승률 분포가 목표에 맞는지 ③ 기믹 해금 시점 분포 ④ 이탈 시뮬 값을 확인. 가상 플레이어의 "판 통과 확률"은 풀이기 지표 + 실력 함수로 정의(예: 이기는 조합 비율이 높을수록, 필요 탭 수가 적을수록 통과 확률↑).
10. **밴딧은 2순위**: 목표 승률을 맞추는 문제엔 Glicko-2가 직접적. 밴딧/Thompson sampling은 "톱니 패턴 A vs B" 같은 설계 선택을 온라인 비교할 때 쓰는 편이 적합.
11. **FBCA**는 생성 파라미터 공간(격자 크기·하품 수 등)이 연속적일 때 "목표 시간"으로 빠르게 맞추는 데 유용하나, 가우시안 프로세스 구현 부담과 시간 단독 지표 문제 때문에 1차 버전엔 비권장.
