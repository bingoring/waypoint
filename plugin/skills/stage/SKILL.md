## 상태 생애주기

```
PENDING → IN_PROGRESS → AI_PROPOSED → HUMAN_APPROVED
```

| 상태 | 설명 |
|------|------|
| `PENDING` | 시작 전. 이전 스테이지가 APPROVED되지 않으면 진입 불가 |
| `IN_PROGRESS` | AI가 현재 작업 중 |
| `AI_PROPOSED` | AI 제안 완료. 사람의 검토 대기 |
| `HUMAN_APPROVED` | 사람이 승인. 다음 스테이지 언락 |

## 비가역 게이트 추가 체크리스트

`⚠️` 표시가 있는 스테이지는 아래 항목을 추가로 확인해야 승인 가능하다:

- [ ] 이 결정을 번복할 경우 영향받는 파일/레이어 목록을 작성했는가
- [ ] 대안을 검토하고 탈락 이유를 문서화했는가
- [ ] 외부 의존성(API, 라이브러리, 비용)을 확인했는가

## 승인 결과 기록

게이트 질문(미해결 질문, 체크리스트)에 대한 사람의 답은 대개 채팅으로 온다. `AI Proposal`은 AI 전용이지만 *제안 당시의 기록*이므로
사후에 고쳐 쓰지 않는다. 대신 AI가 검토 게이트 아래 `### 승인 결과 (날짜, 결정자)` 표에 질문별 답을 기록한다.

- 답이 AI 기본안과 다르면 "기본안과 다름 — §N의 값은 이 답으로 대체한다"처럼 **어느 절을 무효화하는지** 명시한다.
  이후 스테이지는 `AI Proposal`보다 `승인 결과`를 우선해서 읽는다.
- 같은 내용을 `DECISIONS.md`에도 항목으로 남긴다(승인 결과 = 스테이지 내 요약, DECISIONS = 근거와 탈락 대안).
- 승인 *이후* 다른 스테이지에서 계약을 확장·변경해야 하면, 원래 스테이지를 다시 열지 말고 변경하는 스테이지에
  "N-M 계약 확장"으로 적고 DECISIONS에 기록한다. 원래 스테이지에는 한 줄 링크만 덧붙인다.

## 외부 사실 표기

라이브러리 버전, SDK 요구사항, 스토어·광고 정책, 가격처럼 시간이 지나면 바뀌는 사실은 다음을 함께 적는다.

- **조회일**, **출처 URL**, **확인 수준**(`공식 확인` / `2차 자료` / `추론`)
- 공식 문서 조회 도구(예: Context7)를 쓸 수 없으면 웹 검색·공식 페이지로 대체하고, 그 사실을 적는다.
- `2차 자료`·`추론`인 사실에 의존하는 결정은 "재확인 시점"(예: 3-1 착수 전)을 함께 적는다.

## STATUS.md 업데이트 규칙

스테이지 상태가 변경될 때마다 STATUS.md의 테이블을 함께 업데이트한다.

## 문서 깊이 — 린 기본 + 적응형 깊이

스테이지 문서는 **기본은 경량(간결)**하게 쓴다. "문서가 일에 맞춘다" — 복잡도에 깊이를 맞춘다.

- **단순 스테이지**: 목적·입력·체크리스트·간단한 AI 제안으로 짧게.
- **복잡·고위험 스테이지**: AI 제안에 다음을 추가한다.
  - **컴포넌트/모듈 분해**
  - **NFR · 성능 목표**
  - **테스트·검증 계획** (순수 로직은 자동화 테스트로 검증, 시각/수동은 명시)

> 균일하게 얇으면 복잡 단계의 설계·근거가 사라진다. 반대로 모든 단계를 무겁게 쓰면 의식(ceremony)이 되어
> 속도를 깎는다. 깊이는 단계별로 판단한다.

> 템플릿: 스테이지 문서 `${CLAUDE_PLUGIN_ROOT}/templates/stage-template.md`, 비가역 게이트 체크리스트 `${CLAUDE_PLUGIN_ROOT}/templates/gate-template.md`.

> 템플릿 파일은 Read 도구로 읽어 Write 도구로 프로젝트에 복사한다. Bash 명령 안에서는 `${CLAUDE_PLUGIN_ROOT}`를 쓰지 않는다(환경변수로 노출되지 않는다).
