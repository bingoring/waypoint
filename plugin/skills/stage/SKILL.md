## 상태 생애주기

상태 값은 STATUS 표의 「상태」 칸에 쓰고, 보드의 열과 1:1로 대응한다.

| 상태 값 | 보드 열 | 뜻 |
|---|---|---|
| `PENDING` | 대기 | 시작 전 |
| `IN_PROGRESS` | 진행 중 | AI가 작업 중이다. 계획을 쓰는 중이거나, 계획 승인 뒤 구현하는 중이다. |
| `AI_PROPOSED` | 검토 대기 | 오너가 검토할 차례다. 계획 검토인지 결과 검토인지는 「지금」 칸에 적는다. |
| `HUMAN_APPROVED` | 승인 | 오너가 결과를 승인했지만 PR이 아직 머지되지 않았다(예: 「머지·배포는 나중에」). |
| `MERGED` | 머지됨 | 스테이지의 PR이 기본 브랜치에 머지되어 스테이지가 끝났다. |
| `DEFERRED` | 보류 | 오너가 보류했다. 보류 전 상태와 다시 시작할 조건은 「지금」에 적는다. |

이 여섯 값 밖의 값(`IMPLEMENTED`, `READY`, `APPROVED`, 「완료(날짜)」 같은 글)은 상태 칸에 쓰지 않는다.

**흐름:**
- 설계 스테이지(코드를 만들지 않는 스테이지): `PENDING → IN_PROGRESS → AI_PROPOSED → HUMAN_APPROVED → MERGED`
- 코드 스테이지: `PENDING → IN_PROGRESS → AI_PROPOSED(계획 검토) → IN_PROGRESS(구현) → AI_PROPOSED(결과 검토) → HUMAN_APPROVED → MERGED`
- 오너가 수정을 요청하면 `IN_PROGRESS`로 돌아간다.
- 오너가 보류하면 어느 상태에서든 `DEFERRED`로 가고, 다시 시작하면 「지금」의 머리말이 가리키는 보류 전 상태로 돌아간다.
- 결과를 승인하면서 바로 머지하면 `HUMAN_APPROVED`를 거치지 않고 `MERGED`로 간다.

**다음 스테이지로 넘어가는 조건:** 앞 스테이지의 계획이 승인되면(스테이지 문서의 「승인 결과」에 계획 승인이 기록되면) 다음 스테이지를 시작할 수 있다. STATUS에서는 앞 스테이지의 줄이 `구현: `·`결과 검토: ` 머리말이거나 `HUMAN_APPROVED`, `MERGED`이면 계획이 승인된 것이다. 결과 승인이나 머지를 기다리지 않는다. 단, 리뷰 게이트(`🔍`)는 예외다. Operations의 첫 스테이지는 리뷰 게이트(예: R-1)의 결과가 승인된 뒤에 시작한다(core-rules의 독립 코드 리뷰 게이트 규칙).

**Build Spec 상태와의 관계:** Build Spec의 `READY`는 계획 승인에, `IMPLEMENTED`는 결과 검토 직전에 대응한다. 이 값들은 Build Spec 인덱스 안에서만 쓴다. Build Spec은 구현 스펙이 얼마나 준비되었는지를, STATUS는 스테이지가 보드의 어디에 있는지를 나타낸다.

## STATUS 표

스테이지 상태의 원본은 메인 체크아웃 `docs/waypoint/STATUS.md`의 표 한 곳이다. 스테이지 문서와 Build Spec은 스테이지 상태를 들고 있지 않다. 표의 한 줄이 보드의 카드 한 장이다.

**파일 구성:** 제목 한 줄, 링크 한 줄, `## 스테이지` 절, `## 오너 할 일` 절만 둔다. 배너, 「AI 진입점」, `Last updated` 같은 다른 내용은 두지 않는다. 날짜는 git 이력에, 지난 기록은 `HISTORY.md`에 있다. 링크 줄에는 PRD, DECISIONS, HISTORY, 최신 핸드오프처럼 자주 여는 문서의 링크만 둔다.

**표:** 머리 줄은 `| ID | 스테이지 | 상태 | 줄기 | 지금 | 기다림 | 링크 |`이다. 표는 하나만 두고, 단계는 ID의 앞자리로 구분한다. 줄은 ID 순서로 두고, 상태가 바뀌어도 줄을 옮기지 않는다. 셀 안에서는 `|`와 줄바꿈을 쓰지 않는다.

| 칸 | 규칙 |
|---|---|
| ID | `<단계>-<번호>` 형식이다(예: `1-1`, `2-16`, `R-1`, `3-13`). 한 번 정한 ID는 바꾸거나 다시 쓰지 않는다. |
| 스테이지 | 짧은 이름이다. `⚠️`(비가역 게이트)와 `🔍`(리뷰 게이트) 표시는 이름에 붙인다. 괄호로 긴 설명을 덧붙이지 않는다. |
| 상태 | 위 「상태 생애주기」의 여섯 값 가운데 하나다. |
| 줄기 | 카드를 가로로 묶는 기준이다(예: `Yawn`, `공 물리`, `출시`). 비워 둘 수 있다. 같은 줄기는 같은 철자로 쓴다. |
| 지금 | 지금 하는 일이나 다음 할 일을 80자 이하의 한 줄로 쓴다. 아래 머리말로 시작한다. `PENDING`과 `MERGED`일 때는 비운다. 다음 세션이나 오너가 알아야 할 것이 바뀔 때만 고친다. 하위 진행의 이력은 여기에 쌓지 않고 스테이지 문서의 「진행 기록」에 쓴다. |
| 기다림 | AI가 스스로 풀 수 없어서 카드가 멈춰 있는 이유만 쓴다(예: `오너 판정`, `오너 할 일`, `Play 신원확인`). 오너 할 일 때문이면 내용을 되풀이하지 않고 `오너 할 일`이라고만 쓴다. |
| 링크 | 머지 전에는 PR 링크를, 머지 뒤에는 스테이지 문서의 상대 경로 링크(`docs/waypoint/` 기준)를 쓴다. 머지 뒤에도 PR 링크를 함께 남길 수 있다. 링크가 여러 개면 ` · `로 나란히 적는다. |

**「지금」의 머리말:** STATUS만 보고도 계획이 승인되었는지, 보류 전에 어느 상태였는지 알 수 있게 한다.

| 상태 | 머리말 |
|---|---|
| `IN_PROGRESS` | `계획: `(계획을 쓰는 중) 또는 `구현: `(계획 승인 뒤 구현하는 중) |
| `AI_PROPOSED` | `계획 검토: ` 또는 `결과 검토: ` |
| `HUMAN_APPROVED` | 머리말 없음. 머지를 기다리는 이유를 쓴다(예: `배포 묶음을 모아 한 번에 머지`). |
| `DEFERRED` | 보류하기 전 상태의 머리말을 그대로 쓰고 보류 이유나 재개 조건을 붙인다(예: `구현: 오너 보류, 출시 뒤 재개`). |

설계 스테이지는 `계획: `과 `계획 검토: `만 쓴다.

**오너 할 일:** 한 줄에 하나씩 `- [ ] <할 일> (막음: <ID>)` 형식으로 쓴다. 막는 스테이지가 없으면 `(막음: <ID>)`를 생략하고, 여러 스테이지를 막으면 `(막음: 3-1, 3-2)`처럼 쓴다. 끝난 할 일은 체크하지 않고 줄을 지운다. 오너 할 일이 막는 스테이지의 줄에는 「기다림」에 `오너 할 일`이라고 쓴다.

**누가 언제 고치는가:** 상태가 바뀌는 순간 그 작업을 하는 세션이 메인 체크아웃에서 STATUS의 그 줄을 고치고 커밋·push한다. 지시문에 「중재자가 시작한 작업 세션」이라고 적힌 세션은 직접 고치지 않고 `waypoint:worker`의 「보고」로 중재자에게 알린다. 고치는 일은 중재자가 한다(`waypoint:mediator`). 커밋 절차와 `docs(status)` 커밋 메시지는 `waypoint:git`을 따른다. 커밋할 때 pre-commit 훅이 표의 형식을 검사한다.

## 비가역 게이트 추가 체크리스트

`⚠️` 표시가 있는 스테이지는 아래 항목을 추가로 확인해야 승인 가능하다:

- [ ] 이 결정을 번복할 경우 영향받는 파일/레이어 목록을 작성했는가
- [ ] 대안을 검토하고 탈락 이유를 문서화했는가
- [ ] 외부 의존성(API, 라이브러리, 비용)을 확인했는가

## 검토 요약

스테이지 문서의 맨 위(frontmatter와 제목 바로 아래)에 「검토 요약」 절을 둔다. `AI_PROPOSED`로 바꾸기 전에 채우고, 10줄 이하로 다음을 담는다. 오너가 이 절만 읽고 판단할 수 있어야 한다.
- 정해야 할 것
- 선택지와 추천
- 중재자가 대신 답한 질문과 작업 중에 둔 가정(오너가 확인할 것)
- 독립 리뷰 결과(결과 검토일 때: 결함 N건 가운데 수정 M건, 반박 K건). 코드 스테이지는 결과 검토 전에 `waypoint:review-gate`의 「코드 스테이지의 리뷰어 서브에이전트」를 돌린다.
- 근거 문서 링크

검토가 끝나면 다음 검토 때 새로 쓴다. 지난 검토의 내용은 「승인 결과」와 「진행 기록」에 남는다.

## 승인 결과 기록

게이트 질문(미해결 질문, 체크리스트)에 대한 사람의 답은 대개 채팅으로 온다. `AI Proposal`은 AI 전용이지만 *제안 당시의 기록*이므로
사후에 고쳐 쓰지 않는다. 대신 AI가 검토 게이트 아래 `### 승인 결과`의 `#### 계획 승인 (날짜, 결정자)`·`#### 결과 승인 (날짜, 결정자)` 표에 질문별 답을 기록한다.

- 코드 스테이지는 계획 승인과 결과 승인을 따로 적는다. 설계 스테이지는 계획 승인이 곧 결과 승인이므로 계획 승인만 쓴다. 승인을 기록하면 STATUS의 그 줄도 고친다(「STATUS 표」).
- 답이 AI 기본안과 다르면 "기본안과 다름 — §N의 값은 이 답으로 대체한다"처럼 **어느 절을 무효화하는지** 명시한다.
  이후 스테이지는 `AI Proposal`보다 `승인 결과`를 우선해서 읽는다.
- 같은 내용을 `DECISIONS.md`에도 항목으로 남긴다(승인 결과 = 스테이지 내 요약, DECISIONS = 근거와 탈락 대안).
  중재자가 시작한 작업 세션은 `waypoint:decisions`의 「중재자를 쓰는 동안」을 따른다.
- 승인 *이후* 다른 스테이지에서 계약을 확장·변경해야 하면, 원래 스테이지를 다시 열지 말고 변경하는 스테이지에
  "N-M 계약 확장"으로 적고 DECISIONS에 기록한다. 원래 스테이지에는 한 줄 링크만 덧붙인다.

## 진행 기록

- **frontmatter:** 스테이지 문서는 `status:`와 `updated:`를 두지 않고 `id:`를 둔다. `id:`의 값은 STATUS 표의 ID와 같다. `id:`는 스테이지 문서에만 넣고, Build Spec 인덱스처럼 스테이지 문서가 아닌 문서에는 넣지 않는다.
- **시작한 스테이지에는 반드시 스테이지 문서가 하나 있다.** `PENDING`이나 `DEFERRED`인 스테이지는 아직 문서가 없어도 된다.
- **「진행 기록」 절:** 스테이지 문서 맨 끝에 둔다. 아래쪽에 한 줄씩 덧붙이고, 그 스테이지의 작업 브랜치에서 커밋한다.
  - 체크포인트 커밋마다: `- YYYY-MM-DD <무엇을 했나> (<커밋 해시 앞 7자>) / 다음: <다음 할 일>`. 묶음, 차수, 중간 PR 머지 같은 하위 진행도 여기에 쓴다.
  - 작업을 막지 않는 질문을 추천안대로 진행했을 때: `- YYYY-MM-DD 가정: <질문> → <택한 안>`
  - 중재자가 문서를 근거로 대신 답했을 때: `- YYYY-MM-DD 질문: <질문> → 중재자 답: <답> (근거: <문서 위치>)`
- **체크리스트:** 계획을 쓸 때 계획에서 나온 하위 작업으로 채우고, 끝난 항목에 표시한다.
- **스테이지 이슈 본문:** 보드를 쓰는 레포(CLAUDE.md waypoint 블록에 `- 보드:` 줄이 있는 레포)에서는 스테이지마다 이슈가 하나 있다. 체크포인트마다 같은 체크리스트와 최근 진행 몇 줄을 이슈 본문의 `## 체크리스트`와 `## 최근 진행` 아래에 반영한다(`gh issue edit <번호> --body-file <파일>`). 이슈 본문은 스테이지 문서를 따라가는 사본이다.
  - 이슈 번호는 작업 세션 지시문의 「스테이지 이슈」에 있다. 없으면 `gh issue list --label waypoint --state all --limit 1000 --json number,title`에서 제목이 `[<ID>] `로 시작하는 이슈를 찾는다.
  - 이슈의 제목, 라벨, 열림·닫힘과 Project 필드는 보드 동기화만 고친다(`waypoint:git`의 「보드 동기화」). 세션은 이슈 본문만 고친다.
- **PR 본문:** 보드를 쓰는 레포에서는 `Refs #<이슈 번호>`와 짧은 설명만 둔다. `Closes`나 `Fixes`는 쓰지 않는다. 이슈는 STATUS의 줄이 `MERGED`가 될 때 동기화가 닫는다. 보드가 없는 레포에서는 체크포인트마다 같은 체크리스트와 최근 진행 몇 줄을 `gh pr edit`로 PR 본문에 반영한다.

## 외부 사실 표기

라이브러리 버전, SDK 요구사항, 스토어·광고 정책, 가격처럼 시간이 지나면 바뀌는 사실은 다음을 함께 적는다.

- **조회일**, **출처 URL**, **확인 수준**(`공식 확인` / `2차 자료` / `추론`)
- 공식 문서 조회 도구(예: Context7)를 쓸 수 없으면 웹 검색·공식 페이지로 대체하고, 그 사실을 적는다.
- `2차 자료`·`추론`인 사실에 의존하는 결정은 "재확인 시점"(예: 3-1 착수 전)을 함께 적는다.

## 문서 깊이 — 린 기본 + 적응형 깊이

스테이지 문서는 **기본은 경량(간결)**하게 쓴다. "문서가 일에 맞춘다" — 복잡도에 깊이를 맞춘다.

- **단순 스테이지**: 목적·입력·체크리스트·간단한 AI 제안으로 짧게.
- **복잡·고위험 스테이지**: AI 제안에 다음을 추가한다.
  - **컴포넌트/모듈 분해**
  - **NFR · 성능 목표**
  - **테스트·검증 계획** (순수 로직은 자동화 테스트로 검증, 시각/수동은 명시)

> 균일하게 얇으면 복잡 단계의 설계·근거가 사라진다. 반대로 모든 단계를 무겁게 쓰면 의식(ceremony)이 되어
> 속도를 깎는다. 깊이는 단계별로 판단한다.
