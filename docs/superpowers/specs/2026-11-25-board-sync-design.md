## 1. 배경과 목적

2단계에서 오너는 보기용 보드를 Notion이 아니라 GitHub Projects로 정했다. 칸반이 보기 편하고, GitHub가 칸반을 지원하면 GitHub만 쓰겠다는 조건이었다(2단계 4.1절). 그 뒤 다음이 정해졌다.

- STATUS 표의 한 줄이 보드의 카드 한 장이다. 상태 값 6개가 보드의 열 6개에 1:1로 대응한다. 카드를 찾는 열쇠는 「레포 + ID」다(2단계 5.1·5.2절).
- 보드는 STATUS를 한 방향으로만 따라간다. 보드에서 사람이 바꾼 값은 다음 동기화 때 STATUS 값으로 덮어쓴다(2단계 6절).
- 카드의 상태는 중재자가 작업 세션의 보고를 받아 STATUS로 고친다. 작업 세션과 중재자는 보드를 직접 고치지 않는다(3단계 4.6절, 6절).
- 오너가 카드를 열면 체크리스트의 진척과 최근 진행이 보여야 한다. 오너는 각 작업이 어떻게 진행되었고 어떤 내용의 작업을 했는지 세부적으로 확인하고 싶어 한다(3단계 4.6절, 5.9절).

이번 단계에서 오너가 밝힌 구상은 다음과 같다(오너, 2026-11-25).

- 각 레포가 자기 Project를 따로 관리한다.
- 나중에 waypoint 레포에서 그 Project들의 데이터를 가져와 통합해서 보여 준다. 통합 보기는 이번 단계에서 만들지 않는다.

이 단계의 목적은 다음과 같다.

- 레포마다 GitHub Project 보드를 두고, STATUS가 바뀌면 보드가 자동으로 따라오게 한다.
- 카드를 열면 그 스테이지의 세부 진행이 바로 보이게 한다.
- 이 일을 사람의 지시에 기대지 않고 기계적으로 일어나게 하고, 실패하면 드러나게 한다.

## 2. 목표, 비목표, 실패 조건

### 목표
- 레포마다 Project 하나를 두고, 상태 6개를 열로 하는 보드 보기를 갖춘다.
- STATUS의 줄마다 스테이지 이슈를 하나 두고, 그 이슈를 카드로 쓴다.
- STATUS가 바뀐 push 때마다 보드가 STATUS를 따라오게 한다.
- 작업 세션이 세부 진행을 스테이지 이슈 본문에 직접 쓰게 한다.
- 동기화가 실패하면 다음 세션 시작 때 드러나게 한다.
- 처음 적용하는 절차와, 나중에 통합 보기를 더할 수 있는 자리를 정한다.

### 비목표
- 레포별 보드를 통합해 보여 주는 일(다음 단계).
- 보드에서 STATUS로 거꾸로 반영하는 일. 보드는 보기용이다.
- 4단계를 처음 적용하는 시점에 이미 MERGED인 옛 스테이지의 이슈를 만드는 일.
- 이슈 댓글을 오너와 세션 사이의 소통 경로로 쓰는 일.
- GitHub Actions로 동기화하는 일.
- 2단계의 STATUS 형식을 바꾸는 일.

### 실패 조건 (기술적으로 돌아가도 실패로 보는 경우)
- **동기화가 성공했는데 보드가 STATUS와 다르다.**
- **동기화 때문에 push가 막히거나, push가 눈에 띄게 느려진다.**
- **한 스테이지에 이슈가 두 개 생긴다.**
- **동기화가 이슈 본문을 다시 써서 작업 세션이 적은 세부 진행이 사라진다.**
- **보드를 맞추려고 사람이 손으로 카드를 고쳐야 한다.**
- **레포에 비밀 토큰을 둔다.**
- **동기화가 실패했는데 아무도 모른다.**

## 3. 제약

- **레포의 현황(2026-11-25 확인):**
  - 다섯 레포 모두 PR은 쓰지만 이슈는 하나도 없다(shadow PR 1개, tokens-are-running-out 14개, duty 21개, app-factory 24개, forin 38개).
  - shadow, tokens-are-running-out, duty, forin은 public이고 app-factory만 private이다. 모두 이슈 기능은 켜져 있다.
  - `.githooks/`에는 shadow와 app-factory에만 `commit-msg`가 있고, `pre-push`는 어느 레포에도 없다. tokens-are-running-out은 아직 `docs/dlc/.githooks`를 `core.hooksPath`로 쓰고, duty와 forin은 `core.hooksPath`가 비어 있다(1단계 절차 M에서 바뀐다).
  - `gh` 2.91.0과 `jq`가 설치되어 있다. `gh` 토큰의 권한은 `gist`, `read:org`, `repo`이고 `project`가 없다.
- **GitHub Projects(2026-11-25 조회, 공식 확인):**
  - Project는 레포가 아니라 사용자나 조직에 속한다. 같은 사용자가 소유한 레포에 Project를 연결하면 그 레포의 Projects 탭에 표시된다. 출처: https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/adding-your-project-to-a-repository
  - 이슈와 PR은 여러 Project에 함께 넣을 수 있고, 초안 카드는 한 Project에만 속한다. Project 필드 값은 Project마다 따로 저장된다. 한 Project의 필드는 시스템 필드를 포함해 50개까지다. 출처: https://docs.github.com/en/enterprise-cloud@latest/issues/planning-and-tracking-with-projects/understanding-fields/about-issue-fields, https://docs.github.com/en/graphql/reference/projects
  - Project를 복사하면 보기, 사용자 정의 필드, 자동화, 인사이트가 복사된다. 자동 추가(auto-add) 자동화와 항목, 협업자, 레포 연결은 복사되지 않는다. 출처: https://docs.github.com/en/issues/planning-and-tracking-with-projects/creating-projects/copying-an-existing-project
  - Project를 만들면 「이슈나 PR이 닫히면 Status를 Done으로」와 「PR이 머지되면 Status를 Done으로」 두 자동화가 기본으로 켜진다. 출처: https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations
  - 자동 추가 자동화는 요금제에 따라 개수가 제한되고(Free 1개, Pro·Team 5개), 하나가 레포 하나를 대상으로 하며, 켰을 때 이미 있는 항목은 넣지 않는다. 출처: https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/adding-items-automatically
  - GitHub Actions의 `GITHUB_TOKEN`은 Project에 접근하지 못한다. 사용자 계정의 Project에는 `project`와 `repo` 권한의 classic 개인 토큰을 쓰라고 안내한다. fine-grained 토큰은 사용자 계정 소유 Project를 지원하지 않는다. 출처: https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions, https://docs.github.com/en/enterprise-cloud@latest/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens
  - Project에서 이슈를 열면 사이드 패널이 레포의 이슈 화면처럼 본문과 타임라인 전체를 보여 준다(2024-01-18부터). 출처: https://github.blog/changelog/2024-01-18-github-issues-projects-project-status-updates-issues-side-panel/
  - `gh project`에는 `copy`, `link`, `field-create`, `field-list`, `item-add`, `item-edit`, `item-list`가 있다. `item-edit`로 필드 값을 바꾸려면 Project, 항목, 필드, 선택지의 ID가 필요하다. 출처: https://cli.github.com/manual/gh_project_item-edit
- **2단계 설계:**
  - STATUS 형식(표 하나와 「오너 할 일」 절)과 pre-commit 형식 검사(`status-check`). 2단계 5.5절은 4단계의 동기화도 동기화 전에 같은 검사를 통과해야 한다고 정했다.
  - STATUS와 DECISIONS는 메인 체크아웃의 기본 브랜치에서만 커밋된다(검사 1).
  - 레포에 복사된 훅 사본은 둘째 줄의 버전 표시로 낡았는지 확인하고, `session-context.sh`가 경고한다(5.5절).
  - SessionStart 훅(`session-context.sh`)은 셸 내장 명령만 쓴다(PATH가 비어 있을 수 있음).
- **3단계 설계:** 작업 세션은 세부 진행을 체크포인트마다 스테이지 문서(원본)와 자기 PR 본문에 쓰기로 했다(5.9절). 이 단계에서 PR 본문을 스테이지 이슈 본문으로 바꾼다(5.11절).
- **커밋 규칙:** 공동작업 트레일러를 넣지 않는다. 커밋 메시지는 conventional commit 한 줄로 쓰고, 커밋 직후 push한다.

## 4. 접근 방식

오너와 함께 다음을 차례로 골랐다.

### 4.1 카드: 스테이지마다 레포 이슈

| 방식 | 판정 |
|---|---|
| **A. 스테이지마다 레포 이슈를 만들어 카드로 쓴다** | **채택.** 작업 세션이 세부 진행을 이슈 본문에 직접 쓰므로, 카드를 열면 바로 보이고 동기화를 기다리지 않는다. 동기화는 STATUS가 바뀔 때만 돌면 되므로 단순하다. public 레포 네 곳에 이슈가 공개로 생기지만, STATUS와 PR이 이미 공개라 새로 드러나는 내용은 거의 없다. 이슈와 PR이 번호를 나눠 쓴다. |
| B. Project 안에만 있는 초안 카드 | 탈락. 레포에 이슈가 생기지 않지만, 세부 진행이 PR 본문에 있으므로 동기화가 PR 본문을 카드에 복사해야 한다. PR 본문은 STATUS와 무관하게 바뀌므로 주기 실행(GitHub Actions와 classic 토큰)이 필요하고, 카드의 세부 진행은 실행 간격만큼 늦는다. |

### 4.2 Project의 범위: 레포마다 하나, 통합은 나중

설계자는 처음에 다섯 레포의 카드를 Project 하나에 모으고 레포는 탭으로 나누는 안을 냈다. 오너의 구상은 레포마다 Project를 두고 통합은 나중에 waypoint에서 하는 것이었다.

| 방식 | 판정 |
|---|---|
| **A. 레포마다 Project, 통합은 다음 단계** | **채택(오너 구상).** 각 레포의 Projects 탭에 그 레포의 보드가 있다. 이슈는 여러 Project에 넣을 수 있으므로(3절), 나중에 통합 Project를 더해도 같은 이슈를 다시 쓴다. |
| B. 처음부터 Project 하나에 모든 레포 | 탈락. 오너의 구상과 다르다. |

### 4.3 동기화를 실행하는 곳: push 훅

| 방식 | 판정 |
|---|---|
| **A. 레포의 pre-push 훅** | **채택.** STATUS를 push하면 중재자 세션이든 중재자 없는 세션이든 git이 기계적으로 동기화를 실행한다. 오너의 `gh` 인증을 쓰므로 레포에 비밀 토큰이 없다. GitHub 웹 화면에서 STATUS를 직접 고치면 다음 로컬 push까지 반영되지 않지만, 그런 수정은 드물고 2단계도 권하지 않는다. |
| B. 중재자가 STATUS를 push한 뒤 직접 실행 | 탈락. 지시문에 기대므로 빠뜨리기 쉽고, 중재자 없이 쓰는 세션에서는 더 그렇다. 2단계가 줄이려던 「지시로만 지키는 규칙」이다. |
| C. 각 레포의 GitHub Actions | 탈락. 웹 편집까지 반영되지만, classic 토큰(모든 레포에 대한 `repo` 권한 포함)을 다섯 레포에 비밀값으로 넣고 만료 때마다 갱신해야 하며, 레포마다 워크플로 파일이 늘어난다. |

## 5. 설계

### 5.1 Project 구성

- 레포마다 Project를 하나 둔다. 이름은 `<레포> 보드`(예: `forin 보드`)이고, 비공개로 만든 뒤 그 레포에 연결한다.
- **템플릿 Project:** 필드, 보기, 자동화를 갖춘 템플릿 Project(`waypoint 보드 템플릿`)를 하나 만들어 둔다. 레포별 Project는 템플릿을 복사해 만든다(`gh project copy`). 복사하면 보기, 필드, 자동화가 옮겨진다. 자동 추가 자동화는 복사되지 않지만, 이 설계는 자동 추가를 쓰지 않는다.
- **`보드:` 줄:** 레포 CLAUDE.md의 waypoint 블록에 `보드: <Project 주소>` 한 줄을 둔다(예: `보드: https://github.com/users/bingoring/projects/7`). 동기화는 이 줄에서 Project를 찾는다. 이 줄이 없는 레포는 보드를 쓰지 않는 레포로 본다.

### 5.2 필드

| 필드 | 종류 | 값 |
|---|---|---|
| Status | 단일 선택(기본 필드) | `대기`, `진행 중`, `검토 대기`, `승인`, `머지됨`, `보류`. 2단계 5.2절의 대응표대로 상태 값에서 정한다. |
| 줄기 | 단일 선택 | STATUS의 「줄기」. 처음 나온 값이면 동기화가 선택지를 더한다. 빈 칸이면 비운다. |
| 지금 | 텍스트 | STATUS의 「지금」 |
| 기다림 | 텍스트 | STATUS의 「기다림」. 값이 `오너 할 일`이면 「오너 할 일」 절에서 `(막음: …)`에 그 ID가 든 줄의 내용을 `오너 할 일: <내용>`으로 적는다. 여러 줄이면 ` · `로 잇는다. |
| 단계 | 단일 선택 | ID의 앞자리(`1`, `2`, `R`, `3`) |
| ID | 텍스트 | 스테이지 ID. 동기화가 카드를 찾는 열쇠다. |

### 5.3 보기

- **보드 보기(기본):** 열은 Status, 가로 묶음은 줄기다. 카드에 「지금」과 「기다림」을 표시한다.

```
             대기      진행 중                    검토 대기
Yawn         [2-15]    [2-12] 구현: 갈래 B 3차    [2-14] 결과 검토: …
공 물리                [2-9]  계획: …
출시         [3-2]                                [3-1] 결과 검토: … (기다림: 오너 할 일: …)
```

- **표 보기:** 모든 필드를 열로 보여 준다.
- 보기는 템플릿에서 GitHub 화면으로 한 번 설정하고, 복사로 옮긴다(10절: 보기를 API로 만들 수 있는지는 확인하지 않았다).

### 5.4 자동화

- 기본으로 켜지는 두 자동화(닫히면 Done, PR이 머지되면 Done)는 끈다. Status를 쓰는 곳을 동기화 하나로 두기 위해서다.
- 보관 자동화를 켜서 닫힌 지 14일이 지난 카드를 보관한다. 「머지됨」 열이 끝없이 길어지지 않게 하기 위해서다. 보관한 카드는 Project의 보관함에서 다시 볼 수 있다.
- 자동 추가 자동화는 쓰지 않는다. 이슈는 동기화가 Project에 넣는다.

### 5.5 스테이지 이슈

- **제목:** `[<ID>] <스테이지 이름>`(예: `[2-9] 상황 학습 4단계`). 스테이지 이름의 `⚠️`, `🔍` 표시도 그대로 옮긴다.
- **라벨:** `waypoint`. 동기화가 라벨이 없으면 만든다.
- **본문:** 처음 만들 때 본문 틀을 넣는다. 틀은 안내 한 줄(「이 이슈는 waypoint STATUS에서 만들어졌다. 상태는 STATUS가 정한다」)과 `## 체크리스트`, `## 최근 진행` 절로 된다. 레포의 훅 사본은 플러그인 경로를 모르므로(5.9절), 틀은 별도 파일이 아니라 `board-sync.sh` 안에 둔다. 그 뒤로는 작업 세션이 본문을 고치고, 동기화는 본문을 다시 쓰지 않는다.
- **열림과 닫힘:** STATUS가 `MERGED`이면 닫는다(완료). 그 밖의 상태는 열어 둔다. `DEFERRED`도 열어 둔다. 누가 이슈를 손으로 닫았는데 STATUS가 `MERGED`가 아니면, 다음 동기화가 다시 연다.
- **PR과의 연결:** 작업 세션은 PR 본문에 `Refs #<이슈 번호>`를 적는다. 그러면 이슈 타임라인에 그 PR이 나타난다. `Closes`나 `Fixes`는 쓰지 않는다. PR이 여러 개인 스테이지에서 첫 PR이 머지될 때 이슈가 닫히기 때문이다. 이슈를 열고 닫는 일은 동기화만 한다.
- **이슈 댓글:** 오너와 세션 사이의 소통 경로가 아니다. 세션은 이슈 댓글을 읽지 않는다. 오너의 지시는 3단계대로 중재자에게 한다.

### 5.6 동기화를 실행하는 시점

- 레포의 `.githooks/pre-push`가 git이 넘겨주는 push 대상 목록(로컬 ref, 로컬 커밋, 원격 ref, 원격 커밋)을 읽는다. 원격 ref가 기본 브랜치이고, 보내는 커밋 범위에서 `docs/waypoint/STATUS.md`가 바뀌었으면 `.githooks/board-sync.sh`를 실행한다.
- 동기화는 push와 분리된 백그라운드 프로세스로 실행한다. push는 동기화를 기다리지 않는다.
- 동기화는 push하는 커밋의 STATUS(`git show <로컬 커밋>:docs/waypoint/STATUS.md`)를 읽는다. 그래서 push가 거절되면 보드에는 아직 원격에 없는 STATUS가 반영되어 있다. 다음 push의 동기화가 바로잡는다.
- `.githooks/board-sync.sh`를 직접 실행하면 기본 브랜치의 현재 STATUS로 보드 전체를 다시 맞춘다. 처음 적용할 때와 실패를 고친 뒤에 쓴다.
- 결과는 메인 체크아웃의 `.git/waypoint/`에 로그(`board-sync.log`)와 상태 파일(`board-sync.status`)로 남긴다.
- **겹쳐 실행하지 않는다.** push가 잇달아 일어나 동기화가 두 번 겹치면 같은 스테이지의 이슈가 두 개 생길 수 있다(2절 실패 조건). 그래서 동기화는 `.git/waypoint/` 아래의 잠금(예: `mkdir`로 만드는 잠금 디렉터리)을 잡고 실행한다.
  - 잠금 안에는 잡은 프로세스의 PID와 시작 시각을 적는다.
  - 잠금을 잡지 못하면 「다시 실행 필요」 표시를 남긴다. 실행 중이던 동기화는 끝날 때 그 표시를 보고 한 번 더 실행한다. 이 두 번째 실행은 그 시점의 로컬 기본 브랜치 끝 커밋의 STATUS를 읽는다. STATUS는 메인 체크아웃의 기본 브랜치에서만 커밋되므로 이것이 가장 최근 STATUS다.
  - 잠금을 잡은 프로세스가 살아 있지 않으면(`kill -0`으로 PID 확인) 오래된 잠금으로 보고 지운 뒤 다시 잡는다.
  - 잠금이 살아 있는 프로세스의 것인데 10분보다 오래되었으면, 지우지 않고 「잠금이 오래 풀리지 않음」을 실패로 기록한다. 멈춘 동기화가 잠금을 쥐고 있는데 상태 파일이 성공으로 남아 실패가 드러나지 않는 일을 막기 위해서다.
- **직전 실패를 push 출력에 알린다.** pre-push 훅은 동기화를 띄우기 전에 상태 파일을 읽어, 직전 동기화가 실패했으면 표준 오류에 `waypoint: 직전 보드 동기화 실패(<시각>): <이유>` 한 줄을 출력한다. push를 실행한 세션은 이 출력을 바로 본다. 중재자는 compact 없이 오래 이어지므로, 세션 시작 요약(5.8절)만으로는 실패를 늦게 알 수 있기 때문이다.

### 5.7 동기화의 동작: 매번 전체를 맞춘다

1. STATUS를 2단계의 `status-check`로 검사한다. 통과하지 못하면 동기화하지 않고 실패로 기록한다. 동기화는 git index가 아니라 push하는 커밋의 STATUS 내용을 검사하므로, STATUS 내용만으로 하는 검사(2단계 5.5절 검사 2의 1~5번, 7번, 9번, 10번)만 실행한다. 다른 파일을 함께 보는 6번(MERGED 줄의 문서)과 8번(`id:` 문서마다 줄)은 커밋할 때 pre-commit이 이미 확인했다. 그래서 `status-check`는 「내용만 검사」하는 방식으로도 부를 수 있어야 한다(5.13절).
2. CLAUDE.md의 `보드:` 줄에서 Project 주소를 읽는다. 없으면 아무것도 하지 않고 끝낸다(실패가 아니다).
3. Project의 필드와 선택지의 ID, 항목 목록(ID 필드 값과 이슈 번호)을 읽는다.
4. STATUS의 줄마다:
   - **카드가 없고 상태가 `MERGED`가 아니면:** 먼저 `waypoint` 라벨과 제목의 `[<ID>]`로 이슈를 찾는다. 있으면 그 이슈를 Project에 넣는다. 없으면 이슈를 만들어(제목, 라벨, 본문 틀) Project에 넣는다. 그다음 ID 필드를 적는다. 이슈를 먼저 찾는 이유는, 이슈를 만든 뒤 Project에 넣기 전에 실패했을 때 다음 실행이 이슈를 하나 더 만들지 않게 하기 위해서다.
   - **카드가 없고 상태가 `MERGED`이면:** 만들지 않는다. 처음 적용할 때 이미 끝나 있던 스테이지가 여기에 해당한다. 시작된 스테이지는 대개 `MERGED`가 되기 전에 카드가 생긴다. 다만 그 스테이지가 진행되는 동안 동기화가 줄곧 실패했거나, `MERGED`까지 가는 여러 커밋을 한 번에 push하면 카드 없이 끝날 수 있다. 이 빈틈은 받아들인다. 끝난 스테이지의 기록은 STATUS와 스테이지 문서에 남아 있다.
   - **카드가 있으면:** 제목, 열림·닫힘, Status, 줄기, 지금, 기다림, 단계를 STATUS와 비교해 다른 것만 고친다.
5. STATUS에 없는 ID의 카드는 지우지 않고 경고로 기록한다. ID는 지우거나 다시 쓰지 않으므로(2단계 5.1절) 정상이라면 생기지 않는다.
6. 보드에서 사람이 바꾼 값은 4번에서 STATUS 값으로 덮어쓴다.
7. `보드:` 줄에 주소가 여러 개면 2~6번을 Project마다 한다(5.12절). 이슈는 하나이고, Project마다 카드와 필드를 맞춘다.

### 5.8 실패 처리

- 동기화는 push를 막지 않는다. pre-push 훅은 동기화를 띄운 뒤 바로 0으로 끝난다.
- 실패하면 상태 파일에 시각, 실패한 단계, 이유 한 줄을 적는다. 성공하면 상태 파일을 성공으로 바꾼다.
- 실패는 두 곳에서 드러난다.
  - 다음 push의 출력: pre-push 훅이 직전 실패를 한 줄로 알린다(5.6절).
  - 세션 시작 요약: `session-context.sh`가 메인 체크아웃의 상태 파일을 `read`로 읽어, 실패 상태이면 요약에 `보드 동기화 실패(<시각>): <이유>` 한 줄을 붙인다. 셸 내장 명령만 쓰는 2단계 제약을 지킨다.
- 중재자(중재자가 없으면 그 세션)는 이 줄을 보면 원인을 고치고 `.githooks/board-sync.sh`를 직접 실행한다. 원인이 `gh` 토큰의 `project` 권한이면 오너 할 일로 안내한다.
- 동기화는 매번 전체를 맞추므로, 다음에 성공하면 밀린 변경이 함께 반영된다.

### 5.9 실행 환경

- 동기화는 오너의 `gh` 인증을 쓴다. 레포에 비밀 토큰을 두지 않는다. `gh` 토큰에 `project` 권한이 필요하다(오너가 `gh auth refresh -s project`를 한 번 실행).
- 훅은 git을 실행한 프로세스의 환경에서 돈다. PATH에서 `gh`나 `jq`를 찾지 못하면 실패로 기록하고 끝낸다.
- git 훅은 플러그인의 설치 경로를 모른다. 그래서 `pre-push`와 `board-sync.sh`도 2단계의 pre-commit처럼 레포의 `.githooks/`에 사본으로 둔다. 원본은 `plugin/githooks/pre-push`와 `plugin/scripts/board-sync.sh`다.
- 사본의 둘째 줄에 `# waypoint-hook-version: <번호>`를 둔다. `session-context.sh`의 낡은 사본 경고(2단계 5.5절)에 이 두 파일을 더한다.
- `board-sync.sh`가 쓰는 `status-check`는 레포의 사본(2단계에서 pre-commit 사본에 넣는 검사 본문)을 쓴다. 구현자는 두 훅이 같은 검사 본문을 쓰도록 한다(9절).
- **백그라운드 실행이 안 될 때 물러설 자리:** 분리된 백그라운드 프로세스에서 `gh`를 찾지 못하거나 키체인의 인증을 쓰지 못할 수 있다(10절). 이 경우 pre-push 훅이 동기화를 백그라운드가 아니라 push와 같은 프로세스에서 바로 실행하도록 바꾼다. 그러면 동기화는 push를 실행한 세션과 같은 환경(PATH, 인증)에서 돌고, 세션에서 `gh`를 쓰는 것과 똑같이 동작한다. 대신 push가 동기화 시간(달라진 줄만 고치므로 보통 몇 초)만큼 길어진다. 레포에 토큰을 두거나 별도 상주 프로세스를 두는 방법은 쓰지 않는다. 어느 쪽으로 갈지는 구현의 첫 단계에서 정한다(5.14절).
- 이미 `pre-push`가 있는 레포에서는 기존 훅을 지우지 않고, 그 끝에서 waypoint의 처리를 부르도록 합친다. 2026-11-25 기준으로 그런 레포는 없다.

### 5.10 처음 적용

**한 번만 하는 일:**
1. 오너가 `gh auth refresh -s project`를 실행한다. 브라우저 로그인이 필요해서 오너가 직접 한다.
2. 템플릿 Project를 만든다. 필드와 선택지는 `plugin/scripts/board-setup.sh`가 만든다. 보기 설정과 자동화 설정(기본 두 자동화 끄기, 14일 보관 켜기)은 GitHub 화면에서만 할 수 있으므로 오너 할 일로 둔다. 오너가 원하면 AI가 앱의 브라우저로 대신 설정한다.

**레포마다 하는 일:**
1. 템플릿을 복사해 `<레포> 보드`를 만든다.
2. 그 레포에 연결한다(`gh project link`).
3. CLAUDE.md의 waypoint 블록에 `보드:` 줄을 적는다.
4. `pre-push`와 `board-sync.sh` 사본을 `.githooks/`에 복사한다.
5. `board-sync.sh`를 직접 실행한다. `MERGED`가 아닌 줄마다 이슈가 만들어진다.

- 1~4는 `board-setup.sh`가 한다. CLAUDE.md와 훅 사본은 메인 체크아웃의 기본 브랜치에 커밋한다.
- 레포마다 하는 일은 2단계의 STATUS 변환이 끝난 레포에서만 한다. 동기화가 새 형식의 STATUS를 읽기 때문이다. shadow부터 적용한다.
- 아직 1단계 절차 M을 거치지 않은 레포(tokens-are-running-out, duty, app-factory, forin)는 절차 M의 STATUS 변환 단계(M6a, 2단계 5.8절) 뒤에 이 일을 하는 단계를 더한다.
- 새 레포에서 `waypoint:init`을 실행하면 레포마다 하는 일을 함께 한다.

### 5.11 3단계에서 바뀌는 것

- **세부 진행을 쓰는 곳:** 작업 세션은 체크포인트마다 체크리스트와 최근 진행을 PR 본문 대신 스테이지 이슈 본문에 쓴다(`gh issue edit`). 원본은 지금처럼 스테이지 문서의 체크리스트와 「진행 기록」이다. PR 본문에는 `Refs #<이슈 번호>`와 짧은 설명만 둔다.
- **이슈 번호:** 중재자는 작업 세션을 시작할 때 지시문에 이슈 번호를 적는다. 번호는 Project의 ID 필드로 찾는다. 스테이지 줄이 `PENDING`으로 STATUS에 들어와 push되는 순간 동기화가 이슈를 만들므로, 작업 세션을 시작할 때는 이슈가 이미 있다. 동기화가 실패해 이슈가 아직 없으면 중재자가 동기화를 직접 실행한 뒤 번호를 적는다. 중재자 없이 쓰는 세션은 `waypoint` 라벨과 제목의 `[<ID>]`로 이슈를 찾는다.
- **작업 세션이 고치는 범위:** 이슈 본문만 고친다. 제목, 라벨, 열림·닫힘, Project 필드는 동기화만 고친다.
- **보드 상태가 바뀌는 경로:** 3단계 그대로다. 작업 세션 → 중재자 → STATUS → pre-push 훅 → 보드. 중재자가 `MERGED`로 바꾼 STATUS를 push하면 동기화가 이슈를 닫는다.
- 3단계 설계 문서는 그때의 기록이므로 고치지 않고, 이 변경은 이 문서에 남긴다.

### 5.12 통합 보기를 위한 준비

- `보드:` 줄에는 Project 주소를 여러 개 적을 수 있다(공백으로 구분). 동기화는 적힌 모든 Project에 같은 이슈를 넣고 Project마다 필드를 맞춘다(5.7절 7번).
- 4단계에서는 레포 Project의 주소 하나만 적는다.
- 다음 단계에서 통합 Project를 만들면 각 레포의 `보드:` 줄에 그 주소를 더한다. 통합 화면을 따로 만드는 경우에도, 「레포 + ID」로 찾는 스테이지 이슈가 곧 카드라는 구조는 그대로 다시 쓴다.

### 5.13 바뀌는 규칙과 파일

| 파일 | 바뀌는 내용 |
|---|---|
| `plugin/githooks/pre-push` | 새 파일. 기본 브랜치로 가는 push에서 STATUS가 바뀌었으면 동기화를 백그라운드로 띄우고 바로 끝난다(5.6절). |
| `plugin/scripts/board-sync.sh` | 새 파일. 동기화의 원본(5.7·5.8절). 레포에는 `.githooks/board-sync.sh` 사본을 둔다. |
| `plugin/scripts/board-setup.sh` | 새 파일. 템플릿의 필드와 선택지 만들기, 레포별 Project 복사와 연결, `보드:` 줄과 훅 사본 넣기(5.10절). |
| `plugin/scripts/status-check.sh` | 2단계의 새 파일. 커밋 index 대신 넘겨받은 STATUS 내용만 검사하는 방식을 더한다(5.7절 1번). 2단계 구현이 이미 그렇게 만들었으면 바꾸지 않는다. |

| `plugin/skills/worker`, `plugin/skills/mediator` | 3단계의 새 스킬. 이슈 본문에 세부 진행 쓰기, PR의 `Refs`, 지시문의 이슈 번호, 동기화 실패 처리(5.11절). |

이 변경은 1~3단계처럼 waypoint에 PR로 올리고 오너가 머지한다.

### 5.14 구현 순서와 범위

- **순서:** 2단계 → 3단계 → 4단계로 구현한다. 4단계의 동기화 자체는 2단계의 STATUS 형식과 `status-check`만 있으면 동작하지만, 5.11절의 변경이 3단계 스킬(`worker`, `mediator`)과 지시문 템플릿을 고치므로, 3단계가 먼저 있어야 4단계 구현 계획이 그 파일들을 한 번에 고칠 수 있다. 오너가 보드를 더 일찍 원하면 4단계를 3단계보다 먼저 구현할 수 있다. 그때는 4단계 구현 계획이 3단계 구현 계획에 5.11절을 넘겨야 한다.
- **구현의 첫 단계:** 스크립트를 다 쓰기 전에, 비공개 시험용 레포와 시험용 Project에서 다음을 먼저 확인한다.
  1. pre-push 훅이 띄운 분리된 백그라운드 프로세스가 `gh`와 `jq`를 찾고, 키체인에 저장된 `gh` 인증으로 Project와 이슈를 고칠 수 있는가. AI 세션이 `git push`를 실행하는 경우를 반드시 포함한다.
  2. 보관 자동화의 조건을 「닫힌 지 14일」로 줄 수 있는가(10절).
  3. 동기화가 실행 중에 「줄기」 단일 선택 필드에 새 선택지를 API로 더할 수 있는가. 더한 뒤에도 기존 카드의 줄기 값이 유지되는가.
  4. `board-setup.sh`가 기본 Status 필드의 선택지 이름을 API로 `대기`~`보류`로 바꿀 수 있는가.
  5. 템플릿을 복사한 Project에서 기본 자동화 두 개가 꺼진 채로 남고, 보기 설정(열, 가로 묶음, 카드에 보이는 필드)이 그대로 옮겨지는가.

  각 확인이 실패하면 다음으로 물러선다.
  - 1이 실패하면 5.9절의 물러설 자리(push와 같은 프로세스에서 실행)로 간다.
  - 3에서 선택지를 더할 때 기존 카드의 값이 지워지면, 동기화가 선택지를 먼저 맞춘 뒤 같은 실행 안에서 모든 카드의 줄기 값을 다시 적는다. 동기화는 매번 모든 카드를 STATUS와 비교하므로(5.7절) 이 순서만 지키면 되고, 사람이 카드를 고칠 필요는 없다. 새 선택지를 API로 더할 수 없으면 「줄기」를 텍스트 필드로 바꾸고 가로 묶음을 줄기 대신 단계로 한다. 이 경우 보드 모양이 바뀌므로 오너에게 알린다.
  - 4가 실패하면 템플릿을 만들 때 오너가 화면에서 선택지 이름을 바꾼다. 템플릿에서 한 번만 하면 복사로 옮겨진다.
  - 5가 실패하면 레포별 Project를 만들 때마다 화면에서 자동화와 보기를 맞춘다. 오너 할 일에 레포마다 한 번씩 더한다. 시험용 레포는 public 레포에 시험용 이슈가 공개로 남지 않게 하려고 쓴다. 시험용 레포를 만드는 일은 구현 때 오너의 승낙을 받는다.
- **오너가 먼저 할 일:** 시험을 시작하기 전에 오너가 `gh auth refresh -s project`를 실행한다. 머지 뒤가 아니라 구현을 시작할 때 필요하다.
- **끝의 기준:** waypoint PR이 머지되고, shadow에 보드를 적용해(5.10절) 첫 동기화가 성공하면 끝난다. 나머지 네 레포는 각자 절차 M을 거칠 때 적용한다.

## 6. 2·3단계와의 관계

- **2단계에서 그대로인 것:** STATUS 형식, 상태 값과 보드 열의 대응, 단방향 원칙, pre-commit 검사, 훅 사본과 버전 줄 방식.
- **2단계 6절에서 남겨 둔 결정:** 「카드를 레포의 이슈로 만들지, 프로젝트의 초안 카드로 만들지는 4단계에서 정한다」는 레포 이슈로 정했다(4.1절). 2단계 6절의 필드 목록(줄기, 지금, 기다림, 단계)과 PR 연결(링크 칸의 PR 번호)은 다음처럼 바뀐다. 필드에 ID를 더하고, PR은 링크 칸 대신 PR 본문의 `Refs`로 이슈에 연결한다. 링크 칸은 STATUS 안에서 그대로 쓴다.
- **2단계 10절의 미확인 사항:** 「사용자 계정 프로젝트에 private 레포(app-factory)의 항목을 넣었을 때의 표시 범위」는, Project를 레포마다 비공개로 두고 오너만 보므로 이 설계에 영향이 없다. 「github.com에 PR이 머지되면 Done으로 바꾸는 기본 자동화가 있는지」는 공식 문서에서 확인했고(3절), 이 설계는 그 자동화를 끈다(5.4절).
- **3단계에서 바뀌는 것:** 세부 진행을 PR 본문 대신 스테이지 이슈 본문에 쓴다(5.11절).
- **3단계에서 그대로인 것:** 카드 상태는 중재자가 STATUS로 고치고, 작업 세션과 중재자는 보드 필드를 직접 고치지 않는다.

## 7. 오너가 정한 것 (2026-11-25)

- 카드는 스테이지마다 레포 이슈로 만든다(4.1절).
- Project는 레포마다 두고, 통합해서 보는 화면은 나중에 waypoint 레포에서 만든다(4.2절).
- 동기화는 레포의 push 훅에서 실행한다(4.3절).
- 5.1~5.14절의 설계를 세 부분으로 나눠 검토하고 승인했다(Project와 카드, 동기화, 3단계 변경과 파일과 순서). 빌더 점검 뒤 바뀐 부분은 8절에 따로 적었다.

## 8. 설계자가 정한 것 (오너 확인 필요)

- Project 이름 `<레포> 보드`, 비공개, 레포에 연결(5.1절).
- 템플릿 Project를 복사하는 방식(5.1절).
- Project 주소를 CLAUDE.md의 `보드:` 줄에 두고, 여러 주소를 적을 수 있게 함(5.1절, 5.12절).
- 필드 구성. 2단계 6절의 필드에 ID를 더하고, 「기다림」이 `오너 할 일`이면 그 내용을 함께 적음(5.2절).
- 보드 보기(열은 Status, 가로 묶음은 줄기)와 표 보기(5.3절).
- 기본 자동화 두 개를 끄고, 닫힌 지 14일 뒤 보관(5.4절).
- 이슈 제목 형식, `waypoint` 라벨, 본문 틀, 동기화가 본문을 다시 쓰지 않음(5.5절).
- `MERGED`이면 이슈를 닫고 `DEFERRED`는 열어 둠. 손으로 닫힌 이슈는 다시 엶(5.5절).
- PR은 `Refs`로만 연결하고 `Closes`는 쓰지 않음(5.5절).
- 이슈 댓글을 소통 경로로 쓰지 않음(5.5절).
- pre-push의 실행 조건과 백그라운드 실행, push가 거절될 때의 차이를 다음 push로 바로잡음(5.6절).
- 매번 전체를 맞추는 동작, `MERGED` 줄에는 새 카드를 만들지 않음, 라벨과 제목으로 이슈를 먼저 찾아 중복을 막음, 카드를 지우지 않음(5.7절).
- 실패를 상태 파일에 남기고 세션 시작 요약에 한 줄로 드러냄(5.8절).
- 훅 사본과 버전 줄, `gh`와 `jq` 의존(5.9절).
- 처음 적용의 순서와 `board-setup.sh`, 보기와 자동화 설정을 오너 할 일로 둠(5.10절).
- 동기화를 겹쳐 실행하지 않는 잠금과 「다시 실행 필요」 표시(5.6절). 빌더 점검에서 잇단 push로 이슈가 중복될 수 있다는 점이 나와 더했다.
- 직전 실패를 다음 push 출력에 알림(5.6절, 5.8절). 빌더 점검에서 compact 없이 오래 이어지는 중재자는 세션 시작 요약을 늦게 본다는 점이 나와 더했다.
- 동기화는 STATUS 내용만으로 하는 검사만 실행하고, 다른 파일을 함께 보는 검사(6·8번)는 pre-commit에 맡김(5.7절).
- 본문 틀을 별도 파일이 아니라 `board-sync.sh` 안에 둠(5.5절). 설계 검토 때는 `plugin/templates/stage-issue-body.md`로 설명했지만, 레포의 훅 사본이 플러그인 경로를 모르므로 바꿨다.
- **백그라운드 실행이 안 되면 push와 같은 프로세스에서 실행(5.9절).** 이때 push가 몇 초 길어져 2절의 「push가 눈에 띄게 느려진다」에 가까워진다. 레포에 토큰을 두는 것보다 낫다고 판단했다.
- **구현 순서를 2단계 → 3단계 → 4단계로 정함(5.14절).** 설계 검토 때는 「3단계와 4단계는 어느 쪽을 먼저 해도 된다」고 설명했다. 빌더 점검에서 「나중에 하는 쪽이 반영한다」는 규칙이 빠지기 쉽다는 점이 나와 순서를 정했다. 오너가 보드를 더 일찍 원하면 바꿀 수 있다.
- 구현의 첫 단계에서 비공개 시험용 레포와 Project로 백그라운드 실행을 확인함. 시험용 레포를 만드는 일은 구현 때 오너의 승낙을 받음(5.14절).
- 끝의 기준은 waypoint PR 머지와 shadow 적용(5.14절).

## 9. 구현자에게 맡기는 것

- `gh` 명령과 GraphQL 가운데 무엇을 쓸지. 필드와 선택지 ID를 한 번에 읽어 호출 수를 줄이는 방법.
- 세션이 `board-setup.sh`를 실행하는 방법. 플러그인 경로는 Bash에서 보이지 않으므로(지금 스킬들의 안내), Read 도구로 읽어 레포 `.githooks/`에 사본을 둔 뒤 실행하거나, `waypoint:init` 스킬의 절차로 풀어 쓴다.
- pre-push에서 STATUS 변경을 판정하는 세부(원격 커밋이 0으로만 된 새 브랜치, 강제 push 등).
- 백그라운드 프로세스를 push와 분리하는 방법(예: `nohup`과 입출력 재지정). AI 세션이 `git push`를 실행할 때 그 프로세스를 기다리지 않게 한다.
- 로그 파일의 크기 관리.
- `board-sync.sh`와 pre-commit이 같은 `status-check` 본문을 쓰게 하는 방법(사본을 하나 더 둘지, pre-commit 사본에서 함수로 불러 쓸지).
- 본문 틀의 정확한 문구, 라벨 색.
- 보드 열 안의 카드 정렬(예: 이슈 번호 순).
- waypoint PR의 커밋 분할 방식. 이 경우에도 공동작업 트레일러는 넣지 않는다.

## 10. 미확인 사항

- **단일 선택 필드의 선택지를 API로 더하거나 이름을 바꿀 때 기존 카드의 값이 유지되는지, 복사한 Project에 자동화 설정과 보기 설정이 그대로 남는지**(미확인). 구현의 첫 단계에서 시험용 Project로 확인하고, 안 되면 5.14절의 물러설 자리로 간다.
- **Project의 보기를 API로 만들 수 있는지**(미확인). 이 설계는 템플릿의 보기를 화면에서 한 번 설정하고 복사로 옮기므로, API가 없어도 된다.
- **보관 자동화의 조건을 「닫힌 지 14일」로 정확히 줄 수 있는지**(미확인). 보관 자동화의 필터가 닫힌 시각이 아니라 마지막 수정 시각을 기준으로 할 수 있다. 구현 때 템플릿에서 확인하고, 안 되면 비슷한 조건을 쓴다.
- **Project 사이드 패널이 이슈 본문의 체크리스트 진척을 따로 보여 주는지**(미확인). 본문은 그대로 보이므로 체크리스트 자체는 보인다. 카드 위에 진척률을 보여 주는 일은 이 설계에 넣지 않았다.
- **GUI 앱에서 git push를 실행할 때 훅의 PATH에 `gh`와 `jq`가 있는지**(미확인). 없으면 실패로 기록되고 다음 push 출력과 세션 시작 요약에 드러나므로, 직접 실행해 바로잡을 수 있다. waypoint의 STATUS push는 대부분 AI 세션이 하므로 영향은 작다.
- **백그라운드로 분리한 동기화 프로세스가 `gh`를 찾고 macOS 키체인에 저장된 `gh` 인증을 쓸 수 있는지**(미확인). 구현의 첫 단계에서 시험용 레포로 확인하고, 안 되면 5.9절의 물러설 자리로 간다(5.14절).
- **pre-push 훅이 아예 실행되지 않는 경우**(예: `core.hooksPath`가 설정되지 않은 새 클론). 이때는 상태 파일도 남지 않아 실패가 드러나지 않는다. 지금은 2단계의 `git config core.hooksPath .githooks` 안내에 기댄다.
