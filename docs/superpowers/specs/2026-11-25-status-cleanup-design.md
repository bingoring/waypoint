# waypoint STATUS 정리 설계

- 작성일: 2026-11-25
- 상태: 오너 승인(2026-11-25)
- 범위: waypoint 고도화 4단계 중 2단계
- 앞 단계: [`2026-11-24-plugin-split-design.md`](2026-11-24-plugin-split-design.md)(1단계, 플러그인 전환)

## 1. 배경과 목적

STATUS.md는 원래 스테이지별 상태를 보여 주는 대시보드였다. 실사용에서 진행 일지로 변했고, 다음 문제가 생겼다.

- **세션 시작과 compact 때 비용이 크다.** forin의 STATUS는 1,415줄이다. 그 가운데 앞 1,300줄이 완료 배너이고, 상태 표는 1,316행부터 시작한다. 표의 셀에도 문단 길이의 글이 들어 있다. 그래서 1단계에서는 SessionStart 훅이 STATUS 내용을 주입하지 않기로 했다(1단계 설계 5.3절).
- **상태가 두 곳에 기록되고, 서로 어긋나 있다.** 스테이지 문서 frontmatter의 `status:`와 STATUS 표가 각각 상태를 적는다. 2026-11-25 기준으로 어긋난 예는 다음과 같다.
  - forin 1-3: 표는 `AI_PROPOSED`, 문서는 `HUMAN_APPROVED`
  - forin 2-6: 표는 「완료(2026-08-10)」, 문서는 `IN_PROGRESS`
  - forin 2-7: 표는 「체크리스트 전 항목 완료」, 문서는 `PENDING`
  - app-factory 2-7: 표는 `DEFERRED`, 문서는 `AI_PROPOSED`
  - app-factory 2-12·2-14: 표는 `IN_PROGRESS`, 문서는 `AI_PROPOSED`
  - app-factory 2-15: 문서는 있지만 표에 줄이 없다.
- **생애주기에 없는 값이 쓰인다.** `DEFERRED`, `APPROVED`, `IMPLEMENTED`, `READY`, 「완료(날짜)」 같은 글이 상태 칸에 들어 있다. duty의 3-7~3-13은 Build Spec의 상태 값(`IMPLEMENTED`, `READY`)을 스테이지 상태로 쓰고 있다. 지금 생애주기는 코드 스테이지의 「결과 확인」을 다루지 않기 때문이다.
- **머리말 날짜가 어긋난다.** forin 머리말의 `Last updated`는 2026-10-28이지만, 맨 위 배너의 날짜는 2026-11-24다.
- **STATUS 변경은 대부분 스테이지보다 작은 단위다.** waypoint 레포에서 프로젝트 문서를 바꾼 커밋 가운데 STATUS를 바꾼 커밋은 forin 505개 중 228개, app-factory 319개 중 187개다. forin의 최근 STATUS 커밋은 대부분 「OR 묶음 N 합침」이고, app-factory는 「Yawn 갈래 B N차 실험」이다. 둘 다 한 스테이지 안의 진행이다.
- **오너 작업이 배너에 섞여 있다.** app-factory의 「⏳ 오너 작업」(BigQuery 연결, 사업자등록 → D-U-N-S)이 완료 배너 사이에 있어서 눈에 띄지 않는다.
- **세션 시작 절차가 현실과 맞지 않는다.** `waypoint:start`는 「PENDING인 가장 앞 스테이지부터」 시작하라고 한다. 실제로는 app-factory처럼 여러 스테이지가 동시에 진행되고, 세션은 오너가 지정한 작업을 이어 간다.
- **1단계 9절에 긴장이 남아 있다.** STATUS는 기본 브랜치에 있고 스테이지 문서는 기능 브랜치에 있어서, 머지 전에는 STATUS의 문서 링크가 깨진다. 코드 없는 설계 스테이지의 문서를 어느 브랜치에 둘지도 정해지지 않았다.

이 단계의 목적은 다음과 같다.

- STATUS를 다시 대시보드로 만든다. 스테이지 하나가 한 줄이고, 그 줄은 「지금 무엇을 하고, 무엇을 기다리는지」만 담는다.
- 상태의 원본을 STATUS 한 곳으로 정하고, 형식을 커밋 시점에 기계적으로 검사한다.
- 4단계(GitHub Projects 보드로 단방향 동기화)가 그대로 읽을 수 있는 형식으로 만든다.
- 진행 기록은 STATUS 밖으로 옮기되, 기존 기록은 하나도 잃지 않는다.

### 전체 로드맵에서의 위치

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 프레임워크와 프로젝트 문서 분리, 플러그인 전환 | 완료(2026-11-25) |
| 2 | STATUS 정리 | 이 문서 |
| 3 | 중재자 세션과 작업 세션 구조(병렬, worktree) | 별도 설계 |
| 4 | md 원본에서 **GitHub Projects 보드와 이슈·PR**로 단방향 동기화 | 별도 설계 |

**로드맵 변경(오너, 2026-11-25):** 4단계의 보기용 보드는 Notion이 아니라 GitHub Projects로 한다. 오너의 조건은 「GitHub가 칸반을 지원하면 GitHub만 쓰고, 지원하지 않으면 Notion을 쓴다」였고, GitHub Projects가 보드 보기를 지원함을 확인했다(3절). 1단계 설계 문서는 그때의 기록이므로 고치지 않고, 이 문서에 변경을 남긴다.

## 2. 목표, 비목표, 실패 조건

### 목표
- STATUS.md를 「스테이지 한 줄 = 보드 카드 한 장」인 표로 바꾼다.
- 상태 값을 보드의 열과 1:1로 맞추고, 코드 스테이지의 결과 검토와 머지를 생애주기에 넣는다.
- 상태의 원본을 STATUS 한 곳으로 정한다. 스테이지 문서 frontmatter의 `status:`를 없앤다.
- 모든 스테이지를 작업 브랜치와 PR로 진행하고, STATUS가 처음부터 PR을 가리키게 한다.
- 메인 체크아웃은 늘 기본 브랜치에 두고, 스테이지 작업은 worktree에서 한다.
- 커밋 시점에 STATUS 형식과 커밋 위치를 검사하는 pre-commit 훅을 둔다.
- SessionStart 훅이 활성 스테이지만 짧게 주입한다.
- 기존 다섯 레포의 STATUS를 잃는 것 없이 새 형식으로 옮기는 절차를 정한다.

### 비목표
- 4단계의 동기화 스크립트와 3단계의 세션 구조를 구현하는 일.
- 진행 기록(배너)의 내용을 고치거나 요약하는 일. 배너는 그대로 옮기기만 한다.
- DECISIONS.md의 형식을 바꾸는 일.
- Build Spec의 상태 흐름(`DRAFT → QUESTIONS_OPEN → READY → IMPLEMENTED`)을 바꾸는 일.
- 회사 쪽 사본 정리.

### 실패 조건 (기술적으로 돌아가도 실패로 보는 경우)
- **이전 과정에서 배너 내용이 사라진다.** HISTORY.md에서 맨 위에 덧붙인 안내 줄을 뺀 내용이 옛 STATUS.md 전체와 글자 단위로 같아야 한다.
- **STATUS가 다시 길어진다.** 「지금」 칸이 일지처럼 쓰이거나, 표 밖에 배너가 다시 생기면 실패다.
- **상태가 다시 두 곳에 기록된다.** 스테이지 문서, Build Spec, STATUS가 같은 「스테이지 상태」를 따로 들고 있으면 실패다.
- **pre-commit 검사가 정상적인 커밋을 자주 막는다.** 오탐 때문에 `--no-verify`가 일상이 되면 검사가 없는 것과 같다.
- **waypoint를 쓰지 않는 레포에서 훅이 무언가를 출력하거나 커밋을 막는다.**

## 3. 제약

- **원본은 md다(오너, 2026-11-24).** Notion과 GitHub는 md에서 한 방향으로 갱신되는 보기용이다.
- **SessionStart 훅은 셸 내장 명령만 쓴다.** `session-context.sh`가 실행될 때 PATH가 비어 있을 수 있어서 `jq`, `python`, `awk`를 쓸 수 없다. 그래서 주입할 내용은 줄 단위로 읽을 수 있는 형식이어야 한다.
- **compact 뒤 재주입은 실측으로 확인되었다.** 1단계 PR([bingoring/waypoint#1](https://github.com/bingoring/waypoint/pull/1))에서 `/compact` 뒤 `SessionStart:compact` 훅이 같은 블록을 다시 주입하는 것을 세션 기록으로 확인했다.
- **문서 커밋 흐름(1단계 9절):** STATUS.md, DECISIONS.md, 핸드오프(`docs/waypoint/inputs/`)는 메인 체크아웃에서 기본 브랜치로 바로 커밋하고 push한다. 스테이지 문서, Build Spec, 리뷰 문서는 작업 브랜치에 실어 PR과 함께 머지한다.
- **동시 작업:** tokens-are-running-out, duty, app-factory, forin은 아직 waypoint의 `projects/` 아래에서 옛 형식으로 STATUS를 쓰고 있다. 이 레포들은 열린 PR이 정리된 뒤 1단계 절차 M으로 이전된다.
- **플러그인은 커밋을 따라간다.** `plugin.json`에 `version`이 없으므로, waypoint 기본 브랜치에 머지하는 순간 새 규칙이 모든 레포에 적용된다.
- **커밋 규칙:** 공동작업 트레일러를 넣지 않는다. 커밋 메시지는 conventional commit 한 줄로 쓰고, 커밋 직후 push한다.
- **GitHub Projects(2026-11-25 조회, 공식 확인):**
  - 보드 보기에서 단일 선택 필드의 값이 열이 되고, 다른 사용자 정의 필드로 가로 묶음을 만들 수 있다. 출처: https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/customizing-the-board-layout
  - 한 프로젝트에 여러 레포의 이슈와 PR을 담을 수 있다. 레포에 이슈를 만들지 않고 프로젝트 안에만 있는 초안 카드(draft issue)도 만들 수 있다. 출처: https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-items-in-your-project/adding-items-to-your-project
  - 단일 선택 필드는 선택지를 50개까지 가질 수 있다. 출처: https://docs.github.com/en/issues/planning-and-tracking-with-projects/understanding-fields/about-single-select-fields
  - `gh project item-edit`로 스크립트에서 필드 값을 바꿀 수 있다. 출처: https://cli.github.com/manual/gh_project_item-edit
  - 한 프로젝트의 항목 한도는 50,000개다. 출처: https://github.blog/changelog/2025-02-26-increased-items-in-github-projects-now-in-public-preview/
  - 2026-11-25 기준 오너의 `gh` 토큰에는 `project` 권한이 없다(`gh project list`가 `read:project` 권한 부족으로 실패). 4단계에서 `gh auth refresh -s project`를 한 번 실행해야 한다.
- **Anthropic의 진행 목록 사례(2026-11-25 조회, 공식 확인):** Anthropic은 장시간 에이전트용 하네스에서 기능 목록을 JSON으로 두고, 에이전트가 통과 여부 값만 바꾸게 했다. JSON을 고른 이유는 모델이 Markdown보다 JSON을 함부로 고쳐 쓸 가능성이 낮기 때문이라고 밝혔다. 진행 기록은 별도의 `claude-progress.txt`와 git 이력에 둔다. 출처: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

## 4. 접근 방식

오너와 함께 네 가지를 차례로 골랐다.

### 4.1 보기용 보드: GitHub Projects

| 방식 | 판정 |
|---|---|
| **GitHub Projects** | **채택.** 보드 보기가 있고, 카드와 PR이 같은 곳에 있어서 머지 여부를 GitHub가 직접 안다. 동기화할 대상도 하나 줄어든다. |
| Notion 칸반 | 탈락. 오너는 GitHub가 칸반을 지원하지 않을 때만 Notion을 쓰기로 했다. |

### 4.2 카드 단위: 스테이지 하나에 카드 하나

| 방식 | 판정 |
|---|---|
| **A. 카드는 스테이지만** | **채택.** 카드마다 「지금」 한 줄과 「기다림」을 둔다. 묶음·차수 같은 하위 진행은 스테이지 문서의 「진행 기록」에 남긴다. 카드 수가 적고 기록 비용이 낮다. |
| B. 하위 작업도 카드로 | 탈락. 보드는 세밀해지지만 카드가 스테이지보다 몇 배 많아지고, 세션마다 카드를 만들고 닫는 일이 늘어난다. |

### 4.3 코드 스테이지의 카드 이동: 검토 대기를 두 번 지난다

| 방식 | 판정 |
|---|---|
| **A. 검토 대기 두 번** | **채택.** 계획 검토와 결과(PR) 검토 때 모두 카드가 「검토 대기」 열에 온다. 그래서 「검토 대기」 열이 곧 오너가 처리할 일의 목록이 된다. |
| B. 계획 승인에서 끝 | 탈락. 「승인」 열에 구현 중인 카드와 PR 검토를 기다리는 카드가 섞여서, 오너가 처리할 일이 보드에서 보이지 않는다. |

### 4.4 스테이지 문서의 브랜치: 모든 스테이지를 PR로

| 방식 | 판정 |
|---|---|
| **A. 모든 스테이지를 작업 브랜치와 PR로** | **채택.** 스테이지를 시작할 때 초안 PR을 열어 STATUS가 처음부터 PR을 가리킨다. 머지 전 링크 문제가 사라지고, 흐름이 하나라서 규칙이 단순하다. 3단계의 worktree 구조와도 맞는다. |
| B. 코드 없는 스테이지는 기본 브랜치에 바로 | 탈락. 승인 전 초안이 기본 브랜치에 쌓이고 흐름이 두 갈래가 된다. 설계로 시작했다가 프로토타입 코드가 생기는 스테이지(app-factory 2-12)는 도중에 흐름을 바꿔야 한다. |

### 4.5 STATUS 원본 형식: md 표와 커밋 시점 검사

| 방식 | 판정 |
|---|---|
| **A. md 표 한 줄 = 카드 한 장, pre-commit 검사** | **채택.** GitHub에서 사람이 그대로 읽고, SessionStart 훅도 셸 내장 명령만으로 줄 단위로 읽는다. 모델이 Markdown을 망가뜨릴 위험(3절의 Anthropic 사례)은 pre-commit 검사로 막는다. 「원본은 md」 결정을 지킨다. |
| B. STATUS.md 안의 YAML 블록이 원본, 표는 생성 | 탈락. 한 파일에 같은 정보가 두 번 들어가서, AI가 생성된 표를 직접 고치면 다시 어긋난다. 훅에서 YAML을 내장 명령만으로 읽기도 까다롭다. |
| C. 별도 `status.json`이 원본, STATUS.md는 생성 | 탈락. 「원본은 md」 결정을 다시 여는 일이다. 훅이 JSON을 읽으려면 `python`이나 `jq`가 필요해 PATH 제약에 걸린다. 원본과 생성물 두 파일을 관리해야 한다. |

### 4.6 작업 위치: 스테이지 작업은 worktree에서만

빌더 점검에서 나온 문제다. 새 흐름에서는 모든 스테이지가 작업 브랜치를 쓰고, 스테이지 하나에 STATUS 커밋이 5~7번 생긴다. 그런데 2026-11-25 기준 forin의 메인 체크아웃은 `content/or-batch6`, app-factory의 메인 체크아웃은 `ball-roguelite/survive-families`에 있다.

| 방식 | 판정 |
|---|---|
| **A. 메인 체크아웃은 기본 브랜치에 고정, 스테이지 작업은 worktree** | **채택.** 5.5절의 커밋 위치 검사가 정상 작업을 막지 않고, 세션 시작 요약이 늘 최신 STATUS를 읽는다. 여러 세션을 나누는 구조는 3단계에서 정한다. |
| B. 메인 체크아웃에서 브랜치 전환 허용 | 탈락. STATUS를 고칠 때마다 stash와 브랜치 전환이 필요해서, 작업이 섞이거나 사라질 위험이 있다. 기능 브랜치에 있는 동안 요약이 낡은 STATUS를 읽는다. |

결정자: 오너(2026-11-25).

| 칸 | 규칙 |

| 상태 | 5.2절의 여섯 값 가운데 하나다. |
| 줄기 | 카드를 가로로 묶는 기준이다(예: app-factory의 `Yawn`, `공 물리`, `출시`). 비워 둘 수 있다. 같은 줄기는 같은 철자로 쓴다. |

| 링크 | 머지 전에는 PR 링크를, 머지 뒤에는 스테이지 문서의 상대 경로 링크를 쓴다. 머지 뒤에도 PR 링크를 함께 남길 수 있다. PR이 여러 개면 ` · `로 나란히 적는다. |

셀 안에서는 `|`와 줄바꿈을 쓰지 않는다.

**「지금」의 머리말:** 머리말을 두면 STATUS만 보고도 계획이 승인되었는지 알 수 있다. 다음 스테이지로 넘어가는 조건(5.2절)을 STATUS에서 바로 확인할 수 있고, 보류에서 돌아갈 상태도 남는다.

| 상태 | 머리말 |
|---|---|
| `IN_PROGRESS` | `계획: `(계획을 쓰는 중) 또는 `구현: `(계획 승인 뒤 구현하는 중) |
| `AI_PROPOSED` | `계획 검토: ` 또는 `결과 검토: ` |
| `HUMAN_APPROVED` | 머리말 없음. 머지를 기다리는 이유를 쓴다(예: `배포 묶음을 모아 한 번에 머지`). |
| `DEFERRED` | 보류하기 전 상태의 머리말을 그대로 쓰고 보류 이유나 재개 조건을 붙인다(예: `구현: 오너 보류, 출시 뒤 재개`). 다시 시작하면 머리말에 맞는 상태로 돌아간다. |

설계 스테이지는 `계획: `과 `계획 검토: `만 쓴다.

**「오너 할 일」 절의 규칙:**
- 한 줄에 하나씩 `- [ ] <할 일> (막음: <ID>)` 형식으로 쓴다. 막는 스테이지가 없으면 `(막음: …)`을 생략한다. 여러 스테이지를 막으면 `(막음: 3-1, 3-2)`처럼 쓴다.
- 끝난 할 일은 체크하지 않고 줄을 지운다. 지운 내용은 git 이력에 남는다.
- 오너 할 일이 막는 스테이지의 줄에는 「기다림」에 `오너 할 일`이라고 쓴다.

### 5.2 상태 값과 생애주기

상태 값은 보드의 열과 1:1로 대응한다.

| 상태 값 | 보드 열 | 뜻 |
|---|---|---|
| `PENDING` | 대기 | 시작 전 |
| `IN_PROGRESS` | 진행 중 | AI가 작업 중이다. 계획을 쓰는 중이거나, 계획 승인 뒤 구현하는 중이다. |
| `AI_PROPOSED` | 검토 대기 | 오너가 검토할 차례다. 계획 검토인지 결과 검토인지는 「지금」 칸에 적는다. |
| `HUMAN_APPROVED` | 승인 | 오너가 결과를 승인했지만 PR이 아직 머지되지 않았다(예: 「머지·배포는 나중에」). |
| `MERGED` | 머지됨 | 스테이지의 PR이 기본 브랜치에 머지되어 스테이지가 끝났다. |
| `DEFERRED` | 보류 | 오너가 보류했다. 보류 전 상태와 다시 시작할 조건은 「지금」에 적는다(5.1절의 머리말). |

이 여섯 값 밖의 값(`IMPLEMENTED`, `READY`, `APPROVED`, 「완료(날짜)」 같은 글)은 상태 칸에 쓰지 않는다.

**흐름:**
- 설계 스테이지(코드를 만들지 않는 스테이지): `PENDING → IN_PROGRESS → AI_PROPOSED → HUMAN_APPROVED → MERGED`
- 코드 스테이지: `PENDING → IN_PROGRESS → AI_PROPOSED(계획 검토) → IN_PROGRESS(구현) → AI_PROPOSED(결과 검토) → HUMAN_APPROVED → MERGED`
- 오너가 수정을 요청하면 `IN_PROGRESS`로 돌아간다.
- 오너가 보류하면 어느 상태에서든 `DEFERRED`로 가고, 다시 시작하면 「지금」의 머리말이 가리키는 보류 전 상태로 돌아간다.
- 결과를 승인하면서 바로 머지하면 `HUMAN_APPROVED`를 거치지 않고 `MERGED`로 간다.

**승인의 기록:**
- 계획 승인과 결과 승인은 스테이지 문서의 「승인 결과」에 각각 날짜, 결정자와 함께 남긴다(5.3절). STATUS의 상태 칸은 승인 내용을 담지 않는다.
- 설계 스테이지에서는 계획 승인이 곧 결과 승인이다.

**Build Spec 상태와의 관계:** Build Spec의 `READY`는 계획 승인에, `IMPLEMENTED`는 결과 검토 직전에 대응한다. 이 값들은 Build Spec 인덱스 안에서만 쓴다. Build Spec은 「구현 스펙이 얼마나 준비되었는가」를, STATUS는 「스테이지가 보드의 어디에 있는가」를 나타내므로 같은 사실을 두 번 적는 것이 아니다.

**다음 스테이지로 넘어가는 조건:** 앞 스테이지의 계획이 승인되면(스테이지 문서의 「승인 결과」에 계획 승인이 기록되면) 다음 스테이지를 시작할 수 있다. STATUS에서는 앞 스테이지의 줄이 `구현: `·`결과 검토: ` 머리말이거나 `HUMAN_APPROVED`, `MERGED`이면 계획이 승인된 것이다. 결과 승인이나 머지를 기다리지 않는다. 지금 규칙(「HUMAN_APPROVED 없이는 다음 스테이지로 진행하지 않는다」)의 실제 뜻을 그대로 유지하면서, 상태 값의 이름이 바뀐 것에 맞춰 문장을 고친다(5.9절).

**누가 언제 고치는가:** 상태가 바뀌는 순간 그 작업을 하는 세션이 메인 체크아웃에서 STATUS의 그 줄을 고치고 커밋·push한다(1단계 9절의 흐름). 커밋 메시지는 `docs(status): <ID> <새 상태>` 형식의 한 줄이다(예: `docs(status): 2-9 AI_PROPOSED`). 3단계에서는 이 일을 중재자 세션이 맡는다.

### 5.3 스테이지 문서의 변화

- **frontmatter:** `status:`와 `updated:`를 없애고 `id:`를 넣는다. `id:`의 값은 STATUS의 ID와 같다. 그래서 스테이지 문서가 상태를 들고 있지 않게 되고, 어느 줄에 대응하는지만 밝힌다.
  ```yaml
  ---
  id: 2-9
  phase: 02-construction
  stage: lesson-four-steps-v44
  ---
  ```
- **「승인 결과」:** 코드 스테이지는 계획 승인과 결과 승인을 따로 적는다. 템플릿의 「승인 결과」 절 아래를 「계획 승인 (날짜, 결정자)」와 「결과 승인 (날짜, 결정자)」 두 표로 나눈다. 설계 스테이지는 하나만 쓴다.
- **「진행 기록」 절(새로 추가):** 문서 맨 끝에 둔다. 묶음, 차수, 중간 PR 머지 같은 하위 진행을 `- YYYY-MM-DD 내용` 형식으로 한 줄씩, 아래쪽에 덧붙인다. 이 절은 그 스테이지의 작업 브랜치에서 커밋한다.
- **템플릿의 안내 문구:** 「frontmatter의 status를 `HUMAN_APPROVED`로 변경하세요」, 「승인 후 → `STATUS.md`의 이 스테이지 상태를 `HUMAN_APPROVED`로 업데이트」처럼 frontmatter 상태를 전제한 문구를 5.2절의 흐름에 맞게 고친다.
- **시작한 스테이지에는 반드시 스테이지 문서가 하나 있다.** `id:`는 스테이지 문서에만 넣는다. Build Spec 인덱스처럼 스테이지 문서가 아닌 문서에는 `id:`를 넣지 않는다. 그래서 5.5절의 검사는 `id:`가 있는 문서만 스테이지 문서로 본다. 지금 Build Spec 인덱스만 있는 스테이지(forin 2-9)는 이전 때 얇은 스테이지 문서를 새로 만든다(5.8절). `PENDING`이나 `DEFERRED`인 스테이지는 아직 문서가 없어도 된다(app-factory 2-6, 3-1, 3-2).

### 5.4 브랜치와 PR 흐름

1. **스테이지를 시작하면 worktree와 작업 브랜치를 만든다.** 브랜치 이름에 스테이지 ID를 넣는다(예: `feature/3-13-serverless`, `content/2-9-or-batch7`). 접두어는 레포의 기존 관례를 따른다. worktree를 만드는 방법은 아래 「작업 위치」를 따른다.
2. **스테이지 문서를 처음 커밋하면 바로 초안 PR을 연다.** 메인 체크아웃에서 STATUS의 그 줄을 `IN_PROGRESS`(「계획: …」)로 바꾸고, 링크 칸에 PR을 적는다.
   - 초안 PR을 쓸 수 없는 레포에서는 일반 PR을 열고 제목 앞에 `[작업 중]`을 붙인다. 결과 검토 때 이 표시를 뗀다. GitHub 문서에 따르면 개인 계정의 private 레포(app-factory)에서는 초안 PR을 쓸 수 없을 수 있다(10절). 보드의 열은 STATUS의 상태 값으로 정해지므로, 초안 여부는 흐름에 영향을 주지 않는다.
3. **계획 검토:** 계획이 준비되면 STATUS를 `AI_PROPOSED`(「계획 검토: …」)로 바꾼다. 오너는 PR에서 문서를 보거나 채팅으로 답한다. AI는 그 답을 브랜치에 있는 스테이지 문서의 「승인 결과」에 기록한다.
4. **구현:** 코드 스테이지는 계획 승인 뒤 STATUS를 `IN_PROGRESS`(「구현: …」)로 되돌리고 구현한다.
5. **결과 검토:** 결과가 준비되면 PR을 초안에서 검토 준비 상태로 바꾸고, STATUS를 `AI_PROPOSED`(「결과 검토: …」)로 바꾼다.
6. **승인과 머지:** 오너가 결과를 승인하면 `HUMAN_APPROVED`로 바꾼다. PR은 오너가 머지하거나, 오너의 지시를 받아 AI가 머지한다. 머지한 세션이 STATUS의 줄을 `MERGED`로 바꾸고, 링크 칸을 문서 경로로 바꾼다.
7. **GitHub에서 직접 머지된 경우:** 오너가 GitHub 화면에서 PR을 머지하면 STATUS를 고칠 세션이 없다. 그래서 `waypoint:start`는 세션을 시작할 때 활성 줄의 PR 상태를 `gh pr view`로 확인하고, 머지된 PR이 있으면 그 줄을 정리한다(5.7절).

**PR이 여러 개인 스테이지:** forin의 콘텐츠 묶음처럼 한 스테이지에서 PR이 여러 개 나오면, 링크 칸에 PR을 나란히 적는다. 각 PR이 무엇을 합치는지는 그 PR이 머지되기 전에 PR 안에서 「진행 기록」에 한 줄로 써 둔다. 그래서 중간 PR이 머지된 뒤 기록하려고 따로 커밋할 필요가 없다. 스테이지는 그동안 `IN_PROGRESS`나 `AI_PROPOSED`에 머문다. 마지막 PR이 머지되고 오너가 스테이지를 마치면 `MERGED`로 둔다.

**옛 흐름에서 시작한 스테이지:** 이전 때 이미 문서가 기본 브랜치에 있고 링크 칸에 PR이 없는 활성 줄(5.8절)은 다음처럼 마무리한다.
- 남은 일이 승인 기록뿐이면(오너가 계획이나 결과를 승인함), 메인 체크아웃에서 스테이지 문서의 「승인 결과」를 기본 브랜치에 바로 커밋한다. 결과 승인이면 머지할 PR이 없으므로 바로 `MERGED`로 둔다.
- 코드나 문서를 더 고쳐야 하면, 그때 작업 브랜치와 PR을 열고 위의 흐름을 따른다.
- 이 예외는 이전 때 PR 없이 남은 줄에만 적용한다. 새로 시작하는 스테이지에는 적용하지 않는다.

**앞 스테이지가 아직 머지되지 않았을 때:** 다음 스테이지는 앞 스테이지의 계획 승인 뒤에 시작할 수 있지만, 승인된 계획 문서는 앞 스테이지의 브랜치에만 있다.
- 앞 스테이지의 코드가 필요하면, 앞 스테이지의 브랜치 위에 새 브랜치를 쌓는다(stacked PR). forin의 #33 위에 #34~#38을 쌓은 방식과 같다. 앞 PR이 머지되면 새 브랜치를 기본 브랜치에 rebase한다(`waypoint:git`의 브랜치 규칙).
- 문서만 필요하면, 기본 브랜치에서 새 브랜치를 시작하고 앞 스테이지의 문서는 `git show origin/<앞 브랜치>:<경로>`로 읽는다.

**공유 문서는 그대로:** STATUS, DECISIONS, 핸드오프는 1단계 9절대로 메인 체크아웃에서 기본 브랜치로 바로 커밋한다.

**작업 위치(오너 결정, 4.6절):**
- 메인 체크아웃은 늘 기본 브랜치에 둔다. 메인 체크아웃에서 기능 브랜치를 체크아웃하지 않는다.
- 스테이지의 작업 브랜치는 worktree에서만 다룬다. 기본 방법은 메인 체크아웃 옆에 `<레포>-<ID>` 이름으로 만드는 것이다(예: `git -C <메인> worktree add ../forin-2-9 -b content/2-9-or-batch7`). app-factory가 이미 `app-factory-yawn`처럼 쓰는 방식이다.
- Claude Code나 데스크톱 앱이 세션용 worktree를 만들어 주는 경우에는 그 worktree를 써도 된다.
- 세션의 임시 디렉터리(scratchpad)에는 worktree를 만들지 않는다. 재부팅이나 정리 때 지워질 수 있다.
- 스테이지가 `MERGED`가 되면 그 worktree를 `git worktree remove`로 지운다.
- 여러 작업 세션을 어떻게 나누고 누가 어떤 worktree를 맡는지는 3단계에서 정한다.

### 5.5 pre-commit 검사

플러그인에 `githooks/pre-commit`을 둔다. commit-msg 훅처럼 각 레포의 `.githooks/`에 사본을 두고 `core.hooksPath .githooks`로 쓴다. POSIX sh로 쓰고, 이 훅은 커밋 시점에 실행되므로 `git`, `awk`, `sed`, `grep`을 쓸 수 있다.

**적용 범위:** 레포에 `docs/waypoint/STATUS.md`가 없으면 아무것도 하지 않고 통과한다. 커밋에 `docs/waypoint/STATUS.md`나 `docs/waypoint/DECISIONS.md`가 들어 있을 때만 검사한다. 검사 대상은 작업 트리가 아니라 index(stage된 내용)다.

**검사 1: 커밋 위치.** 현재 브랜치가 기본 브랜치가 아니면, STATUS.md나 DECISIONS.md를 바꾸는 커밋을 거부한다. detached HEAD도 거부한다. 「메인 체크아웃에서 기본 브랜치로 커밋한다」는 규칙은 지금까지 지시로만 있었는데, 이 검사로 기계적으로 지키게 한다.
- 예외: 1단계 절차 M에서 STATUS를 변환하는 커밋은 `chore/waypoint-plugin` 브랜치에서 일어난다(5.8절). 이때는 환경변수 `WAYPOINT_ALLOW_BRANCH_STATUS=1`을 붙여 커밋한다. 이 변수는 검사 1만 건너뛰고 검사 2는 그대로 실행한다. 스킬은 이 변수를 절차 M에서만 쓰도록 안내한다. 그 밖의 예외는 오너가 판단해서 `--no-verify`로 넘긴다.

**검사 2: STATUS 형식.** STATUS.md가 커밋에 들어 있으면 다음을 검사한다.
1. `## 스테이지` 절이 있고, 그 아래 표의 머리 줄이 `| ID | 스테이지 | 상태 | 줄기 | 지금 | 기다림 | 링크 |`와 같다.
2. 표의 줄마다 칸이 정확히 7개다.
3. 상태 값이 5.2절의 여섯 값 가운데 하나다.
4. ID가 `<단계>-<번호>` 형식이고 중복되지 않는다.
5. 「지금」이 80자 이하다. `PENDING`과 `MERGED` 줄의 「지금」은 비어 있다. `IN_PROGRESS`, `AI_PROPOSED`, `DEFERRED` 줄의 「지금」은 5.1절의 머리말로 시작한다.
6. `MERGED` 줄의 링크 칸에 스테이지 문서의 상대 경로 링크가 있고, 그 파일이 index에 있으며, 그 파일의 `id:`가 줄의 ID와 같다.
7. `PENDING`, `MERGED`, `DEFERRED`가 아닌 줄에는 PR 링크나 문서 링크가 하나 이상 있다.
8. index에서 `docs/waypoint/` 아래 `id:` frontmatter가 있는 문서마다, 그 ID의 줄이 표에 있다. (app-factory 2-15처럼 줄이 빠진 경우를 잡는다.)
9. 「오너 할 일」 줄의 `(막음: …)`에 적힌 ID가 표에 있다.
10. 파일 전체가 5.1절의 구조만 담고 있다. 허용하는 줄은 제목 한 줄(`# `), 링크 한 줄, `## 스테이지`와 그 표, `## 오너 할 일`과 `- [ ] ` 줄, 빈 줄뿐이다. 옛 배너는 `##` 절이 아니라 머리말 아래의 인용 블록과 굵은 글씨 문단으로 자랐으므로, 절 이름만 검사해서는 막을 수 없다.

**실패 메시지:** 어느 줄의 어떤 검사가 실패했는지, 어떻게 고치는지를 한국어 한두 줄로 출력하고 종료 코드 1로 끝낸다.

**검사 스크립트의 재사용:** 검사 2의 본문은 별도 스크립트(`plugin/scripts/status-check.sh`)로 두고, pre-commit 훅의 사본에도 같은 내용을 넣는다. 4단계의 동기화 스크립트도 동기화 전에 같은 검사를 통과해야 한다. 플러그인 안의 훅과 원본 스크립트가 어긋나지 않는지는 waypoint 레포의 테스트가 확인한다.

**레포에 복사된 훅이 낡는 문제:** 형식이 바뀌어 플러그인의 훅이 갱신되어도, 각 레포의 `.githooks/pre-commit` 사본은 그대로 남는다. 그래서 훅 파일 둘째 줄에 `# waypoint-hook-version: <번호>`를 두고, `session-context.sh`가 레포 사본의 번호가 플러그인의 번호보다 낮으면 「`.githooks/pre-commit`이 낡았다. 플러그인의 `githooks/pre-commit`으로 바꿔라」라는 경고 한 줄을 출력한다. 두 파일의 둘째 줄을 `read`로 읽어 비교하므로 셸 내장 명령만으로 된다.

**기존 pre-commit과의 관계:** 2026-11-25 기준 다섯 레포의 `.githooks/`에는 `commit-msg`만 있고 `pre-commit`은 없다(확인). 이전 때 이미 `pre-commit`이 있으면, 기존 훅을 지우지 않고 그 끝에서 waypoint 검사를 부르도록 합친다.

### 5.6 SessionStart 주입

`session-context.sh`가 핵심 규칙과 안내 뒤에 활성 스테이지 요약을 붙인다. STATUS는 메인 체크아웃의 것을 읽는다.

**레포 안에서 시작한 세션:**

```
현황(forin): 진행 중 1 · 검토 대기 1 · 승인 0 · 대기 3 · 보류 0 · 오너 할 일 1
- 2-9 IN_PROGRESS [콘텐츠] 구현: OR 묶음 7 저작 중, 남은 OR 21주제
- 3-1 AI_PROPOSED [출시] 결과 검토: Android 첫 빌드 (기다림: 오너 할 일)
오너 할 일:
- Google Play 서비스 계정 키 발급 (막음: 3-1)
```

- 활성 줄은 상태가 `IN_PROGRESS`, `AI_PROPOSED`, `HUMAN_APPROVED`인 줄이다. 형식은 `- <ID> <상태> [<줄기>] <지금> (기다림: <기다림>)`이고, 빈 칸은 생략한다.
- 요약 전체(개수 줄, 활성 줄, 오너 할 일)는 20줄 이하로 제한한다. 넘치면 마지막 줄을 `… 외 N개 (STATUS.md 참조)`로 바꾼다.

**레포 밖에서 시작한 세션:** 레포마다 개수 한 줄만 붙인다.

```
현황(forin): 진행 중 1 · 검토 대기 1 · 승인 0 · 대기 3 · 보류 0 · 오너 할 일 1
현황(shadow): 진행 중 0 · 검토 대기 1 · 승인 0 · 대기 8 · 보류 0 · 오너 할 일 0
```

**구현 제약:**
- 셸 내장 명령만 쓴다. 표는 `while IFS='|' read -r …`로 줄 단위로 읽고, 앞뒤 공백은 매개변수 확장으로 지운다.
- STATUS가 새 형식이 아니면(`## 스테이지` 절과 정해진 머리 줄이 없으면) 요약을 붙이지 않고 지금처럼 핵심 규칙과 안내만 출력한다. 플러그인 변경이 머지된 뒤 레포의 STATUS가 변환되기 전까지의 기간을 위한 처리다.
- 메인 체크아웃이 기본 브랜치에 있지 않으면 요약 앞에 경고 한 줄을 붙인다(예: `경고: 메인 체크아웃이 기본 브랜치가 아니다(현재 content/or-batch6). 요약이 낡았을 수 있다.`). 현재 브랜치는 `<메인>/.git/HEAD`를 `read`로 읽어서 알아낸다.
- 레포 밖에서 시작했을 때 `<레포>-<ID>` worktree도 `*/docs/waypoint/STATUS.md`에 걸린다. 같은 메인 체크아웃을 가리키는 항목은 한 번만 출력한다.
- compact 뒤에도 같은 요약이 다시 주입된다(3절).

### 5.7 `waypoint:start`의 새 절차

1. 세션 시작 때 주입된 요약을 확인한다. STATUS 전체는 필요할 때만 읽는다.
2. 활성 줄 가운데 링크 칸에 PR이 있는 줄은 `gh pr view`로 PR 상태를 확인한다. 머지된 PR이 그 스테이지의 마지막 PR이면 오너에게 알리고 `MERGED`로 정리한다. 중간 PR이면 STATUS를 바꾸지 않는다(그 PR의 기록은 머지 전에 PR 안에 써 두었다, 5.4절).
3. 오너가 지정한 카드가 있으면 그 카드를 이어서 진행한다.
4. 새 스테이지를 시작할 때는 오너가 정한 스테이지를 고른다. 오너가 정하지 않았다면 `PENDING` 가운데 ID가 가장 앞선 스테이지를 제안하고 오너의 확인을 받는다.
5. `AI_PROPOSED` 카드는 오너가 답하기 전에는 건드리지 않는다.
6. 스테이지 문서를 쓰기 전에 `waypoint:stage`를 호출한다(지금과 같다).

### 5.8 기존 STATUS의 이전

**시점:**
- **shadow:** 이미 `docs/waypoint/`로 이전되어 절차 M을 다시 거치지 않는다. 그래서 이 단계의 플러그인 변경이 머지되면 바로 메인 체크아웃에서 다음을 한다. 이 작업으로 형식, 검사, 훅 주입을 검증한다.
  1. 플러그인의 `githooks/pre-commit`을 `.githooks/pre-commit`으로 복사하고 실행 권한을 준다(`core.hooksPath`는 이미 `.githooks`다).
  2. `CLAUDE.md`의 waypoint 블록을 새 `claude-md-block.md` 템플릿대로 고친다.
  3. 아래 변환 절차로 STATUS를 변환한다.
  4. 훅 사본과 CLAUDE.md를 먼저 커밋하고, 변환은 따로 커밋한다.
- **tokens-are-running-out, duty, app-factory, forin:** 1단계 절차 M의 이전 PR(`chore/waypoint-plugin`)에 STATUS 변환을 함께 넣는다. waypoint의 `projects/` 아래에서 미리 변환하지 않는다. 그곳에서는 다른 세션들이 옛 형식으로 계속 기록하고 있어서 충돌이 나기 때문이다.
  - 변환은 절차 M의 새 단계 「M6a」로 넣는다. M5(경로 바꾸기)와 M6(설정·훅·CLAUDE.md)이 끝난 뒤, M7(CI) 전에 한다. M6에서 `pre-commit`이 설치되어야 변환 결과를 검사할 수 있기 때문이다.
  - 변환의 기준이 되는 옛 STATUS는 M6a 직전 커밋(M5의 경로 치환이 반영된 상태)의 `docs/waypoint/STATUS.md`다.
  - M8(검증)의 grep 예외 목록에 `docs/waypoint/HISTORY.md`를 넣는다. 옛 기록이므로 옛 경로 언급이 남아 있어도 고치지 않는다.
- 절차 M의 9번(머지 직전 재확인)에서 `projects/<name>`에 새 커밋이 들어와 다시 떼어 내면, 변환도 다시 한다.
- 이전을 시작하기 전에 메인 체크아웃이 기본 브랜치에 있어야 한다. 메인 체크아웃에서 진행 중인 브랜치가 있으면 그 브랜치를 맡은 세션이나 오너가 먼저 worktree로 옮긴다. 절차 M의 M0(사전 조건)에 이 확인을 추가한다.

**변환 절차(레포마다 같다):**
1. **옛 STATUS 전체를 HISTORY.md로 옮긴다.** 옛 STATUS.md를 표까지 포함해 글자 그대로 `docs/waypoint/HISTORY.md`로 복사한다. 셀 안에만 있는 기록(forin 2-5·2-6·R-2 셀의 긴 글 등)이 많고, forin은 셀이 여러 줄로 이어지거나 표 사이에 인용 블록이 끼어 있어서 표와 배너의 경계를 기계적으로 가를 수 없기 때문이다. 파일 맨 위에 「YYYY-MM-DD STATUS 정리 때 옮긴 기록이다. 이후로는 쓰지 않는다.」라는 안내 줄과 빈 줄을 덧붙인다. 이 파일은 그 뒤로 고치지 않는다.
2. **표를 새 형식으로 만든다.** 옛 표의 줄마다 ID, 스테이지 이름, 상태를 옮긴다. 스테이지 이름의 괄호 설명과 셀의 긴 글은 HISTORY.md에 그대로 남아 있으므로 새 표에서는 줄인다.
3. **상태 값을 바꾼다.**

   | 옛 값 | 새 값 | 조건 |
   |---|---|---|
   | `HUMAN_APPROVED`, `APPROVED` | `MERGED` | 표와 frontmatter가 같을 때. 옛 흐름에서는 문서가 이미 기본 브랜치에 있다. |
   | `IMPLEMENTED` | `AI_PROPOSED` | 「지금」은 「결과 검토: …」 |
   | `READY` | `IN_PROGRESS` | 계획은 승인되었고 구현 중이다. 「지금」은 「구현: …」 |
   | `PENDING`, `IN_PROGRESS`, `AI_PROPOSED`, `DEFERRED` | 그대로 | 표와 frontmatter가 같을 때. `IN_PROGRESS`, `AI_PROPOSED`, `DEFERRED`는 「지금」의 머리말(계획인지 구현·결과인지)을 스테이지 문서의 승인 결과와 Build Spec 상태로 판단한다. 판단할 수 없으면 오너 확인. |
   | 「완료(날짜)」 같은 글 | 오너 확인 | |
   | 표와 frontmatter가 다른 값 | 오너 확인 | |

4. **활성 줄의 「지금」과 「기다림」, 「오너 할 일」을 채운다.** 「지금」은 가장 최근 배너와 셀 내용에서 한 줄로 줄인다. ⏳로 표시된 오너 작업은 「오너 할 일」로 옮긴다. 옛 흐름에서 만든 스테이지는 문서가 이미 기본 브랜치에 있으므로, 링크 칸에는 문서 경로를 쓴다.
5. **스테이지 문서를 고친다.** frontmatter에서 `status:`, `updated:`를 빼고 `id:`를 넣는다. 「진행 기록」 절을 만들고 첫 줄에 「이전 기록은 [HISTORY.md](../HISTORY.md)에 있다.」라고 적는다. 상대 경로는 문서 위치에 맞춘다.
   - 활성이거나 `MERGED`인데 스테이지 문서가 없는 스테이지(forin 2-9처럼 Build Spec 인덱스만 있는 경우)는 얇은 스테이지 문서를 새로 만든다. 이 문서에는 `id:` frontmatter, 목적 한 줄, Build Spec 링크, 「승인 결과」, 「진행 기록」만 둔다. 새 표의 링크 칸은 이 문서를 가리킨다.
6. **오너 확인 목록을 만든다.** 다음 항목을 한 목록으로 보여 주고 오너의 답을 받는다.
   - 3번에서 「오너 확인」으로 분류된 줄
   - 문서는 있지만 표에 없는 스테이지(app-factory 2-15)
   - 표에는 있지만 스테이지가 아닌 항목(forin의 「병행 트랙: 콘텐츠 워크스트림」 등). ID가 있는 스테이지로 만들지, HISTORY.md에만 남길지 정한다.
   - 어느 스테이지에도 연결되지 않은 Build Spec(forin의 `journey-binder-v42`, `binder-shelf-buildings-v45`, `lesson-fidelity-v46`, `home-calendar-v47`, `curriculum-v3-journey-ia` 등). 어느 스테이지에 붙일지, 그대로 둘지 정한다.
   - app-factory의 상태판에서 스테이지가 아닌 줄(아래 「app-factory 상태판」).

**app-factory 상태판:** app-factory STATUS 맨 위에는 오너가 만든 「세션 역할」 표와 「앱별 상태판」(앱 · 단계 · 담당 · 다음)이 있다. 새 형식에는 이 표들을 둘 자리가 없으므로(5.5절 검사 10) 다음처럼 나눈다.
- 두 표는 다른 내용과 함께 HISTORY.md에 그대로 남는다.
- 앱별로 묶어 보는 기능은 「줄기」 칸이 대신한다. Yawn 스테이지(2-9, 2-11, 2-12, 2-14, 2-16)에는 `Yawn`, 공 물리(2-15)에는 `공 물리`, 출시 관련 스테이지에는 `출시`를 쓴다.
- 「다음」 칸의 내용은 해당 스테이지 줄의 「지금」과 「기다림」으로 옮긴다.
- 「담당」(어느 세션이 어느 worktree에서 무엇을 맡는가)은 STATUS가 아니라 3단계 중재자 세션이 관리할 정보다. 3단계 전까지는 HISTORY.md에 남은 표를 참고한다.
- 「공통: CI 빨강 → Flutter 3.50.0 업그레이드 PR #24」처럼 스테이지가 아닌 작업(CI 수리, 도구 업그레이드 같은 chore PR)에는 STATUS 줄을 만들지 않는다. 그런 작업이 어떤 스테이지를 막으면 그 스테이지의 「기다림」에 적는다(예: `PR #24 CI 수리`).
7. **검증한다.** HISTORY.md에서 맨 위 안내 줄과 빈 줄을 뺀 내용이 옛 STATUS.md와 글자 단위로 같은지 `diff`로 확인한다. 새 STATUS가 5.5절의 검사를 통과하는지 확인한다.
8. **커밋한다.** shadow는 메인 체크아웃에서 기본 브랜치로 바로 커밋한다. 나머지 네 레포는 `chore/waypoint-plugin` 브랜치에서 `WAYPOINT_ALLOW_BRANCH_STATUS=1`을 붙여 커밋한다.

## 6. 3단계·4단계와의 관계

- **3단계:** 중재자 세션이 메인 체크아웃에서 STATUS를 혼자 쓴다. 작업 세션은 worktree에서 스테이지 브랜치를 맡고, 상태가 바뀌면 중재자에게 보고한다. 한 줄이 카드 한 장인 형식이라 보고를 줄 단위로 반영할 수 있다. 5.4절의 「머지한 세션이 STATUS를 고친다」와 5.7절의 머지 정리는 3단계에서 중재자의 일로 옮긴다.
- **4단계:** 동기화 스크립트가 5.5절의 검사를 통과한 STATUS를 읽어 GitHub Projects의 카드를 만들고 갱신한다.
  - 카드의 열쇠: 레포 + ID
  - 열: 상태 값(5.2절의 대응표)
  - 필드: 줄기, 지금, 기다림, 단계(ID의 앞자리)
  - PR 연결: 링크 칸의 PR 번호
  - 카드를 레포의 이슈로 만들지, 프로젝트의 초안 카드로 만들지는 4단계에서 정한다.
  - 보드에서 사람이 바꾼 값은 다음 동기화 때 md 값으로 덮어쓴다(단방향).

## 7. 오너가 정한 것 (2026-11-25)

- 보기용 보드는 GitHub Projects로 하고, Notion은 쓰지 않는다(4.1절).
- 카드는 스테이지 하나에 하나만 둔다(4.2절).
- 코드 스테이지의 카드는 검토 대기를 두 번 지난다(4.3절).
- 모든 스테이지를 작업 브랜치와 PR로 진행한다(4.4절).
- STATUS의 원본은 md 표로 하고, 커밋 시점에 형식을 검사한다(4.5절).
- 메인 체크아웃은 늘 기본 브랜치에 두고, 스테이지 작업은 worktree에서만 한다(4.6절, 빌더 점검 뒤 결정).
- 5.1~5.9절의 설계를 세 부분으로 나눠 검토하고 승인했다(STATUS 모양과 생애주기, 흐름과 검사와 주입, 이전과 규칙 변경).

- 메인 체크아웃이 기본 브랜치가 아닐 때 세션 시작 요약에 경고를 붙이고, 레포 밖 세션에서는 같은 메인 체크아웃을 한 번만 출력함(5.6절).

## 10. 미확인 사항

- **macOS 기본 `awk`와 셸이 한글을 글자 단위로 세는지**(미확인). 훅이 실행되는 로케일에 따라 `${#var}`와 `awk`의 `length`가 바이트 수를 낼 수 있다. 구현 때 실측하고, 안 되면 다른 방법을 쓴다.
- **github.com의 Projects 기본 워크플로에 「PR이 머지되면 Done으로」가 있는지**(2차 자료). GitHub Enterprise Server 3.21 문서에서만 확인했다. 이 설계는 이 워크플로에 의존하지 않는다. 4단계 착수 전에 재확인한다. 출처: https://docs.github.com/en/enterprise-server@3.21/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations
- **사용자 계정 프로젝트에 private 레포(app-factory)의 항목을 넣었을 때의 표시 범위**(미확인). 4단계 착수 전에 확인한다.
- **app-factory(개인 계정의 private 레포)에서 초안 PR을 열 수 있는지**(2차 자료). GitHub REST API 문서는 초안 PR을 GitHub Free·Pro에서는 public 레포에서만, private 레포에서는 Team·Enterprise Cloud에서만 쓸 수 있다고 적는다. 다만 이 문서는 오래되었을 수 있다. app-factory에는 지금까지 초안 PR이 하나도 없었다(2026-11-25 `gh pr list` 확인). 이 설계는 초안 PR을 쓸 수 없으면 `[작업 중]` 제목 표시로 대신하므로(5.4절) 흐름은 막히지 않는다. 구현 때 app-factory에서 `gh pr create --draft`를 한 번 시험해 어느 쪽을 쓸지 정한다. 출처: https://docs.github.com/en/rest/pulls/pulls
